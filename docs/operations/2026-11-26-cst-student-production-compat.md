## 동일 서비스 호환 빌드

#533의 운영 1단계 산출물은 승인된 `59f09e212f1531f60d55b14cb0cbb240e37fc69a`에서 빌드한다. 이 버전은 운영 `retaste-beta`의 #475 기준 소스에 공식 장소 사진과 A·B 실증 화면·경로를 결합한다. 현재 main의 다른 관리 기능과 보류 스키마는 이 빌드에 포함하지 않는다. 실행에 앞서 현재 운영 버전, 대상 계정, 적용 순서 그대로의 D1 장부 56개, 기존 바인딩·두 cron을 읽어 대조한다. 기준 순서에서는 0032가 0031보다 먼저 적용됐다.

```sh
release_dir=$(mktemp -d)
node scripts/build-official-photo-release.mjs "$release_dir/candidate" --student-pilot
```

후속 main의 빌드는 공개 위치와 장소 상세 평가 진입, 모바일 시트 안 평가 패치를 적용한다. `publicLocationPatchSha256`, `placeDetailVoteLinkPatchSha256`, `publicVotePatchSha256` 및 공유 파일 해시를 기록한다. #533 1단계는 승인된 입력 커밋과 두 패치의 해시를 사용한다.

생성된 후보는 학생 좌석 설정과 실증 버킷 바인딩이 비어 있다. 기존 `REVIEW_PHOTOS`, 전역 리뷰 사진 비활성 설정, 공식 장소 사진 레지스트리를 유지한다. `student-pilot-release.json`에 입력 커밋, 두 패치, 각 소스, 장부 기준과 번들 해시가 들어 있다. 기존 12개 공개·인증 HTTP 응답, 두 예약 작업, 현재 공식 사진 프레임과 모바일 장소 화면을 56개 장부에서 확인한다. 0065만 더한 57개 장부와 합성 비공개 R2에서 학생 작업공간에서 신청·방문 리뷰로 진입하는 경로, 두 좌석의 업로드·승인·철회, 범위 밖 좌석 차단, 데스크톱과 모바일 출처 표시, 지연 쓰기 정리를 확인한다.

## 운영 전환 순서

1. 별도 실행 PR에 정확한 운영 Worker와 시작 버전, 운영 자원, 적용할 0065 파일의 SHA-256, 명령과 한도, 담당자 및 회수 절차를 기록한다. 이 준비 문서는 R2 생성·운영 D1 적용·배포·실제 계정 변경을 승인하지 않는다.
2. 실행 PR에 지정된 전용 표준 R2 한 개의 비공개 상태를 확인한다. 공개 개발 URL과 커스텀 도메인을 연결하지 않는다. 기존 사진 버킷에 대한 새 쓰기 경로는 열지 않는다.
3. 운영의 기존 Worker에 100%를 유지한 상태에서 0065 한 파일만 명시한 별도 마이그레이션 설정을 검증한다. 실제 적용 순서 56개의 장부에서 대기 목록이 그 한 파일과 정확히 일치할 때만 적용한다. 적용 뒤 적용 순서의 장부 57개, 대기 0개, 새 원장 0행 및 기존 장소 원장·공개 검수 연결·좌석의 일치를 읽어 확인한다. 운영 전체 마이그레이션 디렉터리를 적용하지 않는다.
4. 후보와 같은 설정에 새 비공개 바인딩만 추가한다. 학생 좌석은 미지정 상태로 배포한다. 기존 변수·비밀 이름·바인딩·두 cron을 대조하고, 기존 공개·관리 인증 경로와 신규 사진 접수가 닫혀 있는지를 확인한다. 바인딩을 추가한 최종 설정 해시, 업로드 버전과 적용한 좌석 설정을 단계마다 기록하고 전환 전에 대조한다. 새 cron은 만들지 않는다.
5. A·B는 인증된 기존 계정으로 스스로 리뷰어를 신청한다. 활동 자격은 운영자가 기존 B08의 미리보기, 사유와 재인증으로 승인한다. 합성 계정이나 다른 사람의 로그인으로 실제 참여를 대신하지 않는다. 개별 수신자와 문안 승인을 받은 뒤 안내를 각각 발송한다.
6. 별도 승인 범위에서 A부터 연다. 실제 방문 리뷰와 직접 촬영 JPEG 한 장에서 작성자 미리보기, 승인 전 비공개, 관리자 승인, 공개 상세와 출처를 운영에서 확인한다. B는 A의 결과 확인 뒤 추가한다. 기능의 저장 상한은 현재 리뷰 버전당 한 장이다. 첫 제출 확인의 관측 범위는 좌석당 한 장소다. 방문과 검수 판단은 실제로 수행한 시점에 기록한다.

## 회수와 원장 보존

좌석 설정을 비우면 새 첨부가 닫힌다. 기존 승인 사진의 비노출이 필요하면 운영자가 정확한 ID를 회수하고 익명 GET·HEAD를 확인한다. 실증 이력이 생긴 뒤에는 새 테이블과 비공개 R2를 보존한다. 이미 시작된 쓰기와 철회 작업을 추적하려면 실증 바인딩을 붙인 호환 Worker의 기존 정리 cron을 유지해야 한다. 일시적으로 직전 Worker로 트래픽을 회수한 경우 담당자가 좌석 미지정 호환 버전을 다시 배포하고 정확한 정리 대상을 대조한다. 모호한 쓰기에는 예약 키 원장을 유지한다. 보존 기간과 수동 처분 기준은 운영 책임자가 확정한다.
