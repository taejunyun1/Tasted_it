# B13 개인정보 요청·사진 정리 운영

상태: 구현·로컬 검증 중. #453. 실제 정책과 운영 삭제 완료를 뜻하지 않는다.

## 범위

- 인증된 회원이 `/me/privacy`에서 자신의 요청 유형(열람·정정·삭제·처리정지)만 접수한다. 신분증·사진·추가 연락처·자유 문안을 수집하지 않는다. 같은 유형의 진행 중 요청은 중복 생성하지 않는다.
- `/admin/privacy`는 최근 요청 50건과 사진 정리 계획 25건을 cursor로 조회한다. 요청의 검토·정책 대기·기존 경로 안내를 기록하며 실제 개인정보 전체 열람·삭제 완료로 표시하지 않는다.
- ADMIN 상태 변경과 사진 재시도 대기는 현재 관리자·최근 재인증·미리보기·CAS·감사 영수증을 요구한다. 관리자 화면은 임의 리뷰/파일의 삭제 계획을 만들 수 없다.
- 사진 DELETE의 근거는 실제 작성자 WITHDRAW 전이 또는 계정 탈퇴다. 관리자 MODERATE 회수는 근거가 아니다. ORPHAN은 기존 미참조 업로드 보상 경로로 남는다.

## 실행 경계

기존 계획을 보존하고 revision, 상태, 실행 소유권, 실행 기한, 제한된 오류 코드를 추가한다. 같은 계획을 다시 요청해도 실행 중 소유권을 초기화하지 않는다. cron과 소유자 후처리는 같은 원자 claim을 사용한다. 객체 키는 기존 `reviews/<reviewId>/...jpg`의 명시 목록만 사용하며 버킷 목록 조회나 wildcard 삭제는 없다.

R2 이후 metadata·photoCount·계획 삭제와 완료 감사는 같은 D1 batch에서 실행 소유권과 revision을 검증한다. 앞선 계획의 늦은 완료는 새 계획을 삭제하지 않는다. ORPHAN 정리가 실행된 뒤 기존 업로드가 늦게 D1에 사진 참조를 남기는 것도 같은 batch의 guard로 거절한다.

최대 100개 키 계획은 D1 조회·삭제의 review ID 바인딩을 남긴 99개 단위로 나눈다. ORPHAN 계획이 먼저 정리된 뒤 원래 PUT이 늦게 끝난 경우에는, 리뷰가 아직 없는지 확인해 정확한 키의 보상 계획을 다시 확보한다. 이 계획은 업로드 확정에 재사용할 수 없으며 기존 DELETE 계획을 덮어쓰지 않는다.

실패 응답은 1시간 뒤 기존 정리 작업에서 재시도하며, 관리자 확정은 같은 계획을 대기에 올릴 뿐 즉시 R2를 호출하지 않는다. 실행 기한이 지난 RUNNING은 결과 미확인으로 표시하고 자동 탈취·재실행하지 않는다. 이미 전송된 외부 삭제는 원격 취소할 수 없으므로, 결과불명은 추가 관측/운영 판단이 필요하다. 이 제한을 완료로 숨기지 않는다.

## 보존·정책

0055는 기존 계획·원문·감사·작업 영수증을 보존한다. 새 `privacy_requests`에는 회원 관계키, 유형, 상태, revision, 결정 코드/담당자, 접수·갱신 시각만 남는다. 신원 증빙이나 요청 상세는 없다. 새 자동 TTL·법정 처리기한·법적 보존기간을 만들지 않으며 #360의 실제 정책 확인이 필요하다. 완료 감사에는 키 목록·사진·이메일 없이 작업 참조/목적/revision/시도/건수만 기록한다. transaction guard 테이블은 같은 batch에서 생성·삭제되어 성공 후 비어 있다.

## 필수 검증·운영

소유 근거 없는 DELETE 차단, 정확-key·부분 실패 재시도, 동일 계획의 cron/수동 중복, 새 revision에 대한 늦은 완료, ORPHAN 참조 보호, 접수 중복/소유권, 관리자 재인증/CAS, desktop/mobile만 검증한다. 로컬 D1/R2 합성 자료를 사용한다. 운영 검증은 읽기·권한 부정 경로·기존 RSI만 수행하고 실제 개인정보 접수/사진 삭제를 실행하지 않는다. 적용 순번·기존 table count/FK·main 배포·직전 Worker rollback·스키마 보존 범위는 병합 PR에 확정한다.
