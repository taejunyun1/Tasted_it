## 구현 한계와 운영 전환

- 취소 범위는 해당 공공 인허가 수집의 새 요청 허용과 페이지 DB 저장이다. 이미 허용된 공공 API GET 자체를 공급자에서 취소했다는 뜻은 아니다. 공공 수집 뒤 실행하는 NAVER 검증·자동 검수는 별도 작업이며 이 취소의 대상이 아니다.
- `request_count`는 신규 코드에서 허용한 HTTP 시도를 세며 이전 버전의 과거 호출은 소급 추정하지 않는다.
- 페이지 완료 전 장애는 페이지의 모든 자료/부수 변경/집계를 rollback한다. 이미 완료한 페이지는 보존한다.
- 새 코드가 기록한 lease를 가진 오래된 실행은 lease 교체로 기존 worker의 페이지 쓰기를 차단한다. 기존 버전의 `RUNNING` 중 lease가 없는 기록은 결과 불명으로 격리하며 해당 기록의 재개·취소를 허용하지 않는다. 이런 기록이 한 건이라도 남아 있으면 출처·주소 구분을 넘어 모든 공공 동기화의 새 실행과 재개를 중단한다. 다른 미완료 `PENDING`/`RUNNING`이 같은 출처·주소 구분에 있으면 새 claim과 재개 확정도 거절한다. 기존 cron 식과 외부 endpoint/지역은 유지한다.
- 운영 전환은 B10 평가·공공·주차/EV PR 병합 뒤 0050~0052 순차 migration과 합동 배포/필수 live 검증 계획으로 수행한다. 이 로컬 증거 자체는 배포 또는 운영 복구 완료를 의미하지 않는다.


## 최대 500행의 D1 요청 수 검증

[Cloudflare D1 공식 제한](https://developers.cloudflare.com/d1/platform/limits/)은 Workers Paid의 invocation당 D1 요청을 1,000회로 제한하고, `batch()` 전체를 요청 1회로 계산한다. 각 SQL의 100개 바인딩 제한은 batch 내부에서도 유지된다.

`public-sync-request-budget.test.ts`는 실제 로컬 D1 binding의 `all/first/run/raw` 호출과 `batch` 호출을 각각 계수했다. 외부 응답은 페이지마다 100행, 총 5페이지/500행으로 고정했으며, 행수나 페이지를 줄이지 않았다. 완료 상태·500행의 반영 건수·원본 500행 보존과 연결된 폐업 장소 500행의 숨김도 함께 확인했다.

| 합성 시나리오 | 수정 전 D1 요청 | 페이지 사전 조회 후 D1 요청 |
|---|---:|---:|
| 신규 OPEN 500행 | 1,015 (개별 1,010 + batch 5) | 25 (개별 20 + batch 5) |
| 기존 장소에 연결된 CLOSED 500행 | 2,015 (개별 2,010 + batch 5) | 45 (개별 40 + batch 5) |

수정 전 상한 초과 재현을 보존하고, 수정 후 같은 500행 시나리오 2건 및 기존 후보·페이지 fence·재인증·경합 회귀를 포함한 40건이 통과했다. 이 수치는 공공 수집 처리 함수의 D1 요청 수이며 라우트 인증·감사나 뒤의 별도 NAVER/자동 검수 작업까지 측정한 합계가 아니다. 테스트는 처리 함수에 900회 상한을 두어 Paid 한도의 나머지 100회를 다른 호출을 위한 여유로 남긴다.
