## 1. 기존 정책과의 관계

PDF의 ‘리뷰어 입력 → 관리자 검수 → 승인 공개’를 이번 구현의 공개 기준으로 채택한다. 기존 리뷰어 사진 전체 즉시 발행/갤러리 공개 방침과 충돌하는 범위는 이 정책이 대체한다. 기존 `2026-08-14-reviewer-revisit-withdrawal-photo-curation-design.md`의 대표사진 선정·권한/촬영 도구·재방문 아이디어를 통째 폐기하는 것이 아니라 **사전 공개 승인 없는 발행**을 대체한다. 본인 철회/명시 삭제·탈퇴의 기존 정확-key R2 삭제·실패 재시도 절차는 유지한다. 관리자의 일시 공개 회수/보완·반려와 소유자의 삭제 의사를 구분한다.

기존 R2 ADR의 5장/파일8MiB·총25MiB, EXIF/GPS 제거·Worker 경유·정확한 키 삭제·보상 처리 기준은 유지한다. 파일 안전성·EXIF 제거는 이용권리나 콘텐츠 승인의 증명이 아니다. 새 저장소·공급자·유료 API·cron/binding·프레임워크는 추가하지 않는다.

기존 적용 migration은 변경하지 않고 새 순번으로 상태·출처·권리·감사·revision/epoch를 추가한다. 이 정책 PR의 병합은 구현 기준 채택이며, 원격 migration·운영 자료 일괄 변경·사진 업로드 활성화·배포 실행은 포함하지 않는다.

## 2. 리뷰 상태와 소유권

| 상태 | 의미·공개 적격성 | 허용 처리 |
| --- | --- | --- |
| LEGACY_UNREVIEWED | 기존 원문 보존, 승인/권리 근거 불명. 비공개·집계 제외 | 소유자의 실제 정보 보완·재제출, 관리자 검수. 자동 승인/리뷰↔표 추정 매칭 금지 |
| PENDING | 제출/수정 후 검수 대기. 비공개·집계 제외 | 관리자 승인/보완/반려, 본인 수정/철회 |
| APPROVED | 현재 version에 대한 관리자 승인. 다른 공개 조건까지 충족해야 공개 | 본인 수정 시 재심, 관리자 사유 있는 회수, 본인 철회 |
| CHANGES_REQUESTED | 보완 사유를 전달한 상태. 비공개 | 본인 보완 후 PENDING 또는 철회 |
| REJECTED | 반려 사유 보존. 비공개 | 소유자 수정·재제출(새 검수) 또는 철회 |
| WITHDRAWN | 공개 회수/본인 철회. 원문·감사 보존, 비공개 | 사유 확인 후 본인 명시 재제출, 이전 승인으로 fallback 금지 |

제출은 공개 효과를 만들지 않는다. 리뷰·사진 저장이 끝나도 투표/Golden·공개 갤러리·추천·생존보호에 반영하지 않는다. 본인 수정은 새로운 version으로 재심하고 이전 승인본을 자동 노출하지 않는다. 이전 값은 audit/revision으로 보존한다. 신규 체계에서 같은 작성자/장소의 현재 리뷰는 하나로 제한하되, 기존 복수 방문 행을 자동 병합하거나 삭제하지 않는다.

상태 변경은 기존 동일 origin mutation/CSRF 경계를 유지하고 서버의 인증·역할·소유권, expected version, 입력 형식·길이, 전이 가능성을 검사한다. 관리자 승인·보완·반려·회수에는 사유와 검수 확인이 필요하다. 작성자는 자신의 자료만 수정·철회하며 공개 승인을 스스로 할 수 없다. 학생의 배정 자료 열람 권한은 발행 권한이 아니다.

승인과 회수는 상태·현재 신호 projection·감사·집계 무효화를 원자적으로 결속한다. 오래된 version·중복 승인·동시 수정은 충돌로 거절하고 일부만 공개하지 않는다. 감사에는 대상/version·처리자·시각·사유·before/after·규칙 버전을 남기며 내부 기록은 공개 응답에서 제외한다.

## 3. 방문·사진 권리와 검수

리뷰어는 실제 방문일·방문 근거/설명과 이해관계 여부를 사실대로 입력한다. 사진마다 촬영일·설명·이용권리 근거·불필요한 인물/차량번호/위치정보 노출 확인을 기록한다. 같은 날 사진이라도 각 사진에 연결한다. 날짜를 추정하거나 기존 업로드 시각으로 촬영일을 채우지 않는다.

- 권리 근거: 직접 촬영 또는 적법한 제공/이용허락. 이용허락은 확인 가능한 근거 설명을 내부에 남기되 불필요한 개인 연락처·서류 원문을 수집/노출하지 않는다.
- 사진·장소 일치, 중복/흐림, 사실/의견 구분, 불필요한 인물·차량번호, 출처와 확인일을 검사한다. 근거 없는 최고/보장 표현과 외부 원문·사진·평점·외부 식별자 축적은 허용하지 않는다.
- 광고·협찬·이해관계가 있거나 판단 불가한 자료는 일반 승인으로 공개하지 않고 보완/반려 상태로 유지한다. 별도 공개·표시 정책이 확정되기 전 자동 점수 반영하지 않는다.
- 관리자 승인 시 방문/사실·권리·개인정보·장소 적합성을 확인한 현재 version을 기록한다. 사용자 체크박스만으로 권리 검증이 완료됐다고 보지 않는다.
- 기존 자료의 권리 필드는 미확인으로 남기며 실제 보완·검수 전 공개하지 않는다. 레거시 전환·관리자 회수/보완/반려는 원문·파일을 보존하고 단순 비공개를 물리 삭제로 구현하지 않는다. 소유자의 철회/명시 삭제·탈퇴는 기존 정확-key 물리 삭제·실패 재시도를 유지하며, 삭제 대상 파일·메타데이터·photoCount와 공개 참조를 정합하게 갱신한다. 재제출은 필요한 사진/권리 근거를 다시 제공해야 하며 삭제된 파일을 자동 복원하지 않는다.

모든 public 리뷰/사진은 **APPROVED 현재 version + 권리 검수 충족 + ACTIVE 리뷰어 profile/REVIEWER 역할 + 현재 공개·미폐업 장소**를 요구한다. DORMANT/SUSPENDED·탈퇴·철회·재심·반려·레거시·오래된 version은 비적격이다.

직접 사진 GET/HEAD는 R2 접근 전에 같은 기준을 검사한다. 작성자 본인·관리자의 인증된 내부 미리보기는 공개와 분리하며, 학생에게는 배정 소유권 확인 없는 미리보기를 제공하지 않는다. 성공·404·실패 응답은 no-store이며 개인화 미리보기는 Cookie에 따라 격리한다. 이미 내려받은 이미지·기존 브라우저/edge cache까지 새 서버 gate로 즉시 회수할 수 있다는 보장은 하지 않는다. 실제 rollout에서 구 cache TTL/철회 절차를 따로 점검한다.

## 4. 일반 반응과 리뷰어 평가의 출처

`vote_events`가 immutable 출처 원본이다. `current_votes.eventId`는 현재 효력 하나를 가리킨다. 같은 사용자/장소에서 일반 반응과 리뷰어 평가를 동시에 두 표로 세지 않는다.

| source | 생성·효력 |
| --- | --- |
| GENERAL | 로그인 사용자의 명시적 직접 반응. 사용자 현재 역할과 무관하게 일반 반응으로 분류 |
| REVIEWER | 관리자가 승인한 reviewId/version과 연결된 평가. 승인된 현재 자료 및 리뷰어·장소 공개 적격 조건을 함께 요구 |
| LEGACY_REVIEWER | 기존 리뷰어 역할 또는 프로필/방문 이력이 있는 작성자의 출처 불명 표. 원본 보존·공개 집계 제외 |

migration의 레거시 표 분류는 reviewer profile/방문 이력도 사용해 강등·탈퇴 후 역할만 USER로 바뀐 표를 일반 반응으로 재분류하지 않는다. 기존 review와 timestamp/작성자/장소만 같다고 새 승인 provenance를 만들지 않는다. 원래 일반 반응의 이력은 보존한다.

제출/수정은 base event를 기록한다. 관리자의 늦은 승인이 그 뒤 작성자가 누른 GENERAL 반응을 덮어쓰지 않도록 승인 projection CAS에서 대조한다. base가 달라졌다면 콘텐츠 승인은 보존할 수 있지만 현재 효력은 최신 직접 반응을 유지한다. 소유자가 나중에 다시 수정·제출하면 새 의도 기준으로 검수한다. HOLD/취소·철회도 다른 최신 반응을 임의 삭제하지 않는다.

독립 standalone Golden/Flavor 기록도 승인 review/version 결속이 없으면 공개 비적격이다. 새 Golden은 방문 검수 승인 때만 공개 grant를 만든다. 기존 월 quota·원문·회계는 보존하며 임의 승인 매칭하지 않는다. Advanced Flavor 공개·취향그래프 유입은 명시 승인 결속이 생길 때까지 차단하고, 이를 이번 핵심 요구에 끼워 넣어 자동 활성화하지 않는다.

[PR #382](https://github.com/taejunyun1/Tasted_it/pull/382)의 구현 해석: 같은 review/작성자/장소의 아직 유효하고 회수되지 않은 grant를 현재 review가 명시 연결하고 새 내용의 Golden 의도를 다시 승인한 경우, 원래 grant의 version·생성/만료·사유를 유지한다. 추가 grant·quota 소비·기간 연장은 없다. PENDING/회수/만료는 공개 제외하며 만료·회수 후 새 신청은 기존 UTC 월 한도/90일 제한을 적용한다.

## 5. 집계·추천·회수의 일관성

공통 source/공개 적격 판정을 raw counts, 상세 v1 fallback, v2 snapshot·재계산·리뷰어 신뢰/유사도, HotTake/HiddenGem, Golden relay/history, Flavor·내 취향그래프, 장소 생존보호까지 적용한다. 사진만 가리고 미승인 점수/추천이 남는 결과는 허용하지 않는다.

per-place vote revision과 global moderation epoch를 현재 입력에 결속한다. 검수 승인/회수·역할/profile 상태·장소 공개/폐업/삭제·원시표 유효성처럼 source 적격성이 달라지는 변경은 신뢰 보정의 영향도 무효화하고, 기존/오래된 epoch snapshot·신뢰/유사도는 재사용하지 않는다. 재계산 중 상태가 바뀐 결과를 새 snapshot으로 공개하지 않는다. 안전한 중립 보정으로 fallback하고 기존 maintenance에서 재계산하며 새 cron을 추가하지 않는다. 저장 불명확성은 PASS나 공개로 바꾸지 않는다.

미공개 상태가 되면 이후 서버 조회에서 즉시 제외한다. 이미 화면에 받은 과거 응답까지 자동 회수됐다고 주장하지 않는다. 홈/목록/상세의 클라이언트 재검증과 오류 상태도 수용시험에 포함한다. global epoch의 보수적 무효화는 정확성 우선 선택이며 실제 처리량·응답 성능은 이후 측정하고 계약상 성능 보장으로 쓰지 않는다.

#382는 REVIEWER 현재표의 생성·교체·철회를 전역 epoch에 결속한다. GENERAL-only의 합의값 변화에 따른 calibration은 기존 maintenance 주기를 유지하며 실시간 재학습을 주장하지 않는다. 일반 반응/취소 후 사용자 추론은 별도 기존 taste versionToken에 결속해 갱신 실패 시 오래된 INFERRED 신호를 재사용하지 않는다. 산식 변경이나 새 cron은 없다.

## 7. 검증·운영 경계·복원

기술 수용은 상위 T04/T05/T06/T08을 포함한다. 최소 행렬은 PENDING/보완/반려/철회/레거시/old version/hidden place/정지·탈퇴 × 직접사진 GET/HEAD·갤러리/프로필·raw counts·snapshot/추천·trust/Golden/Flavor/liveness다. owner/admin/일반/다른 리뷰어/학생의 권한을 분리한다.

기존 일반표·원문/사진·감사 보존, 제출 public 효과0, 명시 승인만 REVIEWER 신호, 늦은 승인/중복·동시 수정 CAS, 재계산 commit 경합·epoch 불일치, R2 실패/DB 응답 유실·보상, 계정 탈퇴/강등 부정시험을 수행한다. UI에는 데스크톱/모바일의 검수 요청·상태·사유·보완·관리자 확인 화면을 남긴다. 코드/로컬/CI/운영 상태는 분리한다.

원격 migration·실제 자료 재검수·사진 활성화·배포는 이 작업에서 실행하지 않는다. 실제 rollout PR은 대상·백업·집계 읽기·새 migration만 적용·기존 rows 보존·권리 보완·단계 승인·구 cache·구버전 호환·성능 영향·live RSI/공개/권한 검증·rollback을 구체화한다. 새 migration을 임의 되돌리거나 적용 SQL을 수정하지 않는다. 로컬 복원은 코드 revert/새 forward-fix이며 원래 원장/자료·감사 이력은 보존한다.
