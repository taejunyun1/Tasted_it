# Re:Taste 다음 의사결정 목록

**작성일:** 2026-08-05

**상태:** 초안 — 구현 승인 문서가 아님

**적용 범위:** 1주차 기술 베타 이후, 2~4주차 웹 MVP, B2B 결제, iOS·Android 출시

## 1. 이 문서의 목적

현재 배포본은 기능과 배포 구조를 검증하는 기술 프리뷰다. 다음 구현을 시작하기 전에 제품·운영·법무·데이터 기준을 먼저 확정해야 한다. 이 문서는 결정을 다음 세 단계로 나눈다.

- **지금 결정:** 다음 개발 작업의 데이터 구조나 보안을 바꾸는 항목
- **공개 베타 전 결정:** 외부 사용자를 받기 전에 반드시 확정할 항목
- **운영 데이터 후 결정:** 실제 이용 결과가 없으면 추측이 되는 항목

결정되지 않은 항목은 임의로 구현하지 않는다. 표의 `권장 기본안`은 1인 개발과 4주 MVP 범위를 기준으로 한 출발점이며, 승인되면 별도 ADR과 구현 계획에 반영한다.

## 2. 권장 결정 순서

1. 서비스 공개 범위와 운영 주체
2. 실제 로그인과 관리자 인증
3. 장소·지도 데이터의 기준 원본과 검수 상태
4. 이미지 수급 및 이용 권리
5. 평가·리뷰어 운영 규칙
6. 분석·문의·삭제 등 운영 정책
7. B2B 상품과 결제 정책
8. 모바일 앱 기술과 스토어 정책

앞 단계가 확정되지 않으면 뒤 단계의 비용과 개인정보 문구가 다시 바뀐다.

## 4. 공개 베타 전에 확정할 항목

### 4.1 운영·법무

| 결정 | 현재 상태 | 완료 기준 |
|---|---|---|
| 운영자 또는 사업자 법적 명칭 | 미정 | 처리방침·약관·문의 화면에 같은 명칭 사용 |
| 사업장 주소 | 미정 | 공개 가능한 주소와 전자상거래 표시 범위 확인 |
| 개인정보 문의 이메일 | 미정 | 실제 수신·회신 가능한 전용 주소 개설 |
| 문의 전화번호 | 미정 | 공개 번호 또는 전화 미운영 정책 확정 |
| 만 14세 미만 정책 | 미정 | 권장안은 가입 차단; 가입 화면·약관과 일치 |
| 개인정보 국외 이전·위탁 | 일부 미정 | Cloudflare, 이메일, 분석, 결제 공급자별 실제 흐름 기록 |
| 계정 삭제·보존기간 | 미정 | 삭제 즉시 항목과 법정 보존 항목 분리 |
| 장소·이미지 정정 요청 | 미정 | 업주·권리자 요청 접수, 증빙, 처리기한 정의 |

개인정보 처리방침은 `kimlawtech/korean-privacy-terms`를 기준 초안으로 사용하되 실제 데이터 흐름을 먼저 확정한다. 법적 주체와 연락처가 비어 있는 상태에서는 정식 공개 또는 결제를 시작하지 않는다.

### 4.2 도메인과 공개 환경

- `workers.dev` 주소는 개발·초대 베타용으로 유지한다.
- 정식 공개 전 브랜드 도메인 후보, 등록 명의, 갱신 책임자를 정한다.
- 공개 웹과 관리자 경로를 분리한다. 권장 구조는 `www` 또는 루트는 공개, `/admin/*` 또는 별도 관리자 호스트는 Access 보호다.
- 운영·스테이징 D1, 비밀값, 데이터가 섞이지 않도록 환경별 명명 규칙과 백업 절차를 정한다.

Cloudflare Workers의 Custom Domain은 DNS 레코드와 인증서를 자동 구성할 수 있다. `workers.dev`와 Preview URL에는 대시보드에서 Cloudflare Access를 켜 특정 사용자만 허용할 수 있다.

## 5. 지도와 위치 데이터 결정안

### 5.1 권장 역할 분리

| 계층 | 권장 선택 | 역할 |
|---|---|---|
| 화면 렌더링 | MapLibre GL JS | 지도 표시, 마커, 클러스터, 웹·앱 스타일 일관성 |
| 배경 지도 | 운영용 타일 공급자 미정 | 도로·지명·배경 스타일 제공 |
| 장소 검색 | Kakao Local REST API | 한국 음식점 검색, 도로명·지번 주소, 좌표 후보 제공 |
| 내부 기준 원본 | Re:Taste D1 | 검수된 좌표·주소·상태·출처와 변경 이력 보존 |

특정 공급자의 장소 ID는 연결 키일 뿐 Re:Taste 장소의 기본키가 아니다. 공급자를 바꾸거나 ID가 사라져도 내부 장소가 유지되어야 한다.

### 5.2 장소 데이터 권장 필드

다음 필드는 다음 스키마 개정 전에 확정한다.

| 그룹 | 필드 | 규칙 |
|---|---|---|
| 식별 | `placeId` | Re:Taste 내부 불변 ID |
| 표시 | `name`, `shortName` | 원문과 표시명 분리 가능 |
| 좌표 | `latitude`, `longitude` | WGS84, 숫자형, 내부 기준 위치 |
| 주소 | `roadAddress`, `parcelAddress` | 도로명과 지번을 별도 보존 |
| 행정구역 | `region1`, `region2`, `neighborhood` | 광역·시군구·동 단위 검색 |
| 외부 연결 | `source`, `sourcePlaceId`, `sourceUrl` | Kakao·OSM 등 출처별 별도 레코드 권장 |
| 정확도 | `locationPrecision` | `ROOFTOP`, `ENTRANCE`, `PARCEL`, `APPROXIMATE` |
| 검수 | `verificationStatus`, `verifiedAt`, `verifiedBy` | 공개 조건과 책임 추적 |
| 신선도 | `lastCheckedAt`, `closedAt` | 휴·폐업 및 이전 재검수 |

장소와 외부 공급자 연결은 1:1로 고정하지 말고 별도 `place_sources` 구조로 두는 것이 안전하다. 한 장소가 Kakao ID와 OSM ID를 동시에 가질 수 있고 공급자별 주소·좌표 차이도 기록할 수 있기 때문이다.

### 5.3 등록·검수 흐름

`검색 후보 → 중복 확인 → 주소·좌표 확인 → 핀 보정 → 영업 상태 확인 → 이미지 권리 확인 → 검수 완료 → 공개`

- 신규 후보는 기본적으로 `DRAFT`다.
- 이름만 같다고 같은 장소로 합치지 않는다. 주소·전화·좌표·외부 ID를 함께 비교한다.
- 좌표 자동 입력 후 운영자가 실제 출입구 또는 건물 위치를 확인한다.
- 이전·폐업 제보를 받으면 즉시 삭제하기보다 `검토 중` 상태와 변경 이력을 남긴다.
- 공개 장소도 마지막 확인일을 보이고, 초기에는 90일 단위 재검수를 권장한다.

### 5.4 타일 공급자 선정 기준

현재 기술 프리뷰의 `tile.openstreetmap.org`는 서비스 수준 보장이 없는 공동체 운영 서버다. 공개 서비스의 고정 인프라로 가정하지 않는다. 운영 공급자는 아래 항목으로 비교한다.

- 월간 지도 로드·타일 요청 무료량과 초과 단가
- 한국어 지명 품질과 광주·전남 상세도
- MapLibre용 벡터 스타일 제공 여부
- 캐시, 오프라인, 스크린샷, 앱 사용 조건
- 로고·저작자 표시 방식
- 장애 SLA와 공급자 변경 가능성
- 개인정보 및 요청 로그의 처리 지역

OpenStreetMap 표준 타일을 임시 사용한다면 눈에 보이는 저작자 표시, 정상 Referer, 캐시 정책을 지키고 대량 다운로드·오프라인 저장을 하지 않는다.

### 5.5 Kakao API 도입 전에 정할 것

2026-07-21부터 카카오맵 API 사용 절차와 무료 쿼터 방식이 변경되었다. 개발자 계정의 첫 활성화 앱만 무료 쿼터 대상이 될 수 있으므로 다음을 먼저 정한다.

- 어떤 Kakao Developers 앱을 Re:Taste 운영 앱으로 사용할지
- 개발·운영 키를 어떻게 분리할지
- 예상 일간 검색량과 초과 비용 상한
- 검색 결과를 얼마나 오래 저장할 수 있는지에 대한 최신 이용조건 검토
- Kakao 결과를 자동 공개하지 않고 내부 검수 후보로만 사용할지 여부 — **권장: 후보로만 사용**

## 6. 인증과 권한 결정안

### 권장 기본 구조

- 일반 사용자: 이메일 매직링크 로그인
- 관리자: 검증된 일반 로그인 + 서버의 ADMIN 역할 검사
- 관리자 화면의 외부 진입: Cloudflare Access 추가 보호
- 모든 역할 판정: 브라우저 값이 아니라 서버 세션과 D1 기준
- 관리자 변경: actor, reason, before, after, timestamp 감사 로그

현재의 이메일 직접 입력 방식은 기술 데모용이며 공개 사용자의 신원 확인 수단으로 사용하지 않는다. Cloudflare Access만으로 일반 사용자 계정을 대신하지도 않는다. Access는 운영 화면의 외부 방어선이고 앱의 사용자·Reviewer·Admin 데이터 모델은 별도로 유지한다.

### 추가 결정 질문

- 매직링크 발송 공급자와 발신 도메인은 무엇인가?
- 로그인 링크 만료 시간과 재사용 방지 기준은 무엇인가?
- 계정 하나에 여러 이메일·소셜 계정 연결을 허용할 것인가?
- 정지, 탈퇴, 재가입 때 투표와 저장 데이터를 어떻게 처리할 것인가?
- Reviewer 승급과 Admin 지정은 누가 어떤 근거로 승인하는가?

## 7. 평가·콘텐츠·운영 규칙

### 7.1 리뷰어

2주차 전에 아래 정책을 확정한다.

- 모집 방식: 초대제 권장
- 신원 공개 수준: 서비스에는 닉네임, 운영자는 실명·연락 수단 확인 권장
- 이해관계 공개: 본인·가족·고용·금전 관계가 있는 장소 평가 제한
- 평가 수정 가능 기간과 철회 규칙
- 활동 중지·자격 박탈 기준
- 보상 여부와 세무 처리

리뷰어 가중치는 리뷰어 모집과 블라인드 비교 실험이 끝난 뒤 결정한다. 처음부터 높은 가중치를 주면 소수 평가자의 편향이 전체 점수에 크게 반영된다.

### 7.2 점수와 배지

- 현재 Beta(2,2) 평활화와 최소 8표 공개 기준은 첫 베타까지 유지한다.
- 리뷰어 평가, 일반 사용자 평가, 캠페인 참여 여부는 원시 데이터에서 분리한다.
- 유료 캠페인은 점수나 Golden Pick 구매 수단이 될 수 없다.
- Golden Pick의 후보 조건, 평가 기간, 최소 표본, 유효기간, 회수 조건을 3주차 전에 문서화한다.
- 점수 공식이나 기준이 바뀌면 `ratingVersion`을 올리고 이전 결과를 재현할 수 있어야 한다.

### 7.3 콘텐츠와 이미지

- 업주 제공 이미지에는 제공자, 동의 일시, 허용 범위, 원본을 기록한다.
- 직접 촬영 이미지는 촬영자와 촬영일을 기록한다.
- 외부 플랫폼 이미지를 검색 결과에서 그대로 복제하지 않는다.
- 삭제 요청이 들어오면 공개 중단과 원본 삭제를 분리해 처리 이력을 남긴다.
- 이미지 없는 장소는 중립적인 플레이스홀더를 사용하며 품질 점수에 불이익을 주지 않는다.

## 8. 운영 데이터가 쌓인 뒤 결정할 항목

아래 항목은 먼저 최소 2~4주의 실제 지표를 모은 뒤 결정한다.

| 항목 | 필요한 근거 | 결정 시점 |
|---|---|---|
| 취향 DNA 차원·가중치 | 투표·저장·검색 행동 분포 | 3~4주차 |
| 개인화 추천 방식 | 반복 사용자 수와 평가 밀도 | 4주차 이후 |
| 평가 공개 최소 표본 조정 | 장소별 표수와 신뢰구간 | 베타 2주 후 |
| 리뷰어 가중치 | 일반 평가와의 일치도·재현성 | 블라인드 평가 후 |
| 300곳 확대 속도 | 1곳당 검수 시간과 오류율 | CMS 운영 1주 후 |
| 알림·푸시 | 저장 후 재방문과 알림 수요 | 웹 MVP 이후 |
| B2B 상품 가격 | 인터뷰, 수행 원가, 결제 의향 | 최소 5개 업주 인터뷰 후 |
| 앱 기술 | 웹 API 안정성, 푸시·지도 요구 | 웹 MVP 안정화 후 |
| 소비자 구독 | 반복 사용과 지불 의향 | 앱 출시 이후 별도 검증 |

## 9. B2B 결제 전에 별도로 결정할 항목

결제 기능은 사업자 정보만 정한다고 바로 구현하지 않는다. 다음 결정을 하나의 ADR 묶음으로 확정한다.

- 판매 주체와 사업자등록·통신판매 관련 준비
- 상품 정의, 산출물, 수행 기간, 수정 횟수
- 가격의 부가세 포함 여부와 견적 유효기간
- 결제사, 결제 링크, 카드·계좌이체 범위
- 현금영수증·세금계산서 발행 절차
- 작업 시작 전·후 취소와 전액·부분 환불 기준
- 결제 웹훅 검증, 중복 방지, 실패 재처리
- 캠페인 콘텐츠의 `광고/협찬` 표시
- 결제 여부가 평가·추천·배지에 영향을 주지 않는 기술적 격리

첫 버전은 업주 계정과 셀프서비스 결제를 만들지 않고 `문의 → 관리자 견적 → 만료형 결제 링크 → 수행 → 리포트` 흐름을 권장한다.

## 10. 앱 출시 전에 결정할 항목

- React Native 또는 Flutter 중 하나와 선정 근거
- 웹과 앱의 공통 API 버전 정책
- 소셜 로그인 추가 여부와 계정 연결
- 위치 권한을 요청할 정확한 기능과 거부 시 동작
- 푸시 알림 유형, 기본값, 해지 경로
- 앱 내 계정 삭제 완료 흐름
- Apple·Google 개인정보 표시와 처리방침 일치
- 앱에서 판매할 상품의 인앱결제 적용 여부
- 딥링크, 지도 앱 연결, 저장 장소 동기화
- 크래시·분석 도구의 개인정보와 국외 이전

B2B 맞춤 서비스 결제는 웹 흐름을 유지하고 첫 소비자 앱에는 넣지 않는 것을 권장한다.

## 11. 한 번에 승인 가능한 권장 기본안

아래 묶음은 다음 구현 계획의 기본값으로 사용할 수 있다.

1. 법적 정보와 실데이터 검수가 끝날 때까지 초대형 비공개 베타로 운영한다.
2. 만 14세 미만 가입은 MVP에서 차단한다.
3. 일반 사용자는 이메일 매직링크, 관리자는 앱 권한 검사와 Cloudflare Access를 함께 사용한다.
4. MapLibre를 유지하고 운영 타일 공급자는 비용·약관 비교 후 선정한다.
5. Kakao Local은 검색 후보와 주소 보정에 사용하고, D1의 WGS84 좌표를 내부 기준 원본으로 삼는다.
6. 장소는 운영 상태·주소·좌표를 사람이 확인한 뒤에만 공개한다.
7. 카테고리는 대표 1개와 보조 태그 복수 구조로 확장한다.
8. 이미지는 직접 촬영 또는 이용 허락이 확인된 파일만 R2에 저장한다.
9. 첫 베타는 Beta(2,2), 최소 8표를 유지하고 리뷰어 가중치는 실험 후 정한다.
10. 초기 분석은 필수 이벤트와 Workers 로그만 사용하고 외부 분석 도구는 나중에 검토한다.
11. B2B 결제는 법적 주체·상품·환불·세금 문서가 확정된 뒤 시작한다.
12. 첫 앱은 소비자 탐색·투표·저장에 집중하고 B2B 결제는 웹에 둔다.

## 12. 운영자가 답해야 할 결정 질문

다음 회의 또는 문서 검토에서는 아래 순서로 답하면 된다.

1. 공개 베타를 초대제로 할지, 링크를 아는 누구나 접근하게 할지?
2. 운영 주체를 개인, 개인사업자, 법인 중 무엇으로 시작할지?
3. 만 14세 미만 가입 차단 권장안을 승인할지?
4. 첫 로그인을 이메일 매직링크로 할지, 소셜 로그인도 함께 넣을지?
5. 관리자 접근에 Cloudflare Access를 추가할지?
6. 사용할 브랜드 도메인 후보와 월 인프라 예산은 얼마인지?
7. 장소 1건의 최종 검수를 누가 하고 어떤 증빙을 남길지?
8. 초기 이미지 20~50곳을 직접 촬영, 업주 제공, 이미지 없이 출시 중 어느 방식으로 채울지?
9. 리뷰어를 몇 명, 어떤 기준으로 초대할지?
10. B2B 첫 상품 하나의 산출물과 목표 가격대는 무엇인지?
