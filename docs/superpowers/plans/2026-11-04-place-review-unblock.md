# 점포 검수 파이프라인 병목 해소 계획

상태: PROPOSED (2026-11-04)
소유: Jay · 범위: 진단 결과 기록 + 단계별 작업 분할. 각 코드·운영 변경은 별도 PR.

## 실측 근거 (프로덕션 D1, 2026-11-04)

- `place_review_work_items` 총 ~19,800건, 완료 상태 도달 0건
  - SOURCE_REVIEW 18,289 / NAVER_VERIFICATION 754 / CATEGORY_CONFIRMATION 720 / FINAL_APPROVAL 37
- SOURCE_REVIEW 정체 원인: 18,289건 중 **17,660건(97%)이 이미 `sourceReady` 충족**(정상영업·주소·좌표). 실질 미충족은 629건(좌표 367·라이선스 무 213·비영업 49)뿐
- 게이트 자체는 정상: `evaluateReviewAdvance`는 `sourceReady`만 보면 되고 `REVIEW_CONFIDENT_ADVANCE_ENABLED=true`도 배포돼 있다
- 진짜 병목: 진행은 관리자 화면의 페이지 배치(최대 100건/제출)에만 존재하고, 그걸 실행한 운영자가 없었다. 17.6k건은 수동 ~177회 제출이 필요해 사실상 수동 한계
- 수집 sync도 병목: `public_data_sync_runs` — 11-01 FAILED×11(`PUBLIC_DATA_HTTP_504`, ~24h 후 사망), 11-03 RUNNING 1건은 이틀째 미종료(좀비 가능). 150k건을 하루 ~500건 속도로는 수백 일 소요
- 학생 분류 태스크 56건 전원 OPEN·작업이력 0 — A·B 좌석은 활성·계정 연결됐으나 미착수, C·D 초대 만료

## 판정

"점포 입력 정지"는 오인이다. 실제로는 **후보 대량 투입 → 사람 주도 페이지 검수** 구조에서 검수 실행 주체가 부재했고, 수동 처리량으로는 적체를 소화할 수 없다. 공개된 점포는 8개뿐이다.

## 작업 분할

### P0-1 진단 (완료, 이 문서에 기록)
백로그의 단계별·사유별 분포와 게이트 요건 대조. 위 실측 근거가 결과물.

### P0-2 FINAL_APPROVAL 37건 운영자 공개 (운영, 코드 변경 없음)
관리자 장소 운영 화면에서 기존 절차대로 사람이 공개. 대량 자동 공개는 정책상 금지("공개는 사람").

### P0-3 서버 측 유한 배치 진행기 (코드, 별도 PR)
관리자가 한 번 실행하면 배치 단위로 게이트를 평가·진행하는 서버 경로.
- 단계·건별 한도(예: 실행당 최대 N건), dry-run 모드, 진행 사유·스킵 코드 감사 기록
- NAVER_VERIFICATION은 실제 외부 API 호출이라 호출 한도·쿼터 가드 필수
- "공개는 사람" 유지 — 배치기는 FINAL_APPROVAL까지만, 게이트 규칙 변경 없음
- 자동 제외(auto-exclude)는 기존 정책 그대로, 신규 규칙 추가 금지

### P0-4 수집 sync 재설계 (코드, 별도 PR, 더 큼)
증분/날짜 필터·청크 분할·재시도 가능한 커서·24h 타임아웃 회피. 11-03 RUNNING 좀비 run 회수 포함.

### P1 학생 인력 재동원 (운영)
C·D 재초대 또는 태스크 재분배, 학생 감시·메일 재개 여부 결정.

## 비범위
- 게이트 규칙(`evaluateReviewAdvance`) 자체의 기준 완화 — 통과율을 올리기 위한 조건 변경 금지
- 대량 자동 공개, 스키마 변경, 신규 외부 서비스
- 학생 시스템 코드 변경
