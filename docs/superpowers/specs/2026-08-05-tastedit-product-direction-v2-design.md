# Tasted : IT 제품 방향 및 제작 가이드 v2

작성일: 2026-08-05  
상태: 확정 설계  
적용 범위: 광주 공개 베타부터 전남 확장, 결제 모델, 앱 출시까지

## 1. 문서 사용 원칙

- 사용자 답변이 있는 항목은 해당 답변을 확정값으로 사용한다.
- 답변이 없는 항목은 질문에 제시된 예시를 초기 기본값으로 사용한다.
- 서로 충돌하는 답변은 더 구체적이고 나중에 작성된 답변을 우선한다.
- 초기 제품은 광주에 집중하며, 전남과 전국 확장은 기간이 아니라 성과 조건으로 결정한다.
- 장소 공개, 사진 공개, 유료 캠페인 결과 공개의 최종 권한은 관리자에게 둔다.

## 2. 브랜드와 사업 방향

### 2.1 브랜드

- 서비스명: `Tasted : IT`
- 초기 정체성: 광주 맛집·공간 안내 지도
- 확장 정체성: 로컬 큐레이션 미디어, 지역 커머스, 요식업 촬영·캠페인 플랫폼
- 서비스명과 캠페인명은 분리하되 `Taste`, `Tasted`, `Re:Taste` 계열의 연결성을 유지한다.

### 2.2 지역 확장

1. 광주에서 시작한다.
2. 검수·운영 시스템과 고정 사용자층을 확보하면 전남으로 확장한다.
3. 지속가능성, 팬층, 반복 매출이 검증되면 전국 확장을 검토한다.
4. 모바일 앱은 광주 운영 모델이 안정된 뒤 출시한다.

### 2.3 수익 구조

- 내부 촬영팀 중심의 사진·영상 촬영 상품
- 지역 프리랜서 연계 촬영과 운영진 최종 품질 검수
- Re:Taste 재평가 캠페인
- 촬영 + 캠페인 패키지
- 캠페인 페이지, 에디토리얼 콘텐츠, 지도 프로모션 핀 광고
- 음식점이 실제로 사용하는 지역 농산물 중심의 커머스
- 업주는 노출과 재평가 기회를 구매할 수 있지만 추천 결과와 배지는 구매할 수 없다.

## 3. 핵심 데이터 모델

### 3.1 Place 중심 구조

- 기본 단위는 Restaurant가 아니라 `Place`다.
- 음식뿐 아니라 공간, 데이트 적합성, 부모님 동반, 주차, 분위기 등을 함께 다룬다.
- 체인점은 지점별 독립 Place로 저장하고 별도로 평가한다.
- 한 Place는 대표 카테고리 1개를 가진다.
- 보조 분류는 공개 노출 카테고리가 아니라 검색·설명용 태그로만 사용한다.
- 폐업 장소는 운영 데이터에 이력을 보관할 수 있지만 회원 지도·목록·검색에서는 완전히 제외한다.

### 3.2 주소와 동네

- 관리자와 사용자는 `동네`를 직접 입력하지 않는다.
- 도로명주소를 우선하고 지번주소를 보조로 사용한다.
- 괄호 안 법정동이 있으면 이를 최우선으로 추출한다.
- 괄호가 없으면 주소 문자열에서 동·읍·면·리를 추출한다.
- 추출된 값은 검색과 필터 성능을 위해 `places.neighborhood`에 파생값으로 저장한다.
- 주소가 변경되면 동네 파생값도 다시 계산한다.
- 동네를 추출하지 못한 후보는 `주소 확인 필요` 상태로 두고 자동 승인하지 않는다.

### 3.3 중복과 영업 상태

- 중복 판단은 주소, 좌표, 전화번호, 외부 지도 ID를 함께 비교한다.
- 공공데이터상 폐업은 공개 후보에서 제외한다.
- 휴업·상태 불명은 자동 공개하지 않고 수동 검수로 보낸다.
- 매출 데이터는 보조 신호로만 사용하고 법적 영업 상태를 단독으로 확정하는 근거로 사용하지 않는다.

## 4. 사용자와 권한

### 4.1 일반 사용자

- 회원가입, 이메일 인증, 로그인, 비밀번호 재설정
- 장소 저장과 평가
- 장소 제안
- 개인 컬렉션 생성
- 리뷰어 팔로우

### 4.2 리뷰어

- 일반 사용자 기능 전체
- 공개 프로필, 프로필 사진, 직업, 취향 방향, 전문 카테고리
- 한줄평, 추천 메뉴, 점수와 세분화 평가
- 장소 사진 업로드 요청
- Golden Pick 월 3개
- 다른 리뷰어 결과는 본인이 평가하기 전까지 비공개

리뷰어 후보는 승인된 장소 제안 10곳 이상과 본인의 맛집 기준을 설명하는 짧은 의견서를 제출한다. 관리자가 최종 권한을 부여한다. 3개월 동안 평가 활동이 없으면 휴면으로 전환한다.

### 4.3 관리자

- 공공데이터 동기화와 후보 검수
- 장소·카테고리·중복·영업 상태 관리
- 사용자 제안 검수
- 리뷰어 승급·휴면·권한 관리
- 사진과 콘텐츠 최종 승인
- 캠페인·상품·결제·환불 운영

## 5. 장소 제안과 공개

- 일반 사용자는 상호, 위치, 메뉴 카테고리, 추천 이유, 영업시간을 입력한다.
- 장소 제안은 관리자 승인 전까지 공개하지 않는다.
- 초기 공개 데이터 300곳은 운영진과 초기 리뷰어가 직접 선별한다.
- 사용자 제안은 공공데이터와 외부 지도 정보로 중복·영업 상태를 보강한다.
- 승인된 제안 수는 리뷰어 승급 심사 자료로 사용한다.

## 6. 리스트 중심 하이브리드 검수

### 6.1 기본 원칙

- 검수 기본 화면은 지도가 아니라 리스트다.
- 지도는 회원 탐색에 사용하고 관리자 검수의 필수 도구로 사용하지 않는다.
- 규칙 기반 분류를 먼저 수행하고 애매한 후보만 AI 분류에 보낸다.
- AI가 분류해도 공개 결정은 신뢰도와 차단 규칙을 통과해야 한다.
- AI 결과가 없거나 확신도가 낮으면 관리자가 수동으로 대표 카테고리를 선택한다.

### 6.2 검수 상태

#### 자동 승인 가능

- 영업 상태가 OPEN이다.
- 주소와 유효 좌표가 있다.
- 주소에서 동네를 추출했다.
- 활성 대표 카테고리를 찾았다.
- 기존 공개 장소와 중복되지 않는다.
- 규칙과 AI 결과가 일치하거나 최종 신뢰도가 HIGH다.

#### 수동 확인 필요

- 신뢰도가 MEDIUM 또는 LOW다.
- 상호명과 공공데이터 업태가 충돌한다.
- AI와 규칙 분류가 다르다.
- 활성 카테고리를 찾지 못했다.
- 휴업 또는 상태 불명이다.
- 주소의 동네 추출 결과를 확인해야 한다.

관리자는 행의 대표 카테고리 드롭다운을 변경하고 승인하거나 반려한다.

#### 승인 불가

- 폐업 상태다.
- 음식점·카페·제과점·주점 대상이 아니다.
- 주소 또는 좌표가 없다.
- 기존 공개 장소와 중복이다.
- 필수 원천 식별자가 없다.

승인 불가 후보는 체크박스를 비활성화하고 차단 사유를 표시한다.

### 6.3 화면 구성

- 탭: 전체 / 자동 승인 / 수동 확인 / 승인 불가
- 검색: 상호명과 주소
- 필터: 지역, 공공데이터 분류, 원천 업태, 추천 카테고리, 신뢰도, 좌표 상태
- 정렬: 최근 갱신, 상호, 지역, 원천 업태, 추천 카테고리, 신뢰도
- 페이지 크기: 25 / 50 / 100
- 행 표시: 체크박스, 상호, 주소, 자동 동네, 원천 업태, 추천 대표 카테고리, 신뢰도, 차단 사유
- 행 확장: 원본 공공데이터, 규칙 분류 근거, AI 분류 근거, 중복 후보
- 일괄 작업: 자동 승인 후보 전체 선택, 선택 승인, 선택 반려
- 수동 작업: 대표 카테고리 변경 후 단건 또는 선택 일괄 승인
- 지도 패널과 동네 입력 필드는 제거한다.

### 6.4 분류 파이프라인

1. 대상 업종과 영업 상태를 검증한다.
2. 주소를 정규화하고 동네를 자동 추출한다.
3. 상호명 키워드와 공공데이터 업태 규칙으로 대표 카테고리를 제안한다.
4. 규칙 결과가 없거나 충돌하면 AI가 상호·업태·주소를 구조화된 카테고리 목록 중 하나로 분류한다.
5. 규칙 결과, AI 결과, 필수 데이터, 중복 여부로 최종 신뢰도와 검수 상태를 계산한다.
6. 관리자가 승인하면 Place와 대표 카테고리를 생성하고 회원 화면에 공개한다.

AI 응답은 자유 텍스트가 아니라 `categorySlug`, `confidence`, `reasons` 구조로 제한한다. API 실패 시 자동 승인하지 않고 수동 확인으로 전환한다.

## 7. 평가와 리뷰어 알고리즘

- 추천율은 최소 8표 이후 공개한다.
- 전체 추천율을 먼저 보여주고 상세에서 일반 사용자와 리뷰어 결과를 분리한다.
- 투표 직후 집계를 갱신한다.
- 초기에는 일반 사용자와 리뷰어의 투표 가중치를 동일하게 둔다.
- 리뷰어의 한줄평과 전문성을 별도로 강조한다.
- 향후 리뷰어 예측 정확도, 대중 평가와의 반복적 불일치, 유사 리뷰어 집단의 중복 투표를 신뢰 지표에 반영한다.
- 대중의 비추천이 압도적일수록 특정 리뷰어 추천 한 건의 영향력이 결과를 뒤집지 못하게 제한한다.
- 공격적이거나 테러성 평가를 신고·관리자 검수 대상으로 둔다.

## 8. 배지와 Flavor Print

- Golden Pick: 리뷰어당 월 3개, 부여일로부터 90일
- Hidden Gem: 외부 노출은 낮지만 리뷰어 추천과 사용자 반응이 높은 장소
- Hot Take: 특정 리뷰어 평가가 리뷰어 집단과 크게 다를 때 표시
- 만료 배지: 현재 화면에서 제거하고 이력에 보존
- Flavor Print: AI가 메뉴별 핵심 5개, 최대 7개 항목 초안을 만들고 리뷰어가 수정·승인
- 새 평가 항목은 리뷰어가 제안하고 관리자가 승인
- 리뷰어 3명 이상이 재평가하면 새 버전을 생성

## 9. 지도와 개인화

- 모바일 메인은 현재 위치 기반 지도 중심이다.
- 데스크톱은 지도와 목록을 오갈 수 있다.
- 표본이 충분한 메뉴는 돈가스·라멘·국밥처럼 독립 지도를 제공한다.
- 장소에는 주차, 길찾기, 영업 여부, 영업시간, 추천율을 우선 표시한다.
- 길찾기는 네이버지도, 카카오맵, 티맵을 단계적으로 지원한다.
- 주차 정보는 자체 입력, 주변 공영주차장, 검수된 무료 주차 팁으로 구성한다.
- 개인 컬렉션은 사용자가 폴더명을 지정한다.
- 컬렉션은 기본 비공개이고 선택적으로 공개한다.
- 공유 컬렉션 열람은 회원 가입을 요구한다.
- 취향 그래프는 평가 10회 이상부터 제공한다.

## 10. 이미지와 콘텐츠

- 장소 사진은 외관, 대표, 음식, 내부, 메뉴판의 최대 5장이다.
- 리뷰어가 업로드하고 관리자가 최종 승인한다.
- 이미지가 없으면 카테고리별 중립 플레이스홀더를 사용한다.
- 디자인은 사진 중심 에디토리얼 그리드와 흰색·검정·회색을 기본으로 한다.
- 다크모드는 초기 지원 범위에 포함한다.
- 리뷰어 또는 관리자가 맛집 칼럼을 작성한다.
- 월 1명의 리뷰어 프로필 인터뷰를 게시한다.
- 냉면, 삼계탕, 콩국수처럼 계절성이 높은 음식의 시즌 랭킹을 운영한다.

## 11. Re:Taste 캠페인

- 업주가 재평가, 할인, 플랫폼 노출을 요청할 수 있다.
- 참여는 플랫폼 쿠폰 또는 QR로 확인한다.
- 캠페인 평가는 전체 지표에 포함하되 캠페인 참여 리뷰임을 표시한다.
- 최소 10명 이상 참여해야 공식 결과를 공개한다.
- 결과 조작, 추천 결과 구매, 배지 구매는 허용하지 않는다.

- 음식 카테고리 세분화와 대표 카테고리 자동 추천
- 공공데이터 후보 수집·필터·정렬

- 개인정보 처리방침과 이용약관 기본 문서

### 부분 완료

## 13. 전체 제작 단계

## 14. 구현 완료 단위와 다음 순서

단계 1의 첫 구현 단위는 다음 범위로 완료한다.

1. 관리자 후보 검수를 단일 리스트 화면으로 통합한다.
2. 지도 패널과 동네 수동 입력을 제거한다.
3. 주소에서 동네를 자동 계산하고 승인 서버가 계산값만 사용하게 한다.
4. 자동 승인 / 수동 확인 / 승인 불가 탭과 사유를 제공한다.
5. 수동 후보의 대표 카테고리를 행에서 선택하고 선택 일괄 승인할 수 있게 한다.
6. 실제 외부 AI 호출은 별도 환경 설정과 비용 한도를 확정한 다음 연결한다. 이번 단위는 현재 규칙 분류를 유지하면서 AI 어댑터 경계를 만든다.

다음 순서는 Resend 운영 secret 등록, 인증 메일 발송 QA, 관리자 감사 로그 조회 화면, 실제 공개 데이터 반복 검증이다.

## 15. 검증 기준

- 폐업 후보가 어느 탭에서도 승인 가능 상태로 나타나지 않는다.
- 중복·좌표 누락 후보의 체크박스가 비활성화된다.
- HIGH 후보는 자동 승인 탭에 나타난다.
- MEDIUM·LOW·CONFLICT 후보는 수동 확인 탭에 나타난다.
- 수동 후보는 대표 카테고리를 변경한 후 승인할 수 있다.
- 동네 입력 필드가 없고 승인 결과의 동네가 주소에서 자동 생성된다.
- 승인된 Place만 회원 지도와 목록에 나타난다.
- 데스크톱과 모바일에서 리스트 검수가 가능하다.
