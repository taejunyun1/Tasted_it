# 장소 검수 5단계 파이프라인 설계

- 상태: 설계 확정, 구현 계획 작성 전 사용자 검토 필요
- 작성일: 2026-08-15
- 추적 이슈: [#135](https://github.com/taejunyun1/Tasted_it/issues/135)
- 대상 화면: `/admin/place-operations`

## 1. 목표

공공데이터 후보, 회원 제안에서 생성된 비공개 초안, 카테고리 감사로 회수된 장소를 하나의 검수 작업함에서 처리한다. 관리자는 반드시 다음 순서로 작업한다.

1. 공공데이터·원천 검수
2. NAVER 근거 확인
3. 카테고리 확정
4. 중복·프랜차이즈 검토
5. 선택 일괄 승인·공개

NAVER 검증 성공만으로 장소를 자동 공개하지 않는다. 앞의 네 단계를 통과한 항목만 5단계에 나타나며, 관리자가 선택한 항목만 `PUBLISHED`로 변경한다.

## 2. 현재 문제

- `/admin/candidates`와 `/admin/place-operations`가 동일한 검수 목적을 서로 다른 상태와 화면으로 처리한다.
- NAVER 확인은 근거 레코드만 갱신하고 `HIDDEN` 상태는 유지하지만, 운영자가 다음에 해야 할 행동이 화면에 연결되지 않는다.
- 장소 운영 화면은 최대 1,000건을 한 번에 읽고 첫 25건만 렌더링하여 648개 전체를 탐색할 수 없다.
- 공공데이터 후보의 카테고리 선택은 브라우저 상태에만 있고 최종 승인 전에는 저장되지 않는다.
- 현재 탭은 업무를 분리하지만 선행 단계 통과를 서버에서 강제하지 않는다.
- 동일 상호 묶음은 선택 편의를 제공하지만, 중복 해소 여부가 공개 조건으로 연결되지 않는다.

## 3. 검토한 접근

### A. 화면 탭만 5단계로 변경

기존 테이블을 그대로 두고 URL 탭과 필터만 추가한다. 변경량은 작지만 새 URL이나 직접 POST로 앞 단계를 건너뛸 수 있고, 카테고리 확정값을 영속적으로 보존하기 어렵다.

### B. 작업 상태를 서버에서 관리하는 단계 게이트 — 채택

검수 대상마다 현재 단계와 단계별 완료 근거를 기록한다. 모든 상태 변경은 하나의 도메인 서비스를 통과하고, 서버가 선행 조건을 확인한 뒤 다음 단계 이동을 허용한다. 기존 NAVER·카테고리·중복·감사 데이터를 근거의 기준 원본으로 유지하고, 새 작업 레코드는 흐름과 운영 상태만 소유한다.

### C. 실행 회차별 배치 세션

관리자가 648개를 하나의 회차로 묶고 회차 전체를 단계별로 이동한다. 진행률은 선명하지만 일부 항목의 보류·재검증 때문에 전체 회차가 멈추며, 여러 관리자의 병렬 작업이 어렵다.

## 4. 정보 구조

페이지 상단은 최초 공개 파이프라인과 공개 후 운영을 분리한다.

```text
장소 운영
├─ 검수 파이프라인
│  ├─ 1 원천 검수
│  ├─ 2 NAVER 검증
│  ├─ 3 카테고리 확정
│  ├─ 4 중복 검토
│  └─ 5 승인·공개
└─ 공개 후 운영
   ├─ 영업 재검증
   ├─ 정보 정정
   └─ 변경 이력
```

기존 `근거 감사`의 “현재 공개 장소 전체 회수” 작업은 공개 후 운영의 별도 위험 작업으로 유지한다. 회수된 장소는 자동으로 1단계 작업 항목이 되고, 다시 공개하려면 1~5단계를 모두 통과해야 한다.

회원 장소 제안은 위치 확인 후 `DRAFT` 장소와 1단계 작업 항목을 만든다. 정보 정정과 영업 재검증은 공개 후 운영에 남되, 공개 재승인이 필요한 결과는 새 파이프라인 작업 항목으로 되돌린다.

## 5. 단계별 계약

### 1단계: 원천 검수

대상은 공공데이터 `PENDING` 후보, 회원 제안으로 만든 `DRAFT`, 카테고리 감사 또는 영업 검수로 회수된 `HIDDEN` 장소다.

필수 확인:

- 광주·전남 주소와 유효 좌표
- 영업 가능 상태
- 음식점 업종 여부
- 공공데이터 원천 또는 관리자 근거
- 자동 제외 규칙의 결과

결과:

- `다음 단계`: 조건을 만족한 항목을 NAVER 검증 대기로 이동
- `보류`: 누락된 주소·좌표·원천 근거를 보완하기 전까지 유지
- `제외`: 비음식 시설, 유흥업종, 정책 제외, 잘못된 데이터로 종료

### 2단계: NAVER 근거 확인

기존 NAVER Local Search 어댑터와 일일 사용량 제한을 유지한다. 한 번의 API 실행은 최대 25개다.

검증 항목:

- 정규화 상호 일치
- 주소 일치
- 좌표 거리
- NAVER 상세 카테고리

결과:

- `MATCHED` 또는 후보 기준 `VERIFIED`: 3단계 이동 가능
- `AMBIGUOUS`, `LIKELY`: 수동 근거 승인 사유를 기록한 경우에만 3단계 이동 가능
- `NOT_FOUND`, `NO_MATCH`: 다른 공공 근거를 확인하고 수동 근거 승인하거나 보류·제외
- `ERROR`, `FAILED`: 재시도 가능하며 다음 단계 이동 금지

검증 결과는 기존 `naver_local_category_verifications`와 `place_liveness_states`에 저장한다. 작업 항목은 어떤 근거 레코드가 통과 조건을 충족했는지만 참조한다. 공공데이터 연결이 없는 `PLACE` 작업은 `place_liveness_states`의 상호·위치 검증을 사용하고, 3단계에서는 제안 카테고리와 관리자 선택을 비교한다. NAVER 성공은 `places.status`를 변경하지 않는다.

### 3단계: 카테고리 확정

한 카드에서 공공데이터 업태, 규칙 추천, NAVER 카테고리와 최종 선택을 비교한다. 최종 카테고리는 말단 카테고리만 허용한다.

- 추천 카테고리는 읽기 전용 태그로 표시한다.
- 관리자는 카테고리 선택 모달에서 개별 변경할 수 있다.
- 같은 카테고리를 적용할 항목을 선택하여 최대 25개까지 일괄 확정할 수 있다.
- 확정한 카테고리 ID, 관리자, 시각과 근거를 저장한다.
- NAVER 카테고리와 다른 선택은 사유 입력을 필수로 한다.

### 4단계: 중복·프랜차이즈 검토

상호, 주소, 좌표를 사용해 중복 후보를 만든다.

- 알려진 전국·지역·로컬 프랜차이즈는 동일 상호라는 이유로 병합하지 않는다.
- 비프랜차이즈이며 동일 주소 또는 100m 이내인 후보만 안전 병합 후보로 표시한다.
- 관리자는 `병합`, `서로 다른 장소`, `보류` 중 하나를 선택한다.
- 열린 중복 후보가 하나라도 있으면 5단계로 이동할 수 없다.
- 병합은 기존 URL 리다이렉트와 수정 이력을 그대로 남긴다.

### 5단계: 선택 일괄 승인·공개

다음 조건을 모두 충족한 항목만 노출한다.

- 1단계 원천 검수 완료
- 유효한 NAVER 일치 근거 또는 관리자·사유가 기록된 수동 근거 승인 존재
- 최종 말단 카테고리 확정
- 열린 중복 후보 없음
- 활성 자동 제외 없음

관리자는 최대 25개를 선택하고 공개 근거를 입력한 뒤 일괄 공개한다.

- 공공데이터 후보는 선택된 카테고리로 장소를 생성하고 `PUBLISHED`로 공개한다.
- 기존 `DRAFT` 또는 `HIDDEN` 장소는 확정 카테고리를 반영하고 `PUBLISHED`로 변경한다.
- 장소 상태 변경, 공공데이터 후보 승인, 작업 완료와 감사 이력은 하나의 D1 배치 또는 트랜잭션 경계에서 처리한다.
- 일부 항목이 조건을 잃은 경우 전체 요청을 실패시키지 않고 해당 항목만 건너뛰며 구체적인 이유를 반환한다.

자동 공개 버튼이나 전체 648개 무조건 공개 동작은 제공하지 않는다.

## 6. 작업 상태 모델

새 `place_review_work_items` 테이블은 파이프라인 상태만 소유한다. NAVER 응답 원문, 장소 원본과 카테고리 목록을 복제하지 않는다.

주요 필드:

- `id`
- `business_license_id` 또는 `place_id`: 둘 중 정확히 하나만 존재하도록 `CHECK` 제약 적용
- `source_kind`: `PUBLIC_DATA`, `PLACE_SUGGESTION`, `CATEGORY_RECALL`, `LIVENESS_RECHECK`
- `stage`: `SOURCE_REVIEW`, `NAVER_VERIFICATION`, `CATEGORY_CONFIRMATION`, `DUPLICATE_REVIEW`, `FINAL_APPROVAL`
- `status`: `ACTIVE`, `ON_HOLD`, `COMPLETED`, `EXCLUDED`
- `selected_category_id`
- `category_override_reason`
- `manual_evidence_reason`
- `stage_version`: 낙관적 동시성 제어용 정수
- 마지막 단계 변경 관리자와 시각, 최종 완료 시각
- `hold_code`, `hold_note`
- `created_at`, `updated_at`

불변식:

- `ACTIVE` 또는 `ON_HOLD` 작업은 `business_license_id` 또는 `place_id`당 하나만 존재하도록 부분 고유 인덱스를 둔다. 완료 후 영업 재검증으로 새 회차를 만들 수 있다.
- 다음 단계 이동은 현재 `stage`와 `stage_version`이 일치할 때만 성공한다.
- 단계 이동 서비스는 기존 근거 테이블을 다시 조회해 조건을 검증한다.
- 클라이언트가 보낸 점수, 단계 또는 공개 가능 여부를 신뢰하지 않는다.
- 단계별 변경 이력은 기존 `admin_audit_logs`에 기록한다. `COMPLETED`와 `EXCLUDED` 작업은 운영 감사 목적으로 보존하고 관리자 계정 삭제 시 담당자 참조는 `SET NULL`로 처리한다.

새 테이블은 D1의 기존 Drizzle ORM과 순차 migration만 사용한다. 새 데이터베이스, Queue, AI 또는 외부 공급자를 추가하지 않는다.

## 7. 목록·페이지네이션·선택 UX

각 단계 URL은 `?flow=review&step=2&page=1&pageSize=25&status=pending` 형식을 사용한다.

- 기본 페이지 크기 25, 선택 가능 크기 25/50/100
- DB에서 `count`, `limit`, `offset`을 실행하는 서버 페이지네이션
- 상단과 하단에 현재 페이지, 전체 페이지, 전체 건수와 이전·다음 버튼 표시
- 상호·주소 검색, 지역, 원천, 검증 결과, 카테고리 상태 필터 제공
- 페이지가 바뀌면 선택을 초기화한다.
- `현재 페이지 선택`은 API·일괄 처리 상한에 맞춰 최대 25개만 선택한다.
- 결과 토스트는 처리·건너뜀·실패 건수를 구분하고, 처리 중에는 전체 화면 입력을 막는 모달 오버레이를 사용한다.

648건이라는 숫자는 현재 로더 제한이나 페이지 배열 길이가 아니라 DB 전체 조건 집계에서 계산한다.

## 8. 화면 표현

상단 단계 바는 실제 순서를 나타내므로 `01`부터 `05`까지 번호를 사용한다. 각 단계에는 `대기`, `확인 필요`, `완료` 건수를 표시한다. 현재 단계만 짙은 녹색 면으로 강조하고, 완료 단계는 체크 표시, 잠긴 단계는 잠금 사유를 제공한다.

데스크톱은 단계 바 아래에 필터와 2열 작업 카드를 배치한다. 모바일은 단계 바를 가로 스크롤하고 카드를 1열로 표시한다. 모든 단계 링크는 URL 상태를 가지며 새로고침과 뒤로 가기를 지원한다.

버튼 문구는 상태 변화와 일치시킨다.

- `NAVER 근거 확인`
- `카테고리 확정`
- `서로 다른 장소로 확인`
- `선택 장소 승인·공개`

## 9. 오류와 안전장치

- NAVER 비활성화·quota·공급자 오류는 현재 단계에 머물며 기존 근거를 덮어쓰지 않는다.
- 오래된 NAVER 근거와 입력 fingerprint 불일치는 2단계 재검증 대상으로 되돌린다.
- 카테고리가 비활성화되면 5단계 공개를 차단하고 3단계로 되돌린다.
- 공개 직전에 주소·좌표·제외·중복 상태를 다시 조회한다.
- 동시에 두 관리자가 처리하면 `stage_version` 비교에 실패한 요청은 새로고침 안내와 함께 건너뛴다.
- 모든 제외, 보류, 단계 이동, 공개와 병합은 기존 감사 로그 또는 수정 이력에 남긴다.

## 10. 공개 후 운영

영업 재검증, 정보 정정, 변경 이력은 5단계 최초 공개 흐름과 분리한다.

- 영업 재검증에서 `HIDDEN`으로 변경된 장소가 재공개 대상이면 `LIVENESS_RECHECK` 작업으로 1단계에 재등록한다.
- 정보 정정이 상호·주소·좌표·카테고리를 변경하면 기존 NAVER 근거를 만료시키고 2단계로 되돌린다.
- 단순 전화번호나 설명 수정은 공개 상태를 유지한다.
- 이력 화면은 단계 변경과 최종 공개 이력을 함께 조회할 수 있어야 한다.

## 11. 테스트 전략

### 단위 테스트

- 단계별 통과 조건과 차단 코드
- NAVER 상태에서 다음 단계로 이동 가능한지 여부
- 카테고리 override 사유 요구
- 프랜차이즈 병합 제외와 동일 위치 판정
- 페이지 URL과 필터 파싱

### D1 통합 테스트

- migration과 활성 작업 유일성
- 각 단계의 비교 후 변경(compare-and-set)
- 후보 최종 승인 시 장소·카테고리·원천 링크·작업·감사 이력 원자성
- 기존 `HIDDEN` 장소의 선택 공개
- 동시 처리와 일부 건너뜀 결과

### 브라우저 테스트

- 1단계에서 5단계까지 순서대로 이동
- 앞 단계 미완료 항목의 뒤 단계 작업 차단
- 648건 fixture의 페이지 이동과 필터 유지
- NAVER 실행 중 전체 화면 입력 차단
- 선택 항목만 공개되고 미선택 항목은 `HIDDEN` 유지
- 데스크톱과 모바일 단계 바·목록·모달 검증

외부 NAVER API와 운영 D1은 테스트에서 호출하지 않고 기존 fake adapter와 로컬 D1 fixture를 사용한다.

## 12. 구현과 배포 분할

작업은 독립적으로 검증 가능한 세 개의 PR로 나눈다.

1. 파이프라인 기반: 새 migration, 작업 상태 서비스, 단계 불변식, 기존 후보·회수 장소 backfill
2. 관리자 UX: 통합 5단계 화면, 서버 페이지네이션, 필터, 선택과 모달 오버레이
3. 최종 공개와 공개 후 환류: 선택 일괄 공개, 영업·정정의 재등록, 감사 이력, 운영 검증

각 PR은 최신 `origin/main`에서 별도 기능 브랜치로 시작한다. migration PR에는 운영 D1 대상, backfill 예상 건수, 전·후 집계 쿼리, forward-fix 방식과 배포 순서를 명시한다. 원격 migration과 배포는 병합된 PR 범위에서만 수행한다.

## 13. 수용 기준

- 관리자는 648개 이상을 페이지로 모두 탐색할 수 있다.
- 모든 공개 대상은 서버 기준으로 1→2→3→4→5 순서를 통과한다.
- NAVER 검증 기능과 quota·cache·failure 처리가 유지된다.
- NAVER 검증만으로 `HIDDEN` 또는 `DRAFT`가 공개되지 않는다.
- 관리자가 5단계에서 선택한 최대 25개만 공개된다.
- 미선택 및 검증 실패 항목은 비공개 상태를 유지한다.
- 프랜차이즈 지점은 동일 상호 자동 병합 대상이 아니다.
- 모든 주요 상태 변경은 관리자와 근거를 포함한 이력으로 남는다.
- 기존 공개 후 영업 재검증·정보 정정 기능이 사라지지 않는다.
