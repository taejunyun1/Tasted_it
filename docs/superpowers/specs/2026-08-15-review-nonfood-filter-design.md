# 검수 파이프라인 선택 토글·비음식점 자동 제외 설계

## 목적

1단계 원천 검수에서 현재 페이지 선택을 한 버튼으로 조작하고, 기존 음식점 판정 정책을 사용해 확실한 비음식점을 검수 대상에서 자동 제외한다. 이 기능의 목적은 사람이 NAVER 검증에 쓰는 시간을 음식점 후보에 집중시키는 것이다.

## 사용자 흐름

1. 관리자가 1단계 검수 목록을 연다.
2. `현재 페이지 전체 선택` 버튼을 누르면 최대 25개가 선택되고, 버튼은 `선택 해제`로 바뀐다. 다시 누르면 선택이 해제된다.
3. 관리자가 `비음식점 자동 제외` 버튼을 누르면 현재 페이지의 활성 항목을 업태와 상호 규칙으로 검사한다.
4. 확실한 일치 항목은 `검수 제외`로 이동하고, 화면에는 처리 건수와 건너뜀 건수가 표시된다. 나머지 항목은 목록에 남는다.

## 판정 정책

- 기존 `food-venue-policy`의 `classifyFoodVenue`만 사용한다.
- 업태 일치: 유흥주점, 단란주점, 노래연습장 등 확실한 비음식·유흥 업태.
- 상호 일치: 편의점, PC방, 공방, 노래방 등 이미 안전하게 정의된 상호 규칙.
- 카페, 베이커리, 일반음식점처럼 해석 여지가 있는 항목은 자동 제외하지 않는다.
- 프랜차이즈 판정은 이 버튼의 범위가 아니다. 기존 체인점 정책을 그대로 유지한다.

## 데이터와 감사 이력

- 장소 또는 사업자 원천 레코드를 삭제하지 않는다.
- 현재 검수 작업 항목만 `EXCLUDED` 상태와 `AUTO_NON_FOOD` 사유로 기록한다.
- 판정된 규칙 코드와 분류는 감사 이벤트의 메모에 남긴다.
- 기존의 제외 복원/감사 체계가 적용되므로 운영자가 복구할 수 있다.

## 구현 경계

- UI: `PlaceReviewPipeline`의 선택 도구와 1단계 자동 제외 버튼.
- 서버: `admin-place-operations`의 전용 action intent 및 검수 작업 항목 일괄 제외 서비스.
- 정책: 기존 `food-venue-policy`를 재사용하며 새 키워드 목록이나 외부 API를 추가하지 않는다.
- DB migration, 새 의존성, Cloudflare binding, NAVER API 호출은 없다.

## 오류 처리

- 선택 토글은 요청을 만들지 않는다.
- 자동 제외 대상이 없으면 성공 응답으로 `자동 제외 대상 없음`을 표시한다.
- 이미 처리됐거나 현재 단계가 아닌 항목은 건너뜀으로 보고한다.
- same-origin 검증과 관리자 권한 검증은 기존 action과 동일하게 적용한다.

## 검증

- 정책 단위 시험: 업태·상호가 비음식점을 제외하고 음식점명은 허용하는지 확인한다.
- 서비스 통합 시험: 현재 단계의 확실한 비음식 항목만 제외되고 감사 이력이 남는지 확인한다.
- UI 시험: 하나의 버튼이 전체 선택과 선택 해제를 전환하는지, 1단계에서만 자동 제외 버튼이 보이는지 확인한다.
- 데스크톱·모바일 브라우저에서 선택 도구와 처리 결과를 확인한다.

## 롤백

이 변경을 되돌리면 자동 제외 버튼과 action만 사라진다. 이미 기록된 제외 항목은 기존 복원 기능으로 되돌릴 수 있다.
