# 공공데이터 장소 후보·어드민 검수 설계

- 작성일: 2026-08-05
- 상태: 검토 요청
- 대상: Re:Taste 공개 베타

## 1. 결정 요약

공공데이터의 음식점·주점 인허가 기록과 사용자에게 공개되는 장소를 분리한다. 공공데이터에서 확인된 업소는 먼저 비공개 후보로 적재하며, 어드민이 검수하고 승인한 후보만 공개 장소가 된다.

영업 중인 업소만 후보 목록과 후보 지도에 표시한다. 휴업·폐업·상태 불명 업소는 후보 지도에 표시하지 않는다. 이미 공개된 장소의 연결된 인허가 기록이 휴업 또는 폐업으로 변경되면 장소를 삭제하지 않고 즉시 `HIDDEN`으로 전환해 사용자 지도와 검색에서 제외한다.

매출액이나 지방세 납부액으로 영업 여부를 추정하지 않는다. 공개 여부의 근거는 인허가 데이터의 영업 상태와 어드민 검수 결과다.

## 2. 범위

### 포함

- 행정안전부 공공데이터포털의 다음 4개 전국 음식점 인허가 API
  - 일반음식점
  - 휴게음식점
  - 제과점영업
  - 유흥주점영업
- 광주광역시와 전라남도 소재 업소만 수집
- 원천 데이터의 반복 동기화와 변경 이력 관리
- 영업 중 후보의 어드민 목록·상세·지도 표시
- 승인·반려 검수 흐름
- 승인 시 공개 `places` 생성 및 원천 기록 연결
- 휴업·폐업 전환 시 기존 공개 장소 자동 숨김

### 제외

- 매출액·지방세 데이터로 영업 여부 판정
- 공공데이터만으로 자동 공개
- 전국 업소 전체 적재
- 사용자 직접 장소 등록
- 다중 인허가를 한 장소에 병합하는 자동 판정
- 폐업 장소 삭제 및 사용자 평가·저장 데이터 삭제
- 단란주점 등 현재 승인받은 4개 API 밖의 추가 업종

## 3. 핵심 원칙

1. `business_licenses`는 외부 원천 사실을 보관하고, `places`는 서비스에 공개할 편집 결과를 보관한다.
2. 공개 쿼리는 계속 `places.status = PUBLISHED`만 조회한다.
3. 후보 쿼리는 `normalized_status = OPEN`이면서 `review_status = PENDING`인 행만 조회한다.
4. 휴업·폐업·상태 불명 행은 DB에 상태 동기화 목적으로 보관하되 후보 목록·후보 지도 API에서 반환하지 않는다.
5. 어드민 승인 트랜잭션이 성공하기 전에는 `places`에 공개 행을 만들지 않는다.
6. 원천 데이터는 멱등 upsert하며, 같은 API 기록을 여러 번 받아도 후보가 중복 생성되지 않는다.
7. 인증키는 브라우저 번들, 로그, Git 저장소, 공개 API 응답에 노출하지 않는다.

## 4. 데이터 모델

### `business_licenses`

공공데이터의 개별 인허가 기록을 보관한다.

| 필드 | 용도 |
|---|---|
| `id` | 내부 UUID |
| `source_type` | `GENERAL_RESTAURANT`, `REST_CAFE`, `BAKERY`, `ENTERTAINMENT_BAR` |
| `source_management_no` | 원천 `MNG_NO`; `(source_type, source_management_no)` 유일키 |
| `business_name` | 원천 `BPLC_NM` |
| `business_subtype` | 원천 `BZSTAT_SE_NM` |
| `sales_status_code/name` | 원천 `SALS_STTS_CD`, `SALS_STTS_NM` |
| `detail_status_code/name` | 원천 `DTL_SALS_STTS_CD`, `DTL_SALS_STTS_NM` |
| `normalized_status` | `OPEN`, `TEMPORARILY_CLOSED`, `CLOSED`, `UNKNOWN` |
| `lot_address` | 원천 `LOTNO_ADDR` |
| `road_address` | 원천 `ROAD_NM_ADDR` |
| `phone` | 원천 `TELNO` |
| `source_x/source_y` | 원천 `CRD_INFO_X`, `CRD_INFO_Y` |
| `latitude/longitude` | 지도 표시용 WGS84 좌표 |
| `region_code` | `GWANGJU`, `JEONNAM` |
| `source_updated_at` | 원천 `LAST_MDFCN_PNT` 또는 `DAT_UPDT_PNT` |
| `raw_payload` | 감사·필드 변경 대응용 JSON |
| `review_status` | `PENDING`, `APPROVED`, `REJECTED` |
| `review_reason` | 반려·보류 사유 |
| `reviewed_by/at` | 검수자와 시각 |
| `first_seen_at/last_seen_at` | 최초·최근 동기화 시각 |
| `created_at/updated_at` | 내부 생성·수정 시각 |

인덱스는 유일키, `(normalized_status, review_status)`, `region_code`, `business_name`, `last_seen_at`에 둔다.

### `place_source_links`

승인된 후보와 공개 장소의 연결을 보관한다.

| 필드 | 용도 |
|---|---|
| `id` | 내부 UUID |
| `place_id` | `places.id` 외래키 |
| `business_license_id` | `business_licenses.id` 외래키 및 유일키 |
| `is_primary` | MVP에서는 항상 참 |
| `created_at` | 연결 시각 |

MVP에서는 후보 하나가 장소 하나를 만든다. 동일 장소의 복수 인허가 자동 병합은 후속 범위다. 관리자가 중복을 발견하면 기존 장소에 연결하는 수동 선택지를 제공한다.

### `public_data_sync_runs`

동기화의 출처, 진행 위치, 건수, 오류를 기록한다.

- `source_type`, `region_code`
- `status`: `RUNNING`, `COMPLETED`, `FAILED`
- `next_page`, `total_count`, `fetched_count`, `inserted_count`, `updated_count`, `skipped_count`
- `started_at`, `finished_at`, `error_summary`

## 5. 원천 상태 정규화

원천 코드와 명칭을 함께 검사한다. 명시적인 영업 상태만 `OPEN`으로 인정하며 알 수 없는 값은 안전하게 `UNKNOWN`으로 둔다.

| 원천 의미 | 정규화 | 후보 노출 | 기존 공개 장소 |
|---|---|---:|---|
| 영업/정상 | `OPEN` | 가능 | 현 상태 유지 |
| 휴업 | `TEMPORARILY_CLOSED` | 금지 | `HIDDEN` |
| 폐업 | `CLOSED` | 금지 | `HIDDEN` |
| 취소·말소·알 수 없음 | `UNKNOWN` | 금지 | 자동 공개 금지, 연결 장소는 `HIDDEN` |

상태 코드 매핑은 실제 응답 fixture로 테스트한다. 명칭 문자열만 느슨하게 추측해 영업 중으로 처리하지 않는다.

## 6. 수집과 동기화

### 조회 범위

각 API의 `/info` JSON 응답을 사용한다. 약 229만 건의 전국 일반음식점을 전부 순회하지 않고 API 조건검색을 사용한다.

- `ROAD_NM_ADDR LIKE 광주광역시%`
- `LOTNO_ADDR LIKE 광주광역시%`
- `ROAD_NM_ADDR LIKE 전라남도%`
- `LOTNO_ADDR LIKE 전라남도%`

도로명 주소와 지번 주소 검색 결과는 `(source_type, MNG_NO)`로 중복 제거한다. 주소가 두 지역 접두어에 해당하지 않는 행은 방어적으로 제외한다.

### 실행 방식

- 어드민의 데이터 동기화 화면에서 출처·지역별 동기화를 시작한다.
- Worker 요청 한 번에 최대 5페이지를 순차 처리하고 `next_page`를 저장한다.
- 완료되지 않은 실행은 다음 요청에서 이어서 처리한다.
- 하루 한 번 Scheduled Worker가 미완료 실행을 이어가고, 완료된 출처·지역은 첫 페이지부터 변경 사항을 재확인한다.
- 429와 5xx만 제한된 횟수로 재시도하며, 나머지 오류는 실행을 `FAILED`로 기록한다.
- 응답 구조와 필수 필드를 검증하고 잘못된 행은 `skipped_count`에 포함한다. 잘못된 행은 후보로 만들지 않는다.

### 인증키 처리

Cloudflare 비밀값 `DATA_GO_KR_SERVICE_KEY`를 서버에서만 읽는다. 공공데이터포털이 발급한 키가 이미 URL 인코딩된 형식이면 한 번 디코딩한 뒤 `URLSearchParams`로 한 번만 인코딩한다. 이중 인코딩으로 발생하는 `SERVICE KEY IS NOT REGISTERED` 오류를 테스트한다.

## 7. 위치 데이터

원천 `CRD_INFO_X/Y`는 네이버 지도에 직접 넣지 않는다. 해당 좌표를 EPSG:5174에서 WGS84 위도·경도로 변환하고 숫자 범위와 대상 지역 경계를 검증한다.

- 유효 좌표가 있으면 후보 지도에 핀을 표시한다.
- 좌표가 없거나 지역 경계를 벗어나면 후보 목록에는 표시하되 후보 지도에서는 제외하고 `좌표 확인 필요`로 표시한다.
- 어드민 승인 전에 네이버 지도에서 핀 위치를 확인하고 필요하면 수정한다.
- 공개 `places.latitude/longitude`에는 검수된 WGS84 값만 저장한다.

## 8. 어드민 검수 화면

새 경로는 `/admin/candidates`와 `/admin/data-sync`로 구성한다. 두 경로 모두 기존 관리자 인증을 통과해야 한다.

### 후보 목록·지도

기본 쿼리는 서버에서 다음 조건을 강제한다.

```text
normalized_status = OPEN
AND review_status = PENDING
AND region_code IN (GWANGJU, JEONNAM)
```

클라이언트 필터를 조작해도 휴업·폐업 행을 받을 수 없게 한다. 목록과 지도는 같은 서버 쿼리를 사용한다. 출처, 지역, 업종, 상호명, 주소로 필터링할 수 있다.

### 승인

승인 폼에서 다음을 확인하거나 입력한다.

- 공개 상호명과 slug
- 주소, 동네, 전화번호
- 지도 핀 위치
- Re:Taste 카테고리
- 대표 이미지와 주차 정보는 선택 사항
- 중복 검색 결과 및 기존 장소 연결 여부

새 장소 승인은 하나의 DB 트랜잭션으로 처리한다.

1. 후보가 여전히 `OPEN + PENDING`인지 재검증한다.
2. 필수값과 중복을 검증한다.
3. `places.status = PUBLISHED`로 장소를 만든다.
4. 카테고리와 `place_source_links`를 만든다.
5. 후보를 `APPROVED`로 바꾸고 검수자를 기록한다.

어느 단계든 실패하면 전체를 롤백한다. 기존 장소 연결을 선택한 경우 새 장소를 만들지 않고 링크와 승인 상태만 생성한다.

### 반려

반려 사유를 필수로 기록하고 `REJECTED`로 바꾼다. 원천 상태나 핵심 주소·상호가 이후 변경되면 재검수 대상으로 되돌릴 수 있도록 변경 여부를 표시하되 자동으로 `PENDING`으로 복귀시키지는 않는다.

## 9. 폐업·휴업 처리

동기화 upsert 후 연결된 원천 기록의 정규화 상태가 `OPEN`이 아니면 같은 트랜잭션에서 연결 장소를 `HIDDEN`으로 바꾼다.

- 장소 행은 삭제하지 않는다.
- 평가, 저장, 추천·비추천 기록은 보존한다.
- 사용자 지도, 검색, 상세 공개 API는 기존 `PUBLISHED` 조건 때문에 즉시 제외된다.
- 재영업으로 `OPEN`이 되어도 자동 재공개하지 않는다. 어드민이 상태와 위치를 재확인한 뒤 수동으로 `PUBLISHED`로 전환한다.
- 변경 사유와 시각은 감사 로그에 기록한다.

## 10. 보안과 개인정보

- 공공데이터 API 호출은 Worker 서버에서만 수행한다.
- 동기화·승인·반려·재공개는 관리자 인증과 CSRF 방어를 적용한다.
- API 키와 원본 응답 전체를 애플리케이션 로그에 남기지 않는다.
- 원천 전화번호는 장소 검수 목적에 한해 저장하고 사용자 화면 노출 정책은 별도로 적용한다.
- 어드민 변경은 행위자, 대상, 이전/이후 상태, 시각을 감사 로그에 남긴다.

## 11. 실패 처리와 관측성

- 출처·지역·페이지 단위로 구조화 로그를 남기되 키와 원본 개인정보는 제외한다.
- 동기화 화면에 마지막 성공 시각, 진행 페이지, 처리·건너뜀·오류 건수를 표시한다.
- 한 출처의 실패가 다른 출처의 기존 후보와 공개 장소를 삭제하거나 초기화하지 않게 한다.
- API에서 행이 일시적으로 누락됐다는 이유만으로 폐업 처리하지 않는다. 명시적인 휴업·폐업 상태를 받은 경우에만 자동 숨김한다.
- 장기간 미수신 행은 `stale` 경고만 표시하고 어드민 확인 대상으로 둔다.

## 12. 테스트 기준

### 단위 테스트

- 인코딩/디코딩된 서비스 키가 URL에서 정확히 한 번 인코딩됨
- 네 가지 API 응답 파싱과 필수 필드 검증
- 상태 코드 정규화와 `UNKNOWN` 기본값
- 광주·전남 주소 접두어 판정
- EPSG:5174 → WGS84 변환과 지역 경계 검증
- 후보 노출 조건

### 통합 테스트

- 동일 데이터 반복 동기화 시 중복 없음
- 영업 중 신규 행은 `PENDING` 후보가 됨
- 휴업·폐업 신규 행은 후보 목록·지도 결과에 없음
- 승인 트랜잭션이 장소·카테고리·링크·검수 상태를 함께 생성함
- 연결 행이 폐업으로 바뀌면 공개 장소가 `HIDDEN`이 됨
- 재영업만으로 장소가 자동 재공개되지 않음
- 비관리자는 동기화·승인·반려 불가

### 브라우저 검증

- 후보 목록과 지도에 같은 영업 중 후보만 표시
- 좌표 없는 후보가 지도에 잘못 표시되지 않음
- 승인 후 사용자 지도·검색에 장소 표시
- 폐업 fixture 동기화 후 사용자 지도·검색에서 즉시 사라짐

## 13. 배포 순서

1. D1 마이그레이션 적용
2. Cloudflare에 `DATA_GO_KR_SERVICE_KEY` 비밀값 등록
3. Preview에서 네 가지 API의 광주·전남 소량 동기화
4. 후보 목록·지도와 승인·반려 검증
5. 폐업 전환 fixture로 자동 숨김 검증
6. PR 검사 통과 및 diff 검토 후 squash merge
7. 병합된 `main`에서 프로덕션 배포
8. 출처·지역별 최초 동기화 실행 및 건수 확인

## 14. 완료 조건

- 영업 중인 광주·전남 음식점·주점 기록만 어드민 후보 목록에 나타난다.
- 휴업·폐업 기록은 후보 지도와 사용자 지도 어디에도 나타나지 않는다.
- 어드민 승인 전 후보는 사용자에게 공개되지 않는다.
- 승인된 후보만 공개 장소로 조회된다.
- 공개 후 폐업 상태가 확인되면 장소가 자동으로 숨겨지고 기존 사용자 데이터는 보존된다.
- 동기화가 반복 가능하고 중복, 키 노출, 전국 데이터 전수 수집이 발생하지 않는다.
