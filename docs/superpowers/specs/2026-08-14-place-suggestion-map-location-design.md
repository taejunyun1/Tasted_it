# Re:Taste 장소 제안 지도 위치 선택·관리자 승인 안정화 설계

- 상태: `PROPOSED` — 이 문서를 포함한 Pull Request가 병합되면 `ACCEPTED`
- 작성일: 2026-08-14
- 담당자: Codex / taejun-yun
- 추적 이슈: [#99](https://github.com/taejunyun1/Tasted_it/issues/99)
- 기준선: `origin/main@5a94801`
- 범위: 장소 제안 위치 입력 UX, 관리자 위치 확인, 승인 오류·중복 승인 방어
- 제외 범위: 제품 코드, migration, 운영 데이터, 배포 변경

## 1. 목적

사용자가 위도·경도를 직접 입력하지 않고 상호명과 주소를 검색해 지도에서 위치를 확인한 뒤 장소를 제안하도록 바꾼다. 관리자는 같은 위치 정보를 지도에서 확인·보정한 후 안전하게 승인할 수 있어야 한다.

이 설계는 다음 문제를 해결한다.

1. 일반 사용자가 위도·경도를 이해하고 입력해야 하는 현재 폼의 사용성이 낮다.
2. 입력된 주소와 좌표가 실제 같은 위치인지 확인하기 어렵다.
3. 좌표가 없는 기존 제안은 관리자가 승인하려 하면 서버 예외가 전체 오류 화면으로 전파된다.
4. 승인 버튼 연타나 두 관리자의 동시 승인으로 장소가 중복 생성될 수 있다.
5. 승인 실패 이유가 해당 카드 안에 표시되지 않아 사용자가 무엇을 고쳐야 하는지 알 수 없다.

## 2. 핵심 결정

### 2.1 위치 입력은 `주소 검색 → 지도 확인 → 위치 확정` 흐름으로 바꾼다

사용자에게 위도와 경도 입력란을 노출하지 않는다. 장소 제안 화면의 위치 입력 흐름은 다음과 같다.

1. 상호명과 주소를 입력한다.
2. `지도에서 위치 찾기`를 누른다.
3. 기존 NAVER Maps 지오코더가 주소를 좌표로 변환한다.
4. 지도와 핀이 나타나며 사용자가 실제 출입구 또는 건물 위치를 확인한다.
5. 필요하면 핀을 지도 안에서 조정한다.
6. `이 위치가 맞아요`를 누르면 좌표가 내부 hidden field에 저장된다.
7. 위치가 확정되어야 제안을 접수할 수 있다.

사용자가 주소를 다시 수정하면 이전 위치 확정은 즉시 무효화한다. 수정된 주소로 다시 위치를 찾아야 한다.

### 2.2 네이버 지도 기존 연동만 사용한다

- 기존 `NAVER_MAPS_CLIENT_ID`와 NAVER Maps Dynamic Map을 그대로 사용한다.
- 현재 SDK 로더에 공식 `geocoder` 서브모듈을 추가한다.
- 새 외부 공급자, 새 비밀값, 새 npm 의존성은 추가하지 않는다.
- NAVER 장소 ID를 내부 원본으로 저장하지 않는다.
- D1의 주소와 WGS84 좌표를 Re:Taste 내부 단일 기준 원본(SSOT)으로 유지한다.

단, 지도 표시 권한만으로 주소 변환 호출이 자동 승인되는 것은 아니다. 같은 NAVER Cloud 애플리케이션에 Geocoding 사용 상품·웹 서비스 URL·쿼터가 설정되어 있어야 하며, 호출마다 Geocoding 일일 허용량과 과금 기준을 사용한다. 구현 PR에는 실제 상품 활성 상태, 일일 호출 상한, 비용 책임자와 kill switch를 기록한다.

따라서 이번 변경은 기술 스택 확장이 아니라 승인된 지도 기준선의 기능 확장이다.

### 2.3 검색 결과는 주소와 지역 범위를 검증한다

자동 완성 검색 전체를 만들지 않고, 사용자가 입력한 주소 한 건을 지오코딩한다. 첫 단계에서 광주광역시·전라남도 주소만 허용한다.

검증 순서:

1. 사용자 입력 주소가 비어 있지 않은지 확인한다.
2. 네이버 지오코더 응답이 정확히 한 곳 이상인지 확인한다.
3. 응답의 도로명 또는 지번 주소가 광주·전남 범위인지 확인한다.
4. 좌표가 광주·전남을 포괄하는 서버 안전 경계 안인지 다시 확인한다.
5. 핀 조정은 최초 지오코딩 위치 반경 2km 안에서만 허용한다.
6. 서버 action에서 같은 규칙을 다시 검증한다.

지역 검증은 클라이언트 편의 기능이 아니라 서버 저장 경계에서도 수행한다.

### 2.4 새 제안은 위치 필수, 기존 제안은 관리자 보정 가능

- 새 장소 제안은 주소와 확정 좌표가 모두 있어야 `SUBMITTED`가 된다.
- 기존 데이터 중 좌표가 없는 제안은 삭제하지 않는다.
- 관리자 화면에서 `위치 확인 필요`로 표시하고, 관리자가 주소 검색과 지도 확인으로 좌표를 채울 수 있다.
- 위치가 없는 제안의 승인 버튼은 비활성화하고 `먼저 위치를 확인해 주세요`를 카드 안에 표시한다.

### 2.5 관리자 승인은 화면 전체 오류가 아니라 카드 단위 결과를 반환한다

관리자 장소 제안 카드는 `useFetcher` 기반의 독립 작업 단위로 바꾼다.

- 제출 중에는 해당 카드의 승인·반려·위치 수정 버튼만 잠근다.
- 성공하면 `승인 완료` 상태와 생성된 장소 링크를 표시한다.
- 입력 오류는 카드 안 필드 아래에 표시한다.
- 다른 관리자가 먼저 처리한 경우 `이미 처리된 제안입니다`를 표시하고 최신 상태를 다시 읽는다.
- 예상하지 못한 오류는 `승인하지 못했습니다. 다시 시도해 주세요`로 축약하고 내부 예외나 SQL을 노출하지 않는다.

브라우저의 `unsafe-eval` CSP 경고를 해제하기 위해 정책을 약하게 만들지 않는다. 현재 오류 화면은 서버 action 예외를 정상적인 오류 응답으로 변환하지 않은 것이 핵심이므로 서버 오류 계약을 고친다.

### 2.6 한 제안은 한 장소로만 승인된다

승인 동작은 다음 불변식을 만족해야 한다.

- 동일 `placeSuggestion.id`에서 생성되는 장소는 최대 하나다.
- 승인 성공, 제안 상태 변경, 장소 카테고리, revision, audit log는 한 D1 batch에서 함께 반영된다.
- 조건부 장소 생성이 0건이면 뒤의 외래키 작업도 성공 처리하지 않는다.
- D1이 실제 commit 후 응답만 잃은 모호한 실패에서는 `approvedPlaceId` 사후 조건을 조회해 기존 성공을 반환한다.
- 같은 버튼 재전송은 새 장소를 만들지 않고 기존 승인 결과를 표시한다.

## 3. 사용자 화면 구조

### 3.1 회원 장소 제안

```text
MEMBER / PLACE SUGGESTION
새 장소 제안

상호명
[ 오육일김밥                         ]

주소
[ 전남 무안군 ...                    ]
[ 지도에서 위치 찾기 ]

┌──────────────────────────────────┐
│             NAVER MAP            │
│                  ● 선택한 위치    │
└──────────────────────────────────┘
전남 무안군 ...
핀을 움직여 실제 위치를 맞춰 주세요.

[ 이 위치가 맞아요 ]

대표 카테고리 / 전화번호 / 추천 이유
[ 비공개 제안 접수 ]
```

상태별 문구:

| 상태 | 화면 |
|---|---|
| 검색 전 | `주소를 입력하고 지도에서 위치를 찾아주세요.` |
| 검색 중 | `위치를 찾는 중…` |
| 검색 성공 | 지도·핀·정규화 주소 표시 |
| 검색 결과 없음 | `이 주소의 위치를 찾지 못했어요. 건물명이나 도로명까지 입력해 주세요.` |
| 범위 밖 | `현재는 광주·전남의 장소만 제안할 수 있어요.` |
| 지도 SDK 실패 | `지도를 불러오지 못했어요. 잠시 후 다시 시도해 주세요.` |
| 위치 확정 | `위치 확인 완료` 배지 |

### 3.2 관리자 제안 카드

```text
SUBMITTED · 위치 확인 완료
오육일김밥
전남 무안군 ...

┌──────────────────────────────┐
│ NAVER MAP              ●     │
└──────────────────────────────┘

[ 위치 수정 ]
위도·경도 숫자는 보조 정보로만 작게 표시

승인 근거
[                               ]

[ 승인 ] [ 추가 정보 ] [ 반려 ]
```

좌표가 없는 기존 제안:

```text
위치 확인 필요
[ 주소로 위치 찾기 ]
[ 승인 — 비활성 ]
```

## 4. 데이터 계약

기존 `place_suggestions.address`, `latitude`, `longitude`를 그대로 사용한다. 새 테이블은 만들지 않는다.

클라이언트가 보내는 값:

```ts
type ConfirmedPlaceLocation = {
  address: string;
  latitude: number;
  longitude: number;
};
```

화면은 `locationConfirmed=true`를 제출하지만 이는 UI 상태일 뿐 보안 토큰이 아니다. 서버는 이 값을 신뢰하지 않고 주소·좌표 범위와 필수값을 다시 검증한다. 확정 상태는 DB에 별도 저장하지 않는다.

관리자 위치 수정은 기존 suggestion 행의 주소·좌표를 업데이트하고 audit log를 남긴다. 승인 전에 수정된 최종 값이 장소 생성 입력이 된다.

## 5. 서버 오류 계약

모든 예상 오류는 JSON action data로 변환한다.

```ts
type PlaceSuggestionActionResult =
  | { ok: true; intent: "submit" | "location" | "approve"; suggestionId: string; placeId?: string; message: string }
  | {
      ok: false;
      status: 400 | 409 | 503;
      code:
        | "LOCATION_REQUIRED"
        | "LOCATION_OUT_OF_SCOPE"
        | "ADDRESS_LOCATION_MISMATCH"
        | "REVIEW_REASON_REQUIRED"
        | "SUGGESTION_ALREADY_PROCESSED"
        | "MAP_PROVIDER_UNAVAILABLE"
        | "APPROVAL_FAILED";
      message: string;
      fieldErrors?: Record<string, string>;
    };
```

- `400`: 사용자가 수정할 수 있는 값 오류
- `409`: 이미 처리되었거나 경쟁 요청에서 진 상태
- `503`: 외부 지도 또는 D1 일시 오류
- 알 수 없는 예외는 구조화 로그에 `code`, `intent`, `suggestionId`만 남기고 개인정보·주소 원문·비밀값은 남기지 않는다.

## 6. 보안·개인정보·비용

- NAVER 키는 기존 클라이언트 ID만 사용하고 서버 비밀값을 브라우저에 노출하지 않는다.
- 장소 주소는 서비스 핵심 공개 정보지만, 제안이 승인되기 전에는 공개 API와 검색 결과에 노출하지 않는다.
- 관리자 mutation은 관리자 역할과 same-origin 검증을 모두 통과해야 한다.
- 주소·좌표는 Zod로 엄격 검증하고 `NaN`, 무한대, 범위 밖 숫자를 거부한다.
- 지오코딩은 주소 입력 또는 명시적 재검색 때만 실행한다. 타이핑마다 API를 호출하지 않는다.
- 1회 클릭당 1회 요청으로 제한해 호출량을 예측 가능하게 유지한다.
- `NAVER_PLACE_GEOCODING_ENABLED=false` kill switch를 두고, 비활성 상태에서는 새 위치 검색을 막되 기존 제안 조회와 관리자 비지도 작업은 유지한다.

## 7. 접근성·반응형

- 지도만으로 위치를 전달하지 않고 확정 주소를 텍스트로 함께 표시한다.
- 지도 조작이 어려운 키보드 사용자를 위해 `핀을 원래 위치로` 버튼과 좌표 미세 조정 버튼을 제공한다.
- 모든 활성 컨트롤은 최소 44×44px이다.
- 오류는 색상 외에 텍스트와 `aria-describedby`로 연결한다.
- 지도 로딩 상태는 `aria-live="polite"`로 알린다.
- 모바일에서는 지도 높이 280px, 데스크톱에서는 360px을 기준으로 한다.
- 관리자 카드 지도는 기본 접힘 상태로 두어 200개 제안이 동시에 지도를 생성하지 않게 한다.

## 8. 실패·복구 시나리오

### 8.1 지도 SDK 실패

입력 내용은 유지하고 위치 확정만 막는다. 자동으로 제안을 제출하거나 임의 좌표를 만들지 않는다.

### 8.2 지오코더가 여러 결과를 반환

첫 결과를 자동 확정하지 않는다. 최대 5개 주소 후보를 텍스트 목록으로 보여주고 사용자가 하나를 선택한 뒤 지도에서 확인한다.

### 8.3 승인 중 브라우저 재전송

서버의 조건부 승인과 사후 조건 조회가 기존 성공 결과를 반환한다. 새 장소는 생성하지 않는다.

### 8.4 두 관리자가 동시에 승인

먼저 commit한 요청만 장소를 만든다. 늦은 요청은 `이미 다른 관리자가 처리했습니다`를 받고 최신 상태와 생성 장소 링크를 표시한다.

### 8.5 승인 후 응답 유실

요청 재시도 시 suggestion의 `approvedPlaceId`를 확인하고 기존 장소를 성공 결과로 반환한다.

## 9. rollout과 rollback

### rollout

1. 순수 위치 검증과 NAVER SDK 지오코더 타입을 먼저 배포한다.
2. 관리자 위치 보정과 승인 오류 계약을 먼저 활성화해 기존 좌표 누락 제안을 처리한다.
3. 회원 제안 화면의 새 위치 필수 흐름을 활성화한다.
4. 7일 동안 지오코딩 성공률, 위치 확정 이탈률, 승인 400/409/503 비율을 관찰한다.

### rollback

- 새 UI를 되돌려도 기존 address/latitude/longitude 스키마는 호환된다.
- 지오코더 장애 시 feature flag로 새 제안 접수를 일시 중단하고 기존 제안 조회·관리자 검수는 유지한다.
- 승인 서비스는 이전 구현으로 되돌리지 않는다. 동시 승인·오류 계약 보강은 데이터 안전 수정으로 유지한다.

## 10. 수용 기준

1. 일반 사용자에게 위도·경도 입력칸이 보이지 않는다.
2. 주소 검색 후 지도 핀을 확정해야 새 제안을 접수할 수 있다.
3. 광주·전남 밖 주소와 좌표는 클라이언트·서버에서 모두 거부된다.
4. 주소를 수정하면 기존 위치 확정이 무효화된다.
5. 좌표 없는 기존 제안은 관리자 지도에서 보정할 수 있다.
6. 승인 예상 오류가 전체 오류 화면이 아니라 카드 안에 표시된다.
7. 승인 연타와 두 관리자 동시 승인에서도 장소가 하나만 생성된다.
8. commit 후 응답 유실 재시도도 기존 성공 결과를 반환한다.
9. 지도 실패 시 입력값이 유지되고 임의 좌표가 저장되지 않는다.
10. 데스크톱·모바일·키보드 QA가 모두 통과한다.
