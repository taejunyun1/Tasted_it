# Re:Taste 제품·개발 마스터 설계

**상태:** 승인됨  
**작성일:** 2026-08-05  
**기준 문서:** `refer/ReTaste_Codex_MVP_개발명세서.docx`, `refer/ReTaste_MVP_사업계획서.docx`  
**목표:** 1인 개발로 1주 안에 실제 데이터 기반 웹 베타를 만들고, 3주 동안 운영 가능한 MVP로 확장한 뒤 B2B Re:Taste 캠페인 결제와 iOS·Android 앱 출시까지 단계적으로 연결한다.

## 1. 문서의 역할

이 문서는 Re:Taste 제작의 제품·기술 기준이다. 기능 우선순위, 시스템 경계, 신뢰 원칙, 단계별 완료 조건이 충돌할 때 이 문서를 기준으로 판단한다. 세부 수학 모델과 데이터 정의는 기존 개발명세서를 따르되, 일정과 출시 순서는 이 문서가 우선한다.

변경 원칙은 다음과 같다.

1. 새 기능은 현재 단계의 출시 목표에 직접 기여해야 한다.
2. 추천 결과와 유료 상품은 데이터·권한·화면에서 분리한다.
3. 원시 평가와 알고리즘 버전을 보존해 모든 점수를 재계산할 수 있어야 한다.
4. 웹과 앱은 같은 도메인 서비스와 JSON API를 사용한다.
5. 각 단계는 독립적으로 배포하고 실제 사용자 또는 운영자가 검증할 수 있어야 한다.

## 2. 제품 정의와 최종 목표

Re:Taste는 광주·전남의 음식점을 메뉴별 지도와 사진 중심 콘텐츠로 탐색하는 지역 큐레이션 서비스다. 공개 리뷰어의 평가와 일반 사용자의 추천·비추천을 결합하되, 단순 별점 평균 대신 표본 수·불일치·리뷰어 신뢰도를 반영한다.

장기 제품은 세 축으로 구성한다.

- **소비자 제품:** 지도, 장소 상세, 추천율, Place DNA, 배지, 저장, 개인화.
- **콘텐츠 운영:** 장소·사진·리뷰어·평가·제안·정정·감사 관리.
- **B2B 상품:** 평가 결과가 아닌 촬영·재방문·캠페인 운영·성과 리포트를 판매.

최종 출시 상태는 반응형 웹, iOS 앱, Android 앱이 하나의 서비스 데이터를 공유하고 B2B 캠페인 결제가 운영되는 상태다.

## 3. 비협상 제품 원칙

- 업주는 추천율, Golden Pick, Hidden Gem, Consensus, Hot Take 결과를 구매할 수 없다.
- 유료 캠페인은 모든 노출 지점에서 편집 추천과 구별한다.
- 일반 사용자는 무제한 장문 리뷰나 사진을 올리지 않는다.
- 사진 업로드는 Reviewer와 Admin에게만 허용한다.
- 관리자는 추천율을 직접 수정할 수 없다.
- 투표 변경과 철회는 이벤트로 보존하고 현재 투표를 별도 상태로 유지한다.
- 정밀 위치를 저장하지 않으며 위치 권한은 사용자의 명시적 동작에서만 요청한다.
- MVP 기간에는 광주·전남 이외 지역, 업주 직접 정보 수정, 커머스, AI 코스 추천을 구현하지 않는다.

## 4. 사용자와 권한

### Guest

지도, 목록, 상세, 리뷰어 프로필, 추천율과 공개 캠페인을 조회한다.

### User

Guest 기능에 더해 추천·비추천, 저장, 컬렉션, 장소 제안을 사용한다.

### Reviewer

User 기능에 더해 블라인드 평가, 확신도, 호불호 예측, Place DNA, Golden Pick, 사진 업로드를 사용한다.

### Admin

장소·카테고리·제안·리뷰어 권한·이미지·배지·알고리즘 버전·캠페인·주문을 관리한다. 민감한 변경은 사유와 감사 로그가 필수다.

### Business Contact

초기에는 별도 업주 계정 없이 문의·견적·전자 결제 링크로 운영한다. 반복 구매와 운영량이 검증된 뒤 Owner 역할과 사업자 포털을 추가한다. 이 순서로 1인 개발의 인증·분쟁·정보 정정 부담을 줄인다.

## 5. 목표 아키텍처

```text
Responsive Web / iOS / Android
               │
     Shared JSON API boundary
               │
 Auth ─ Places ─ Ratings ─ Reviewers ─ Campaigns ─ Orders
               │
 D1 ─ R2 ─ Cloudflare Images ─ Scheduled Jobs / Queues
               │
 NAVER Maps API ─ Payment Provider ─ Notification Provider
```

### 기술 기준

- Cloudflare Workers + Static Assets
- React Router full-stack + TypeScript strict + Vite
- Cloudflare D1 + Drizzle ORM
- Better Auth + D1 세션
- Cloudflare R2 + Cloudflare Images/Image Transformations
- NAVER Maps Dynamic Map SDK(Web·Android·iOS) + Geocoding API
- Zod 입력 검증
- Vitest + Workers integration + Playwright
- Workers Observability + 구조화 로그

Cloudflare와 라이브러리 버전·호환성은 구현 시작 시 공식 문서로 확인하고 ADR에 고정한다. Workers 런타임에서 동작하지 않는 Node 전용 API는 사용하지 않는다.

### 모듈 경계

- `auth`: 사용자, 세션, 역할, 권한 검사.
- `places`: 장소, 카테고리, 검색, 지도 조회, 제안.
- `ratings`: 투표 이벤트, 현재 투표, 점수 스냅샷, 배지.
- `reviewers`: 프로필, DNA, Golden Pick, 유사도와 취향 그래프.
- `images`: 업로드 권한, 메타데이터 제거, R2와 변환 URL.
- `campaigns`: 유료 상품, 일정, 공개 캠페인, 결과 리포트.
- `orders`: 견적, 주문, 결제·취소·환불 상태, 결제 웹훅.
- `admin`: 위 모듈의 운영 화면과 감사 가능한 명령.

UI route는 도메인 규칙을 직접 구현하지 않는다. 웹 loader/action과 앱 JSON endpoint는 같은 서비스 함수를 호출한다.

## 6. 핵심 데이터 흐름

### 장소 탐색

1. 사용자가 카테고리 또는 지도 영역을 선택한다.
2. URL query가 카테고리·bounding box·정렬·선택 장소를 보존한다.
3. 서버가 공개 장소와 점수 스냅샷을 cursor 방식으로 조회한다.
4. 지도 핀과 접근 가능한 목록이 동일한 결과와 선택 상태를 표시한다.
5. 상세에서 길찾기 클릭을 익명 분석 이벤트로 기록한다.

### 사용자 투표

1. 서버가 인증, 역할, 입력, rate limit을 검증한다.
2. `vote_events`에 CREATE·CHANGE·WITHDRAW 이벤트를 추가한다.
3. `current_votes`를 같은 트랜잭션에서 갱신한다.
4. 해당 장소의 점수 스냅샷을 stale로 표시한다.
5. v1 점수를 즉시 또는 짧은 비동기 작업으로 재계산한다.
6. UI는 갱신 결과와 표본 상태를 표시한다.

### 리뷰어 평가

1. 제출 전 다른 리뷰어의 개별 선택을 숨긴다.
2. 투표, 확신도, 호불호 예측, DNA, Golden Pick을 검증한다.
3. 평가 이벤트와 DNA 값을 저장한다.
4. Golden Pick 월 3회와 동일 장소 90일 제한을 적용한다.
5. 제출 후에만 집단 분포를 공개한다.

### B2B 결제

1. 업주가 캠페인 문의를 제출한다.
2. Admin이 상품, 범위, 금액, 일정이 포함된 견적을 생성한다.
3. 시스템이 만료 시간이 있는 결제 링크를 발급한다.
4. 결제사의 서명된 웹훅으로 주문 상태를 갱신한다.
5. 결제 완료 후 캠페인 작업 항목과 일정을 생성한다.
6. 공개 콘텐츠에는 Sponsored 또는 Re:Taste Campaign 표시를 붙인다.
7. 종료 후 저장·길찾기·페이지 반응을 집계한 리포트를 제공한다.

평가와 배지 생성 로직은 주문·결제 테이블을 읽지 않는다. 캠페인 수행 중 리뷰어가 남긴 평가도 일반 평가와 같은 규칙을 적용한다.

## 7. 4주 웹 MVP 제작 계획

### 1주차: 실데이터 베타

**목표:** 외부 사용자가 실제 장소를 지도에서 찾고 상세를 본 뒤 투표·저장할 수 있다.

포함 범위:

- Workers·React Router·TypeScript 프로젝트와 local/preview/production 환경
- D1·Drizzle의 장소, 카테고리, 사용자, 투표, 저장 기본 스키마
- 관리자 CSV import와 행별 오류 리포트
- 실제 장소 20~50곳과 대표 이미지 URL을 이용한 초기 데이터
- 메인, 카테고리 지도·목록, 장소 상세
- MapLibre 클라이언트 전용 지도와 URL 상태 동기화
- 카카오·네이버 등 외부 길찾기 딥링크
- 최소 로그인, 추천·비추천 변경, 장소 저장
- Beta(2,2) 기반 기본 추천율과 표본 부족 표시
- 최소 관리자 장소 CRUD
- 핵심 사용자 흐름의 단위·통합·E2E 테스트

제외 범위:

- 리뷰어 신뢰도, 중복 감쇠, 자동 Hidden Gem·Consensus
- 취향 그래프, 정교한 개인화, 직접 이미지 업로드
- 업주 계정, 결제, 캠페인, 모바일 앱

완료 기준:

- production URL에서 모바일 핵심 흐름이 동작한다.
- CSV로 20개 이상의 실제 장소를 재현 가능하게 등록한다.
- Guest 조회와 User 투표·저장 권한이 서버에서 구분된다.
- 지도·목록·상세가 같은 장소 데이터를 표시한다.
- 투표를 변경해도 활성 투표가 사용자·장소당 하나만 존재한다.

### 2주차: 운영 CMS와 리뷰어

**목표:** 운영자와 리뷰어가 개발자의 DB 직접 조작 없이 콘텐츠를 만든다.

- Better Auth 인증과 User·Reviewer·Admin 권한 가드 완성
- 리뷰어 공개 프로필과 Reviewer 대시보드
- 블라인드 평가, 확신도, 호불호 예측
- 카테고리별 버전형 DNA 템플릿과 DNA 입력
- Golden Pick 월 3회·90일 제한
- 장소 제안, 관리자 승인·반려·추가정보 요청
- CSV 검증과 중복 장소 후보 탐지 강화
- 관리자 감사 로그
- 실제 장소 100곳 이상으로 확대

완료 기준:

- 세 역할의 허용·거부 통합 테스트가 통과한다.
- 제안 승인으로 장소 초안이 생성되고 공개까지 이어진다.
- 리뷰어는 제출 전 타 리뷰어 선택을 볼 수 없다.
- Golden Pick 한도와 이력이 서버에서 강제된다.

### 3주차: 평가 신뢰도와 이미지

**목표:** 추천 결과를 재현할 수 있고 사진 운영이 플랫폼 내부에서 가능하다.

- 버전형 추천율 설정과 pure TypeScript 계산 모듈
- 리뷰어 총량·사용자 표본·불일치 감쇠
- 리뷰어 신뢰도 v1과 유사 리뷰어 중복 감쇠
- 점수 스냅샷, stale 표시, 재계산 작업
- Consensus·Hidden Gem·Hot Take 판정과 근거 보존
- R2 원본 업로드와 이미지 변환 URL
- MIME sniffing, 크기 제한, 콘텐츠 해시, EXIF 제거
- 이미지 순서·역할·focal point 관리
- 실제 장소 200곳 이상으로 확대

완료 기준:

- 개발명세서의 알고리즘 시나리오 단위 테스트가 통과한다.
- 동일 입력과 버전은 결정론적 결과를 만든다.
- 모든 스냅샷은 입력 수와 알고리즘 버전을 기록한다.
- Reviewer·Admin만 유효한 이미지 파일을 업로드할 수 있다.

### 4주차: 개인화와 출시 안정화

**목표:** 300곳 규모의 비공개 베타를 운영하고 반복 사용을 측정할 수 있다.

- 저장 장소, 개인 컬렉션, 내 투표·제안 상태
- 간소화한 리뷰어 유사도와 취향 그래프
- 지도 클러스터링, 검색, 필터, 모바일 지도·목록 전환
- Kakao 주변 주차장 검색과 캐시
- 기능별 rate limit, 배지 만료 스케줄, 캐시 무효화
- 구조화 로그와 핵심 행동 이벤트
- 접근성, 반응형, 성능, 오류 상태 점검
- D1 export, R2 inventory, 환경변수와 복구 절차
- 실제 장소 300곳과 대표 사진·카테고리·좌표 검수
- 비공개 베타와 회귀 E2E

완료 기준:

- 핵심 페이지 LCP 목표 2.5초, 지도 첫 상호작용 목표 3초 이내를 중급 모바일·4G 조건에서 측정한다.
- 공개 장소의 좌표·대표 사진·주력 카테고리·길찾기 누락률이 5% 이하다.
- 배지 만료, 권한 거부, 외부 API 실패가 로그에서 구분된다.
- 이용약관, 개인정보처리방침, 리뷰·광고 분리 정책과 문의 채널이 존재한다.

### 개인정보 처리방침 기준

- 개인정보 처리방침과 이용약관의 작성 기준은 [`kimlawtech/korean-privacy-terms`](https://github.com/kimlawtech/korean-privacy-terms) 저장소의 한국 PIPA용 `privacy-kr` 템플릿·체크리스트로 고정한다.
- 저장소 문구를 완성본으로 간주하지 않는다. Re:Taste의 실제 수집 항목, 처리 목적, 보유기간, 파기, 위탁·국외 이전, 쿠키·분석 도구, 이용자 권리, 개인정보 보호책임자와 문의처를 배포 환경과 대조하여 채운다.
- 베타에서는 이메일, 표시 이름, 로그인 세션, 추천·비추천, 저장 장소와 Cloudflare 운영 로그를 데이터 인벤토리에 포함한다. 브라우저 위치는 사용자가 `내 주변`을 누를 때만 요청하며, 서버 저장 여부를 방침에 명시한다.
- Cloudflare, 결제사, 이메일·분석·크래시 도구를 추가할 때마다 개인정보 처리방침과 위탁·국외 이전 표를 같은 변경에서 갱신한다.
- 웹 공개 전 `/privacy`와 `/terms`를 제공하고 회원가입·로그인 화면에서 접근 가능하게 한다. 앱 출시 전에는 계정 삭제, 권한 설명, 스토어 개인정보 표시와 문서 내용이 일치하는지 재검증한다.
- 기준 저장소는 Apache-2.0 라이선스이므로 필요한 저작권·라이선스 고지를 보존한다. 생성 문서는 참고용 초안이므로 실서비스와 결제 출시 전 법률 전문가의 최종 검토를 출시 게이트로 둔다.

## 8. MVP 이후 제작 로드맵

### Phase 2: 운영 안정화 — 권장 2~4주

- 실제 사용 퍼널과 오류를 기반으로 지도·상세·투표 UX 개선
- 장소 정보 정정과 업체 이의 제기 워크플로
- 리뷰어 활동·콘텐츠 누락·배지 만료 운영 대시보드
- 알고리즘 결과 분포, 호불호 예측 정확도, 부정행위 검토 도구
- 캠페인 도입 전 광고·평가 분리 정책과 법무 검토
- B2B 문의 폼과 영업 파이프라인

진입 조건은 300곳 데이터 품질과 핵심 E2E가 안정적인 상태다. 종료 조건은 개발자 없이 운영자가 장소·리뷰어·정정·배지를 관리할 수 있는 상태다.

### Phase 3: Re:Taste B2B 결제 — 권장 3~5주

#### 상품

- **Revisit:** 장소 정보 갱신, 리뷰어 재방문, 결과 노출.
- **Re:Taste Campaign:** 재평가, 사용자 혜택, 캠페인 노출, 반응 리포트.
- **Re:Taste Studio:** 캠페인, 사진·영상, 에디토리얼 제작.

#### 결제 1차 범위

- Admin이 관리하는 상품·견적·주문
- 결제 링크와 단건 결제
- 서명 검증·중복 방지되는 웹훅
- 주문 상태: DRAFT, QUOTED, PAYMENT_PENDING, PAID, IN_PROGRESS, COMPLETED, CANCELED, REFUNDED
- 캠페인 상태: DRAFT, SCHEDULED, ACTIVE, ENDED, ARCHIVED
- 취소·전액 환불과 사유 기록
- 영수증·세금계산서 처리 상태 기록
- 캠페인 전용 공개 페이지와 명확한 유료 표시
- 저장·길찾기·페이지 반응 기반 종료 리포트

부분 환불, 구독, 복합 정산, 리뷰어 개별 지급 자동화는 거래량이 검증된 뒤 추가한다.

#### 결제 안전장치

- 웹훅 서명 검증과 idempotency key를 필수 적용한다.
- 금액과 상품 정보는 서버가 확정하며 클라이언트 값을 신뢰하지 않는다.
- 결제 상태 변경과 관리자 수동 조정은 모두 감사 로그에 남긴다.
- 평가 서비스는 결제 여부를 입력값으로 사용하지 않는다.
- 캠페인 참여 리뷰어에게 결과 방향을 요구하지 않는다.

### Phase 4: 앱 출시 — 권장 6~10주

#### 앱 전략

웹 MVP의 API와 인증 경계를 안정화한 뒤 얇은 네이티브 클라이언트를 만든다. 앱 전용 데이터베이스나 평가 엔진은 만들지 않는다. 첫 앱은 소비자 탐색과 반복 사용에 집중하고 B2B 주문·결제는 웹에서 처리한다.

#### 앱 1차 기능

- 회원가입·로그인·로그아웃
- 카테고리 지도와 목록
- 장소 상세, 이미지, 추천율, 배지, DNA
- 추천·비추천, 저장, 컬렉션
- 외부 지도 길찾기
- 리뷰어 프로필과 유사 리뷰어
- 공개 캠페인 조회
- 딥링크와 기본 푸시 알림

#### 출시 순서

1. PWA 수준의 반응형 웹·API 계약 안정화.
2. iOS·Android 공통 기능과 플랫폼별 지도·딥링크 검증.
3. 내부 배포로 로그인·지도·투표·저장 회귀 테스트.
4. 개인정보 표시, 계정 삭제, 권한 설명, 분석·크래시 리포팅 적용.
5. TestFlight와 Play Internal Testing.
6. 스토어 메타데이터·스크린샷·심사 대응 후 단계적 출시.

앱에서 일반 사용자 디지털 구독을 판매하게 되면 Apple·Google 인앱결제 정책을 별도 설계한다. B2B 맞춤형 서비스 계약과 결제는 웹 영업 흐름을 유지한다.

## 9. 오류 처리와 운영 안전성

- 사용자가 복구할 수 있는 오류는 구체적인 다음 행동을 표시한다.
- 외부 지도·주차 API 실패 시 장소 기본 정보와 길찾기 링크는 계속 제공한다.
- 점수 재계산 실패 시 마지막 정상 스냅샷과 갱신 시각을 유지한다.
- 이미지 변환 실패 시 원본을 공개하지 않고 안전한 대체 이미지를 표시한다.
- 결제 웹훅 실패는 재시도하며 같은 이벤트를 중복 처리하지 않는다.
- 예약 작업 실패, D1 오류, R2 오류, 권한 거부, 외부 API 실패를 구조화된 코드로 구분한다.
- 관리자 작업과 결제 상태 변경은 actor, reason, before, after, timestamp를 보존한다.

## 10. 테스트 전략

### 단위 테스트

- 평가 수학, 배지 조건, 리뷰어 한도, 권한 정책, 상태 전이.
- 결제 금액 계산, 웹훅 서명, idempotency, 취소·환불 조건.
- URL 필터 직렬화와 앱·웹 공통 응답 변환.

### Workers 통합 테스트

- D1 migration과 FK·unique 제약.
- 투표 이벤트와 현재 투표의 원자적 갱신.
- 역할별 mutation 허용·거부.
- R2 업로드 검증과 이미지 메타데이터.
- 주문·캠페인·감사 로그의 상태 전이.

### 웹 E2E

- 로그인 → 지도 탐색 → 상세 → 투표 변경 → 저장.
- 리뷰어 블라인드 평가 → DNA → Golden Pick 제한.
- 관리자 CSV import → 제안 승인 → 장소 공개.
- 견적 → 테스트 결제 → 웹훅 → 캠페인 공개 → 종료 리포트.

### 앱 E2E

- 설치·로그인·세션 갱신·계정 삭제.
- 지도·목록 동기화, 딥링크, 길찾기.
- 오프라인·느린 네트워크·권한 거부 상태.
- 투표·저장의 웹과 앱 간 일관성.

## 13. 범위 변경 규칙

다음 단계로 넘어가려면 현재 단계의 완료 기준과 회귀 테스트를 통과해야 한다. 일정이 부족하면 기능의 품질을 낮추기보다 다음 단계로 이동한다.

우선 연기할 항목은 고급 취향 시각화, 자동 부정행위 판정, 부분 환불, 구독, 리뷰어 정산 자동화, 앱 내 B2B 관리다. 투표 이력, 서버 권한 검사, 결제 검증, 평가·광고 분리는 연기할 수 없다.

## 14. 최종 완료 정의

Re:Taste의 장기 1차 제품은 다음 조건을 모두 만족할 때 완료로 본다.

- 광주·전남 300곳 이상을 웹과 앱에서 탐색할 수 있다.
- User·Reviewer·Admin의 핵심 작업이 서버 권한 검사와 감사 로그 아래 동작한다.
- 추천율·DNA·배지 결과를 원시 데이터와 버전에서 재현할 수 있다.
- B2B Re:Taste 상품을 견적, 결제, 수행, 공개, 리포트, 환불까지 운영할 수 있다.
- 유료 캠페인과 편집 추천이 데이터와 UI에서 명확히 분리된다.
- iOS·Android 앱이 웹과 같은 계정·장소·투표·저장 데이터를 사용한다.
- 백업·복구·관측성·법적 문서·문의 채널·스토어 심사 요건이 갖춰져 있다.
