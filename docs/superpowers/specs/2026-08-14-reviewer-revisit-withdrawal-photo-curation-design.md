## 1. 목적

리뷰어가 같은 장소에 여러 번 방문하더라도 평가 점수를 중복해서 올리지 않으면서, 실제 재방문 사실은 더 신뢰도 높은 공개 근거로 보여준다. 동시에 리뷰 철회, 사진 공개, 대표 이미지 선정과 리뷰어 프로필 표시가 서로 어긋나지 않도록 하나의 정책으로 묶는다.

이 설계가 해결하는 문제는 다음과 같다.

1. 발행 버튼 연타나 네트워크 재전송으로 리뷰가 중복 생성될 수 있다.
2. 같은 리뷰어가 같은 장소에 남긴 여러 평가가 점수에 중복 반영될 수 있다.
3. 리뷰 철회가 평가, Golden Pick, 사진, 추천 결과에 일관되게 반영될 계약이 없다.
4. 리뷰어 사진은 공개되지만 장소 대표 이미지로 사용되는 품질 기준은 없다.
5. 활성 리뷰어에게도 신청 버튼이 노출되고 계정 정보의 시각적 위치가 어색하다.

## 2. 핵심 결정

### 2.1 최초 리뷰와 재방문 확인을 분리한다

동일한 `리뷰어 × 장소` 조합에는 점수에 반영되는 **최초 리뷰**가 하나만 존재한다. 최초 발행 90일 이후의 기록은 새로운 평가 리뷰가 아니라 **재방문 확인**으로 저장한다.

| 구분 | 최초 리뷰 | 재방문 확인 |
|---|---|---|
| 생성 시점 | 해당 장소 첫 발행 | 직전 발행 또는 재방문 확인 90일 이후 |
| 점수 직접 반영 | 예, 1회 | 아니요, 가중치 0 |
| 맛 배지 | 최대 2개 | 기존 리뷰와 달라진 항목만 선택 가능 |
| 사진 | 0~5장 | 0~5장 |
| 공개 표시 | 리뷰 평가와 배지 | 재방문 확인 배지와 타임라인 |
| Golden Pick | 조건 충족 시 가능 | 새 Golden Pick 부여 안 함 |
| 철회 | 평가 반영까지 해제 | 해당 확인 기록만 공개 해제 |

재방문 확인은 기존 리뷰를 삭제하거나 대체하지 않는다. 최초 리뷰와 모든 재방문 확인은 시간순 기록으로 보존한다.

### 2.2 90일은 직전 기록 기준의 연속 쿨다운이다

- 최초 리뷰 발행일부터 90일 후 첫 재방문 확인이 가능하다.
- 이후에는 직전 재방문 확인일부터 다시 90일 후 다음 확인이 가능하다.
- 리뷰 또는 재방문 확인을 철회해도 다음 가능일은 앞당겨지지 않는다.
- 90일 계산은 UTC 시각을 원본으로 저장하고, 화면에서는 한국 시간 기준 날짜로 표시한다.

예시:

```text
2026-08-14 최초 리뷰 발행
  → 2026-11-12 첫 재방문 확인 가능

2026-11-15 재방문 확인
  → 2027-02-13 다음 재방문 확인 가능
```

### 2.3 재방문 확인은 점수가 아니라 신뢰 근거다

재방문 확인은 Wilson 점수, 리뷰어 가중치, Flavor Print 표본 수, 사용자 취향 벡터에 직접 더하지 않는다. 장소 상세에는 숫자 대신 다음과 같은 신뢰 근거를 표시한다.

- `90일 후 재방문 확인`
- `재방문 2회 확인`
- `최근 확인 2026.11`
- `기존 판단 유지`
- `변화 감지 · 재검수 중`

동일 리뷰어가 반복 방문한 횟수를 독립 표처럼 계산하면 안 된다. 표시 목적은 “한 사람이 한 번 더 확인했다”는 이력 제공이며, 평가 표본은 여전히 한 명의 한 표다.

### 2.4 판단 변화는 새 점수가 아니라 정정 신호다

재방문 화면은 다음 세 가지 상태만 제공한다.

1. `그대로예요`: 기존 판단이 유지됨을 확인한다.
2. `달라졌어요`: 새 점수는 만들지 않고 최초 리뷰를 `재검수 필요` 상태로 표시한다.
3. `장소 정보가 달라요`: 폐업, 이전, 업종 변경 등 운영 검수 대상으로 전달한다.

`달라졌어요`를 선택해도 기존 리뷰는 자동 삭제되거나 새 리뷰로 교체되지 않으며 최초 평가의 점수도 자동 중단하지 않는다. 재방문 확인은 `변화 감지 · 재검수 중`이라는 공개 배지와 운영 검수 신호만 만든다. 사용자에게 기존 리뷰 철회를 선택적으로 안내하며, 점수에서 제외되는 시점은 리뷰어가 최초 리뷰를 명시적으로 철회했을 때다. 따라서 재방문 확인은 어떤 선택에서도 점수와 표본 수를 직접·간접으로 바꾸지 않는다.

## 3. 발행 중복 방지 정책

중복 방지는 클라이언트, 요청, 데이터베이스 세 경계에서 수행한다.

### 3.1 클라이언트 경계

- `리뷰 발행` 또는 `재방문 확인` 버튼을 누르는 즉시 동기 잠금한다.
- 버튼 문구를 `발행 중…`으로 바꾸고 모든 이전·다음·사진 변경 동작을 비활성화한다.
- 응답이 성공하거나 명시적 오류로 끝난 뒤에만 잠금을 해제한다.
- 성공 후에는 입력 화면을 유지하지 않고 완료 화면으로 전환한다.

### 3.2 요청 경계

- 발행 화면 진입 시 서버가 비식별 발행 요청번호를 발급한다.
- 동일 화면에서 발생한 재전송은 같은 요청번호를 사용한다.
- 같은 요청번호가 재도착하면 새 리뷰를 만들지 않고 최초 성공 결과를 반환한다.
- 요청번호는 사용자 ID, 이메일, 장소명을 포함하지 않는다.

### 3.3 데이터베이스 경계

- `리뷰어 × 장소`의 최초 리뷰는 데이터베이스 부분 고유 인덱스로 하나만 허용한다.
- 각 재방문 확인은 직전 기록을 가리키며, 하나의 직전 기록에는 후속 확인을 하나만 허용한다.
- 동시 요청 두 개가 같은 직전 기록을 사용하면 하나만 성공한다.
- 애플리케이션 사전 조회 결과만 신뢰하지 않고 D1 제약이 최종 중복 방어선이 된다.

### 3.4 성공·충돌 UX

성공 화면:

```text
발행 완료
이번 방문의 판단이 추천에 반영됐어요.

[발행 기록 보기] [다른 장소 리뷰하기]
```

재방문 확인 성공 화면:

```text
재방문 확인 완료
점수는 늘리지 않고 최근 확인 기록으로 남겼어요.

[기록 보기] [다른 장소 확인하기]
```

이미 처리된 같은 요청은 오류 대신 기존 성공 화면으로 이동한다. 90일 이전 제출은 다음 가능일을 안내하는 `409` 응답으로 처리한다.

## 4. 실제 철회 정책

### 4.1 철회는 공개·추천 반영을 실제로 중단한다

최근 발행 목록의 `×`는 목록 숨김이 아니라 실제 철회다. 철회 후 다음 변화가 하나의 작업으로 처리된다.

- 리뷰 또는 재방문 확인 공개 중단
- 리뷰 사진 공개 중단
- 관리자 대표 사진 선정 해제
- 최초 리뷰라면 해당 리뷰가 만든 평가 이벤트 철회
- 최초 리뷰의 Golden Pick이 활성 상태라면 철회 이벤트 생성
- 장소 점수와 추천 후보 재계산 예약
- 리뷰어 신뢰도 파생값 재계산 예약
- 공개 캐시 무효화

리뷰 행과 감사 정보는 삭제하지 않고 `WITHDRAWN` 상태로 보존한다. 사진 객체는 공개 경로에서 즉시 차단하고 비동기 정리 작업이 실제 R2 삭제를 재시도한다.

### 4.2 철회가 다른 평가를 지우면 안 된다

최초 리뷰에는 해당 리뷰가 만든 투표 이벤트 ID를 저장한다. 철회 시 현재 유효 투표가 그 이벤트를 가리킬 때만 투표를 제거한다. 리뷰 발행 이후 사용자가 별도 화면에서 평가를 변경했다면 그 최신 평가는 건드리지 않는다.

### 4.3 철회 확인 UX

최근 발행 행 오른쪽에 시각적 `×` 버튼을 배치한다. 접근 가능한 이름은 `{장소명} 리뷰 철회` 또는 `{장소명} 재방문 확인 철회`로 제공하고, 최소 터치 영역은 44×44px이다.

```text
O61김밥 리뷰를 철회할까요?

평가, 맛 배지, Golden Pick과 사진이
서비스에서 내려갑니다.

다시 기록할 수 있는 날은
2026년 11월 12일로 유지됩니다.

[취소] [리뷰 철회]
```

- 기본 포커스는 `취소`에 둔다.
- `Escape`로 닫을 수 있다.
- 철회 중에는 버튼을 잠그고 `철회 중…`으로 표시한다.
- 성공 시 행을 제거하고 `리뷰를 철회했어요` 토스트를 표시한다.
- 실패 시 행을 유지하고 `철회하지 못했어요. 다시 시도해 주세요` 토스트를 표시한다.

### 4.4 재방문 확인 철회

재방문 확인 철회는 점수에 영향을 주지 않는다. 해당 확인 배지, 타임라인, 사진과 대표 사진 선정만 내려간다. 다음 재방문 가능일은 철회 전 기록 시각을 기준으로 유지한다.

## 5. 리뷰 사진 공개와 대표 이미지 큐레이션

### 5.1 하단 갤러리에는 발행 사진을 모두 공개한다

`PUBLISHED` 상태의 최초 리뷰와 재방문 확인에 포함된 모든 사진은 장소 상세 하단 `리뷰어가 남긴 사진` 갤러리에 노출한다.

- 최신 발행순, 각 기록 안에서는 사용자가 정한 순서로 표시한다.
- 사진에는 장소명과 기록 성격을 포함한 대체 텍스트를 제공한다.
- 사진 선택 시 큰 보기로 열되 리뷰어 개인정보는 노출하지 않는다.
- 철회, 관리자 공개 중단, 정지된 리뷰어 정책에 해당하는 사진은 즉시 제외한다.
- 페이지당 제한과 `더 보기`를 사용해 모든 사진을 한 번에 다운로드하지 않는다.

### 5.2 메인 대표 영역에는 관리자 선정 사진만 노출한다

리뷰어가 올린 사진이라는 이유만으로 장소 메인 이미지에 자동 노출하지 않는다. 관리자가 품질을 확인하고 선정한 사진만 기존 대표 사진과 함께 메인 이미지 슬라이드에 들어간다.

선정 기준:

- 음식 또는 장소가 선명하게 보임
- 과도한 필터, 워터마크, 타인 얼굴, 개인정보가 없음
- 장소와 실제 연관성이 확인됨
- 메인 비율로 잘랐을 때 핵심 피사체가 유지됨
- 중복 구도보다 장소를 설명하는 다양성이 있음

장소당 선정 사진은 최대 5장이다. 기존 `heroImageUrl`을 첫 이미지로 유지하고, 이후에 관리자 선정 리뷰 사진을 순서대로 배치한다. 관리자가 별도로 지정하면 선정 리뷰 사진을 첫 이미지로 승격할 수 있다.

### 5.3 슬라이드 UX

- 자동 재생하지 않는다.
- 데스크톱은 이전·다음 버튼, 모바일은 스와이프를 제공한다.
- 현재 위치를 `1 / 4`와 점 표시로 함께 제공한다.
- 키보드 좌우 화살표를 지원한다.
- 첫 이미지만 우선 로드하고 나머지는 지연 로드한다.
- `prefers-reduced-motion`에서는 전환 애니메이션을 제거한다.

### 5.4 관리자 사진 관리

관리자 화면에 장소별 사진 큐레이션 영역을 둔다.

- 리뷰 사진 모아보기
- 대표 선정·해제
- 최대 5장 제한
- 순서 변경
- 메인 비율 미리보기
- 사진 공개 중단·복구
- 선정자와 선정 시각 감사 기록
- 철회된 원본 리뷰의 선정 상태 자동 해제

`대표 미선정`과 `공개 중단`은 다른 상태다. 대표로 선정하지 않은 사진도 하단 갤러리에는 계속 공개될 수 있다.

## 6. 프로필 UX

활성 리뷰어에게는 `리뷰어 신청·상태` 버튼을 표시하지 않는다.

프로필 정보의 시각적 순서는 다음과 같다.

```text
프로필 사진 · 표시 이름

MY TASTE / PROFILE
대표 취향 문구
취향 배지

PROFILE
@reviewer-slug · account@example.com · 이메일 확인됨

TASTE LOG
내가 남긴 맛의 기록
```

- 내부 사용자 UUID는 노출하지 않는다.
- 공개 가능한 리뷰어 프로필 slug를 `@아이디`로 사용한다.
- 이메일은 본인 화면에서만 표시한다.
- 활성 리뷰어는 작은 `리뷰어` 상태 배지를 받을 수 있지만 신청 CTA는 제거한다.
- 일반 회원은 `리뷰어 신청`, 심사 중은 `리뷰어 심사 중`, 정지 상태는 작은 상태 안내를 표시한다.

## 7. 사용자 흐름 시뮬레이션

### 7.1 최초 리뷰 발행

1. 리뷰어가 장소를 선택한다.
2. 평가, 최대 2개 맛 배지, 사진, Golden Pick 여부를 선택한다.
3. 확인 화면에서 `리뷰 발행`을 누른다.
4. 버튼은 즉시 잠기고 한 요청만 전송된다.
5. 최초 리뷰와 연결 평가가 생성된다.
6. 성공 화면과 최근 발행 목록에 한 행이 나타난다.

건강 상태: 정상. 점수에 반영되는 유일한 리뷰다.

### 7.2 버튼 연타·네트워크 재전송

1. 사용자가 발행 버튼을 빠르게 두 번 누른다.
2. 클라이언트가 두 번째 동작을 막는다.
3. 프록시나 브라우저가 요청을 다시 보내더라도 같은 요청번호가 사용된다.
4. DB 고유 제약과 요청번호가 두 번째 삽입을 차단한다.
5. 사용자는 기존 성공 결과를 본다.

건강 상태: 정상. 리뷰, 사진, 투표, Golden Pick은 한 묶음만 생성된다.

### 7.3 90일 이전 재방문

1. 이미 리뷰한 장소가 목록에 보인다.
2. 장소 행에는 `11월 12일부터 재방문 확인 가능`이 표시된다.
3. 선택은 가능하지만 발행 단계는 비활성화하고 가능일을 안내한다.
4. 오래된 탭에서 제출해도 서버가 다시 차단한다.

건강 상태: 정상. 사용자가 제한 이유와 다음 행동을 알 수 있다.

### 7.4 90일 후 재방문 확인

1. 장소 행에 `재방문 확인 가능` 배지가 나타난다.
2. 사용자는 `그대로예요`, `달라졌어요`, `장소 정보가 달라요` 중 하나를 선택한다.
3. 필요한 경우 달라진 맛 배지와 사진을 추가한다.
4. 발행 후 점수는 변하지 않는다.
5. 상세 화면에는 `90일 후 재방문 확인`과 최근 확인일이 나타난다.

건강 상태: 정상. 표본을 부풀리지 않고 최신 확인 근거를 제공한다.

### 7.5 판단이 달라진 재방문

1. 리뷰어가 `달라졌어요`를 선택한다.
2. 재방문 확인 자체는 점수 0으로 저장된다.
3. 기존 최초 리뷰의 점수는 그대로 유지되고 `변화 감지 · 재검수 중` 배지가 별도로 붙는다.
4. 사용자에게 기존 리뷰 철회 선택지를 제공한다.
5. 운영자는 변화 근거와 사진을 확인할 수 있다.

건강 상태: 주의. 새 점수를 중복 추가하지 않으면서 오래된 점수의 오해를 막는다.

### 7.6 최초 리뷰 철회

1. 사용자가 최근 발행 목록의 `×`를 누른다.
2. 영향과 다음 가능일을 확인한다.
3. 철회가 완료되면 리뷰, 사진, Golden Pick과 연결 평가가 공개·추천에서 제외된다.
4. 감사 이력과 90일 기준 시각은 보존된다.

건강 상태: 정상. 사용자 의도와 서비스 반영 결과가 일치한다.

### 7.7 관리자 대표 사진 선정

1. 관리자가 장소의 발행 사진을 확인한다.
2. 품질이 좋은 사진을 최대 5장 선정하고 순서를 정한다.
3. 장소 상세 메인 영역에서 기존 대표 사진 다음에 나타난다.
4. 원본 리뷰가 철회되면 해당 사진은 즉시 대표 영역과 갤러리에서 내려간다.

건강 상태: 정상. 공개 참여와 대표 이미지 품질을 함께 유지한다.

## 8. 데이터 구조 계획

기존 적용 migration은 수정하지 않고 새 순번 migration으로 추가한다.

### 8.1 리뷰 확장

`reviewer_visit_reviews`에 다음 개념이 필요하다.

- `review_kind`: `PRIMARY | REVISIT`
- `status`: `PUBLISHED | WITHDRAWN`
- `root_review_id`: 재방문 확인이 연결되는 최초 리뷰
- `previous_review_id`: 직전 리뷰 또는 재방문 확인
- `publish_request_key`: 발행 멱등성 키
- `vote_event_id`: 최초 리뷰가 만든 투표 이벤트
- `revisit_verdict`: `UNCHANGED | CHANGED | PLACE_CHANGED`, 최초 리뷰는 null
- `review_case_id`: 변화 감지 운영 검수 건과의 선택적 연결
- `withdrawn_at`
- `withdrawal_reason`
- `withdrawal_request_key`

필수 제약:

- 최초 리뷰는 `리뷰어 × 장소`당 하나
- `publish_request_key` 고유
- 하나의 `previous_review_id`에는 후속 재방문 확인 하나
- `PRIMARY`에는 `root_review_id`, `previous_review_id`, `revisit_verdict`가 없음
- `REVISIT`에는 세 값이 모두 유효함
- `REVISIT`는 평가 이벤트와 Golden Pick을 소유하지 않음

### 8.2 사진 큐레이션

기존 사진 메타데이터와 분리된 대표 선정 구조가 필요하다.

- 사진 ID
- 장소 ID
- 선정 상태
- 대표 순서
- 선정 관리자
- 선정 시각
- 공개 중단 상태와 사유
- 마지막 수정 시각

대표 선정 행은 원본 사진과 장소가 일치할 때만 생성한다. 철회 또는 공개 중단 시 조회 계층에서 즉시 제외하고, 비동기 작업이 파생 캐시와 객체를 정리한다.

### 8.3 감사 이벤트

다음 상태 변경은 감사 로그에 남긴다.

- 리뷰 철회
- 재방문 확인 철회
- 대표 사진 선정·해제·순서 변경
- 사진 공개 중단·복구
- 판단 변화 검수 건 생성·해제

감사 로그에는 사진 원본 바이트, 이메일, 객체 키와 같은 민감값을 넣지 않는다.

## 9. 서비스 경계

기본 호출 방향은 저장소 기술 가이드라인을 따른다.

```text
React UI
  → reviewer route loader/action
    → review publication/withdrawal domain service
      → D1 + 기존 R2 photo adapter

Admin UI
  → admin photo curation action
    → photo curation domain service
      → D1 audit/state
```

- React 컴포넌트는 90일 계산이나 권한 판정을 소유하지 않는다.
- route는 인증, 역할, same-origin, 요청 크기와 입력 schema 검증을 담당한다.
- domain service는 중복 방지, 상태 전이, 평가·Golden Pick·사진 정합성을 담당한다.
- 기존 R2 binding과 정리 작업을 재사용하며 새 외부 서비스나 의존성을 추가하지 않는다.

## 10. 오류와 복구

| 실패 | 사용자 경험 | 정합성 처리 |
|---|---|---|
| 중복 발행 요청 | 기존 성공 결과 표시 | 요청번호로 기존 결과 조회 |
| 90일 이전 요청 | 가능일 안내 | 아무 상태도 변경하지 않음 |
| 사진 저장 실패 | 입력 유지, 오류 토스트 | 리뷰·평가 미생성, R2 정리 작업 유지 |
| DB 응답 유실 | 성공 여부 재확인 | 정확한 리뷰·사진 후조건 확인 |
| 철회 중 R2 실패 | 공개는 즉시 중단 | 정리 작업 재시도 |
| 점수 재계산 실패 | 철회 성공 표시 | stale 표시와 재계산 작업 유지 |
| 대표 사진 원본 철회 | 메인에서 즉시 제외 | 큐레이션 상태 자동 해제 |
| 관리자 순서 충돌 | 최신 화면 재요청 | 버전 기반 조건부 갱신 |

철회는 두 번 실행해도 같은 최종 상태가 되는 멱등 작업이어야 한다. 이미 철회된 기록의 반복 요청은 성공으로 응답한다.

## 11. 접근성·모바일 기준

- 발행, 철회, 사진 이동 등 모든 조작 대상은 최소 44×44px이다.
- 아이콘 버튼은 장소명과 동작을 포함한 접근 가능한 이름을 가진다.
- 확인 대화상자는 포커스 이동, 포커스 가두기, `Escape`, 닫은 뒤 포커스 복원을 지원한다.
- 토스트만으로 결과를 전달하지 않고 화면 내 상태 영역에도 결과를 반영한다.
- 슬라이드는 자동 재생하지 않고 키보드·스와이프·버튼을 모두 지원한다.
- 사진 순서와 현재 위치는 색상만으로 구분하지 않는다.
- 오류 시 입력, 선택 배지와 사진 미리보기를 보존한다.

## 12. 개인정보·보존·비용

- 철회된 공개 사진은 즉시 접근 차단하고 기존 정리 작업으로 실제 객체를 삭제한다.
- 리뷰·재방문 상태와 감사 로그는 운영 정합성과 악용 방지를 위해 보존하되 공개 조회에서는 제외한다.
- 구체 보존 기간과 계정 탈퇴 연계는 기존 개인정보 처리 정책과 맞춰 PR에서 확정한다.
- 대표 사진 선정은 새 R2 객체 복사를 만들지 않고 기존 사진 ID를 참조한다.
- 새 외부 공급자, Cloudflare binding, 런타임 의존성은 추가하지 않는다.
- 페이지네이션과 지연 로딩으로 R2 Class B 조회와 전송량 증가를 제한한다.

## 14. 검증 계획

### 14.1 단위 테스트

- 90일 경계 직전·정확히 경계·경계 이후
- 철회가 가능일을 앞당기지 않음
- 재방문 확인의 평가 가중치가 항상 0
- 재방문 표시 문구와 배지
- 관리자 대표 사진 최대 5장과 순서

### 14.2 Workers/D1 통합 테스트

- 동시 최초 발행 중 하나만 성공
- 동일 요청번호 재전송이 기존 결과 반환
- 동시 재방문 확인 중 하나만 성공
- 최초 리뷰 철회가 연결된 현재 투표만 제거
- 이후 변경된 사용자 투표는 보존
- Golden Pick 철회와 리뷰 상태 전이가 원자적으로 일치
- 철회된 사진 route가 즉시 404
- R2 삭제 실패 후 정리 재시도
- 재방문 확인이 rating snapshot 입력 수를 증가시키지 않음
- `CHANGED`와 `PLACE_CHANGED`도 기존 점수·표본 수를 바꾸지 않음
- 관리자 선정 사진이 철회 시 자동 제외

### 14.3 Playwright 실제 흐름

- 데스크톱·모바일 최초 리뷰 발행
- 발행 버튼 연타
- 응답 지연과 재전송
- 90일 이전 차단과 가능일 표시
- 90일 이후 재방문 확인
- 점수 불변과 신뢰 배지 표시
- 최초 리뷰·재방문 확인 철회
- 철회 실패 시 행 보존
- 관리자 대표 선정 후 메인 슬라이드 표시
- 하단 전체 사진 갤러리 표시
- 키보드만으로 철회 대화상자와 슬라이드 사용
- 활성 리뷰어 프로필에서 신청 CTA 미노출

### 14.4 레거시 데이터 감사

배포 전에 다음을 읽기 전용 보고서로 확인한다.

- 동일 리뷰어·장소의 기존 중복 리뷰 수
- 리뷰와 연결 가능한 현재 투표 이벤트 비율
- 고아 사진 메타데이터와 R2 객체
- 만료되지 않은 Golden Pick과 리뷰 연결 상태
- 철회 도입 시 자동 연결할 수 없는 레거시 행

불확실한 레거시 행은 임의로 삭제하거나 연결하지 않고 관리자 검수 대상으로 분리한다.

## 15. Rollout과 rollback

1. 읽기 전용 레거시 감사 실행
2. additive migration 적용
3. 발행 중복 방지와 90일 정책 활성화
4. 철회 기능을 내부 리뷰어 계정에 우선 활성화
5. 정합성·R2 정리 지표 확인 후 전체 리뷰어에 활성화
6. 재방문 확인과 신뢰 배지 활성화
7. 관리자 사진 큐레이션 적용 후 대표 슬라이드 활성화

문제 발생 시 새 발행·철회·큐레이션 action을 feature flag로 비활성화한다. additive schema와 기존 데이터는 유지하며, 적용된 migration을 되돌려 수정하지 않는다. 공개 조회는 기존 최초 리뷰와 기존 hero 이미지 경로로 즉시 복귀할 수 있어야 한다.

- 90일 이전 차단 수
- 멱등 재응답 수
- 리뷰·재방문 철회 성공/실패 수
- 철회 후 사진 정리 대기 수와 최장 지연
- 점수 재계산 실패 수
- 재방문 확인 수와 `CHANGED` 비율
- 대표 사진 선정 수와 철회 자동 해제 수
- 사진 route 404/503 비율

로그에는 이메일, 사용자 표시명, 장소명, 사진 객체 키를 기록하지 않는다. 내부 비식별 ID와 제한된 오류 코드만 사용한다.

## 17. 검토한 대안

### 대안 A — 최초 리뷰 + 점수 0 재방문 확인 (채택)

표본 중복 없이 최근 방문 근거를 보여주며 기존 리뷰를 보존한다. 철회와 변화 감지를 별도 상태로 다룰 수 있다.

### 대안 B — 90일마다 새 평가로 교체

최근 판단을 점수에 쉽게 반영할 수 있으나 이전 리뷰를 대체해야 하고, 동일 리뷰어가 표본에 반복 포함되거나 시간에 따라 점수가 크게 흔들릴 위험이 있다. 사용자 요청과 맞지 않아 기각한다.

### 대안 C — 모든 재방문 리뷰를 독립 평가로 누적

구현은 단순하지만 자주 방문하는 리뷰어가 점수를 과도하게 지배한다. 리뷰어 영향 최대 30%와 한 사람 한 표 원칙을 훼손하므로 기각한다.

## 18. 수용 기준

다음 조건을 모두 만족해야 구현이 완료된 것으로 본다.

1. 같은 리뷰어·장소의 최초 평가 리뷰는 하나만 생성된다.
2. 버튼 연타와 네트워크 재전송으로 중복 리뷰가 생성되지 않는다.
3. 재방문 확인은 90일 이후에만 가능하며 점수·표본 수를 바꾸지 않는다.
4. 기존 리뷰와 재방문 기록은 대체·삭제되지 않고 공개 타임라인으로 유지된다.
5. 실제 철회는 공개, 평가, Golden Pick, 사진과 추천 반영을 일관되게 중단한다.
6. 철회해도 90일 가능일이 앞당겨지지 않는다.
7. 모든 발행 사진은 하단 갤러리에 공개되고, 관리자 선정 사진만 메인 대표 영역에 노출된다.
8. 원본 리뷰 철회 시 해당 사진은 갤러리와 대표 영역에서 즉시 제외된다.
9. 활성 리뷰어에게 신청 CTA가 보이지 않고 계정 메타가 Profile과 Taste Log 사이에 표시된다.
10. 데스크톱, 모바일, 키보드, 중복 요청, 느린 네트워크와 저장소 실패 QA가 통과한다.
