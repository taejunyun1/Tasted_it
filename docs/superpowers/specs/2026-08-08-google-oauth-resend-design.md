# Google OAuth 로그인 및 Resend 환영 메일 설계

- 상태: 승인됨
- 작성일: 2026-08-08
- 담당자: taejunyun1 / Codex
- 기준 브랜치: `origin/main`

## 1. 배경

Re:Taste는 이메일·비밀번호 가입, 이메일 인증, 비밀번호 재설정, 장소 정정 확인 메일과 자체 세션을 이미 운영한다. 이번 작업은 기존 계정 체계를 유지하면서 Google 로그인을 추가하고, Google로 처음 가입한 사용자에게 Resend 환영 메일을 보내는 것이 목적이다.

## 2. 목표

- Google OAuth 2.0 서버 인증 흐름을 Cloudflare Workers에서 제공한다.
- Google이 인증한 동일 이메일의 기존 계정은 안전하게 자동 연결한다.
- Google 신규 사용자는 비밀번호 없이 계정을 만들고 기존 Re:Taste 세션을 사용한다.
- 로그인·회원가입 화면에서 같은 `Google로 계속하기` 흐름을 제공한다.
- 신규 Google 회원에게 Resend 환영 메일을 발송한다.
- 기존 이메일 인증·비밀번호 재설정·장소 정정 메일 흐름은 그대로 유지한다.

## 3. 범위 밖

- Google 외 SNS 제공자
- Google API의 연락처·캘린더 등 추가 권한
- Google 액세스 토큰 또는 갱신 토큰 저장
- 기존 사용자에게 계정 연결을 해제하는 설정 화면
- Google 신규 사용자의 이메일 재인증

## 4. 선택한 방식

서버 기반 승인 코드(Authorization Code) 방식과 OpenID Connect를 사용한다. 브라우저 팝업이나 클라이언트 SDK에 인증 책임을 두지 않고, Worker가 코드 교환과 ID 토큰 검증을 수행한다.

ID 토큰 서명은 Google의 공개 키(JWKS)와 검증 라이브러리로 확인한다. 토큰 정보 확인용 네트워크 API에 매 로그인마다 의존하거나 JWT 검증을 직접 구현하지 않는다.

## 5. 사용자 흐름

### 5.1 로그인 시작

1. 사용자가 로그인 또는 회원가입 화면에서 `Google로 계속하기`를 누른다.
2. `/auth/google`은 `state`와 `nonce`를 암호학적으로 안전한 난수로 생성한다.
3. `state`, `nonce`, 검증된 `returnTo`, 만료 시각을 10분짜리 서버 DB 요청으로 저장하고, 브라우저에는 요청을 찾는 임의 식별자만 HttpOnly 쿠키로 저장한다.
4. Google 승인 화면으로 이동한다. 요청 범위는 `openid email profile`만 사용한다.

### 5.2 콜백 검증

1. `/auth/google/callback`은 오류 응답, 승인 코드, `state`를 확인한다.
2. 쿠키가 가리키는 서버 요청의 `state`와 콜백의 `state`를 상수 시간 비교하고, 일치하지 않거나 만료·사용된 요청은 거절한다.
3. 승인 코드를 Google 토큰 엔드포인트에서 교환한다.
4. ID 토큰의 서명, `iss`, `aud`, `exp`, `iat`, `nonce`, `email`, `email_verified`, `sub`를 검증한다.
5. `email_verified=true`가 아니면 로그인과 계정 연결을 모두 거절한다.
6. 승인 코드를 교환하기 전에 요청을 사용 처리하여 같은 콜백의 재전송을 막는다.
7. OAuth 임시 쿠키는 성공·실패와 관계없이 만료시킨다.

### 5.3 계정 결정

1. `provider=GOOGLE`, `provider_subject=sub` 연결이 있으면 해당 사용자를 로그인시킨다.
2. 연결이 없고 같은 소문자 이메일의 기존 사용자가 있으면 그 사용자에게 Google 연결을 추가한다.
3. 기존 사용자의 표시 이름, 역할, 비밀번호는 변경하지 않는다. 이메일 인증일이 비어 있으면 Google의 검증 시각으로 채우고, 기존 값이 있으면 유지한다.
4. 기존 사용자가 없으면 비밀번호 해시·소금이 `NULL`인 새 사용자를 만든다.
5. 신규 사용자의 이메일 인증일은 Google 검증 시각으로 기록한다.
6. 신규 사용자 이메일이 `ADMIN_EMAIL`과 같으면 기존 가입 정책과 동일하게 관리자 역할을 부여한다.
7. 연결·사용자 생성 경합은 고유 제약 조건으로 막고, 충돌 시 다시 조회하여 하나의 계정만 사용한다.

### 5.4 세션과 복귀

기존 `sessions` 테이블과 `retaste_session` 쿠키를 그대로 사용한다. 기존 제품 정책을 유지해 로그인 완료 후에는 전달된 경로와 관계없이 회원 메인 지도 `/`로 이동한다.

## 6. 데이터 모델

새 migration에서 `auth_identities`와 `oauth_requests`를 추가한다.

| 필드 | 설명 |
| --- | --- |
| `id` | 내부 UUID 기본 키 |
| `user_id` | `users.id` 외래 키, 사용자 삭제 시 함께 삭제 |
| `provider` | 현재는 `GOOGLE` |
| `provider_subject` | Google의 불변 사용자 식별자 `sub` |
| `provider_email` | 연결 당시 정규화한 이메일 |
| `created_at` | 생성 시각 |
| `updated_at` | 갱신 시각 |

고유 제약은 `(provider, provider_subject)`와 `(provider, user_id)`에 둔다. 이메일은 계정 식별의 최종 키가 아니므로 identity 테이블의 고유 키로 사용하지 않는다.

기존 `users.password_hash`와 `users.password_salt`는 이미 nullable이므로 users 테이블 재작성은 필요하지 않다.

`oauth_requests`는 임시 서버 상태를 보관한다.

| 필드 | 설명 |
| --- | --- |
| `id` | 브라우저 HttpOnly 쿠키가 가리키는 임의 식별자 |
| `state_hash` | 콜백 위조 방지 값의 해시 |
| `nonce` | ID 토큰 재사용 방지 값 |
| `return_to` | 검증된 내부 복귀 경로 |
| `expires_at` | 10분 만료 시각 |
| `consumed_at` | 최초 콜백 사용 시각 |
| `created_at` | 생성 시각 |

원문 `state`는 DB에 저장하지 않고 SHA-256 해시만 저장한다. 만료된 요청은 로그인 시작 시 소량 정리한다.

## 7. 보안

- Google 클라이언트 보안 비밀번호는 Cloudflare secret으로만 관리한다.
- 승인된 리디렉션 URI는 로컬과 운영 콜백 주소만 허용한다.
- OAuth 쿠키는 임의 요청 식별자만 담고 `HttpOnly`, `SameSite=Lax`, 운영 HTTPS에서 `Secure`, `Max-Age=600`을 사용한다.
- 외부에서 받은 `returnTo`, 이메일, 표시 이름을 그대로 신뢰하지 않는다.
- `sub`를 Google 계정의 불변 식별자로 사용한다.
- 로그에 승인 코드, 토큰, secret, 전체 OAuth 쿠키를 남기지 않는다.
- 오류 화면은 내부 응답이나 개인정보를 노출하지 않는 제한된 오류 코드만 표시한다.

## 8. 환경 변수

| 이름 | 용도 | 관리 방식 |
| --- | --- | --- |
| `GOOGLE_CLIENT_ID` | ID 토큰 audience 및 승인 요청 | Cloudflare secret |
| `GOOGLE_CLIENT_SECRET` | 승인 코드 교환 | Cloudflare secret |
| `ADMIN_EMAIL` | 신규 계정 관리자 판정 | 기존 secret |
| `RESEND_API_KEY` | 환영·계정 메일 발송 | 기존 secret |
| `RESEND_FROM_EMAIL` | 인증된 발신 주소 | 기존 secret |
| `APP_BASE_URL` | 운영 기준 URL | 기존 환경값 또는 secret |

## 9. Resend 정책

Google 신규 계정에만 환영 메일을 한 번 보낸다. 기존 계정 자동 연결이나 반복 로그인에는 보내지 않는다. Google이 이미 이메일을 검증했으므로 인증 링크는 포함하지 않는다.

메일 발송 실패는 인증 성공을 되돌리지 않는다. 실패는 비밀값과 개인정보를 제외한 운영 로그로 남기고 사용자는 정상 로그인시킨다. 이메일 단위 테스트는 fetch 모의 객체를 사용하며, 운영 발송 확인은 배포 후 지정 테스트 계정 1회로 제한한다.

## 10. 화면 설계

- 로그인과 회원가입의 주요 입력 영역 위에 `Google로 계속하기` 버튼을 둔다.
- 버튼 아래에 `또는 이메일로 계속하기` 구분선을 둔다.
- Google 버튼은 키보드 포커스와 명확한 접근성 이름을 제공한다.
- OAuth 오류가 돌아오면 로그인 화면 상단에 재시도 가능한 한국어 안내를 표시한다.
- 기존 Re:Taste 색상, 타이포그래피, 모바일 폭을 유지한다.

## 11. 오류 처리

- 사용자가 동의를 취소한 경우: `Google 로그인이 취소되었습니다.`
- 요청 상태가 없거나 불일치한 경우: 새 로그인 시도를 안내한다.
- 토큰 교환 또는 검증 실패: 일반적인 로그인 실패 안내와 운영 로그를 남긴다.
- 이메일이 검증되지 않은 경우: 검증된 Google 계정을 사용하도록 안내한다.
- DB 고유 제약 충돌: identity를 다시 조회해 정상 로그인하거나, 관계가 모순되면 안전하게 실패한다.

## 12. 테스트 전략

- 단위 테스트: 승인 URL, `state`/`nonce`, 콜백 오류 매핑, ID 토큰 검증 입력, 계정 연결 결정, 환영 메일 내용·1회 발송
- 통합 테스트: 신규 Google 사용자, 기존 이메일 자동 연결, 반복 로그인, 미검증 이메일 거절, 중복 콜백 경합, 세션 생성
- 회귀 테스트: 이메일·비밀번호 로그인, 이메일 인증, 비밀번호 재설정, 관리자 역할
- 화면 검증: 데스크톱과 모바일에서 로그인·회원가입 버튼, 오류 상태, 키보드 포커스
- 외부 호출은 테스트에서 모두 모의 처리한다.

## 13. 배포와 롤백

1. 기능 브랜치에서 새 migration과 코드를 검증한다.
2. PR에 데스크톱·모바일 증거, 테스트 결과, 환경 변수와 migration 영향을 기록한다.
3. 사람 승인과 필수 검사를 받은 뒤 squash merge한다.
4. 병합된 `main`에서 원격 D1 migration을 적용한다.
5. Worker를 배포하고 Google 로그인과 환영 메일을 지정 계정으로 1회 확인한다.

문제 발생 시 Google 버튼과 OAuth 시작 경로를 비활성화한 이전 Worker 버전으로 롤백한다. `auth_identities`는 기존 인증 흐름에 영향을 주지 않으므로 즉시 삭제하지 않는다.
