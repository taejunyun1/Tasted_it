# Re:Taste 프로필 취향 배지·벡터 설계

## 1. 목표

프로필의 첫 질문을 `어디에 연결되어 있는가`에서 `무엇을 좋아해 먹으러 다니는가`로 바꾼다. 사용자가 프로필에 진입하면 닉네임, 대표 취향 문구, FOOD/TASTE/STYLE 배지 순서로 취향을 읽고, 저장·평가 기록을 확인한 뒤 마지막에 외부 계정 연결 상태를 본다.

## 2. 정보 구조

1. 프로필 이니셜 아바타와 닉네임
2. 상위 취향을 조합한 대표 자연어 문구
3. FOOD/TASTE/STYLE 대표 취향 배지
4. 취향 근거가 부족할 때의 학습 진행도
5. 저장·평가 활동 기록
6. 최하단 네이버·Google 연결 상태 소형 배지

외부 연결은 별도의 큰 카드·제목·행동 버튼을 만들지 않는다. 이번 작업은 상태 표현만 다루며 Google 연결/해제 흐름 추가는 별도 계정 작업으로 남긴다.

## 3. 데이터 모델

### taste_badges

- `id`: 안정적인 영문 식별자
- `category`: `FOOD | TASTE | STYLE`
- `label`: 사용자에게 보이는 한글 배지명
- `headline_noun`: 대표 문장에 사용할 자연어 명사
- `sort_order`: 동점일 때의 안정적인 순서
- `is_active`: 운영 노출 여부

### user_taste_badges

- `user_id`
- `badge_id`
- `source`: `USER | NAVER | GOOGLE | INFERRED`
- `score`: `0.0 ~ 1.0`
- `evidence_json`: 점수 근거를 기록하는 JSON
- `created_at`, `updated_at`

한 사용자가 같은 배지를 여러 출처에서 가질 수 있으므로 기본키는 `user_id + badge_id + source`다. 프로필에서는 출처별 점수를 합성하고, 추천 시스템은 같은 서비스 함수를 취향 벡터 입력으로 재사용한다.

## 4. 현재 단계의 점수 생성

- `USER`: 사용자가 직접 고른 저장 점수. 가장 높은 신뢰 가중치를 가진다.
- `NAVER`, `GOOGLE`: 향후 사용자가 명시적으로 제공한 외부 취향 데이터를 저장할 자리다. 단순 로그인 연결만으로 점수를 만들지 않는다.
- `INFERRED`: Re:Taste 안의 추천 평가, 저장 장소, 음식 카테고리, 장소명, Flavor Print에서 계산한다.

추천 평가는 저장보다 강한 근거다. 비추천 평가는 좋아하는 취향 근거로 사용하지 않는다. 적은 활동으로 지나치게 확정적인 배지를 만들지 않도록 포화 곡선을 사용하고 점수는 항상 `0~1`로 제한한다.

## 5. 배지 선정과 문구

- 대표 영역은 합성 점수가 높은 순서로 최대 7개를 노출한다.
- FOOD, TASTE, STYLE 중 데이터가 존재하는 그룹을 고르게 보여주되 억지로 빈 그룹을 채우지 않는다.
- 대표 문구는 상위 FOOD 두 개, 또는 FOOD 한 개와 STYLE 한 개를 우선 조합한다.
- 데이터가 부족하면 `OO님의 취향을 알아가는 중`을 사용한다.
- 한국어 받침에 맞춰 `과/와`, `을/를`을 계산해 자연스러운 문장을 만든다.

## 6. 시각 체계

- FOOD: 크림 바탕과 짙은 녹색 테두리
- TASTE: 옅은 미스트 바탕과 녹색 텍스트
- STYLE: 흰 바탕과 점선 또는 얇은 테두리
- 최상위 대표 배지 하나만 라임 포인트를 사용한다.
- 모두 캡슐형이지만 테두리, 채움, 크기와 자간을 미세하게 달리해 단조로움을 줄인다.
- 외부 연결 상태는 회색에 가까운 작은 상태 배지로 처리한다.

## 7. 안전성과 확장

- GET 요청에서 데이터베이스를 갱신하지 않는다.
- 프로필 조회 시 저장된 출처별 신호와 현재 활동 기반 추론을 읽어 합성한다.
- 외부 계정 연결 여부와 외부 취향 데이터 동의는 구분한다.
- 추천 알고리즘에 실제 반영하는 작업은 이번 범위 밖이지만 반환 타입은 그대로 사용자 취향 벡터로 사용할 수 있게 유지한다.
