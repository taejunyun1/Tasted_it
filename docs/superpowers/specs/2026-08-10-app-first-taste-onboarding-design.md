# 앱 우선 취향 온보딩 및 추천 피드백 루프 설계

## 1. 문서 목적

Re:Taste 신규 사용자가 회원가입 전에 자신의 음식 취향을 가볍게 선택하고, 선택 직후 개인화 추천을 체험하도록 한다. 추천 결과를 저장하거나 평가하려는 시점에 로그인을 안내하고, 비회원 상태에서 만든 취향과 행동 기록은 로그인 후 계정에 안전하게 합친다.

이 설계의 중심은 가입 절차가 아니라 “내 취향을 고르면 추천이 바로 달라진다”는 경험이다. 웹, 모바일 웹, 향후 네이티브 앱이 동일한 데이터 계약과 추천 로직을 사용하도록 화면과 서버 책임을 분리한다.

## 2. 목표와 제외 범위

### 목표

- 가입하지 않은 사용자도 취향 선택과 추천 결과 확인까지 완료할 수 있다.
- 음식 취향 5개와 식당 스타일 최대 3개를 권장하되 모든 단계는 건너뛸 수 있다.
- 직접 선택한 취향과 이후 행동으로 학습한 취향을 분리해 관리한다.
- 저장, 긍정 반응, 부정 반응을 추천 개선에 사용할 수 있다.
- 개인화가 지나치게 강화되지 않도록 기존 개인화 영향 상한과 새로운 취향 노출 원칙을 유지한다.
- 모바일·앱에서는 전체 화면, 데스크톱 웹에서는 중앙 카드로 표현하되 같은 상태 흐름을 공유한다.

### 제외 범위

- 네이티브 앱 패키징과 앱스토어 배포
- 실시간 대규모 기계학습 모델
- 리뷰 임베딩 또는 대형 언어 모델을 이용한 실시간 취향 추론
- 외부 광고·트렌드 데이터 결합
- 온보딩과 무관한 프로필·관리자 화면 개편

## 3. 채택한 접근 방식

### 비회원 체험 우선형

다음 흐름을 채택한다.

1. 앱 또는 웹 첫 진입
2. 위치 사용 여부 선택
3. 음식 취향 5개 선택 권장
4. 식당 스타일 최대 3개 선택 권장
5. 선택 결과를 반영한 추천 장소 8곳 미리보기
6. 장소 저장, 평가 또는 코스 만들기 시 로그인 안내
7. 로그인 성공 후 비회원 취향과 행동을 회원 계정에 한 번만 병합

가입을 먼저 요구하는 방식은 데이터 보존이 단순하지만 첫 진입 이탈 위험이 크다. 아무 질문 없이 자동 추천하는 방식은 진입 속도는 빠르지만 개인화 체감이 약하다. 비회원 체험 우선형은 초기 전환 부담을 낮추면서 Re:Taste의 추천 가치를 가장 빨리 보여준다.

## 4. 사용자 경험

### 4.1 공통 원칙

- 각 단계 상단에 진행 상태와 선택 개수를 표시한다.
- 드롭다운 대신 켜고 끌 수 있는 큰 배지 버튼을 사용한다.
- 권장 개수를 채우지 않아도 다음 단계로 이동할 수 있다.
- 모든 단계에 `나중에 할게요`를 제공한다.
- 선택 즉시 다음 단계로 강제 이동하지 않는다. 사용자가 선택을 확인한 뒤 계속 버튼을 누른다.
- 온보딩 완료 후 `/places` 상단에 `오늘의 취향` 요약 배지를 표시하고 수정할 수 있게 한다.
- 프로필에서 사용하는 FOOD, TASTE, STYLE 배지 체계와 같은 식별자를 사용한다.

### 4.2 단계별 화면

#### 1단계: 위치 사용

- 주 동작: `내 위치 사용`
- 보조 동작: `광주시청 기준으로 둘러보기`
- 위치 권한 거부 또는 확인 실패 시 광주시청을 기본 좌표로 사용한다.
- 권한은 이 단계에서 한 번만 요청하고, 거부한 사용자를 반복해서 방해하지 않는다.

#### 2단계: 음식 취향

- FOOD 계열 배지를 전체 메뉴판 형태로 표시한다.
- 5개 선택을 권장하지만 0개부터 5개까지 허용한다.
- 선택 개수는 `2/5 선택`처럼 고정 영역에 표시한다.
- 검색이나 접기 기능은 초기 범위에 넣지 않고, 사용 빈도가 높은 카테고리를 먼저 배치한다.

#### 3단계: 식당 스타일

- STYLE 및 일부 TASTE 계열 배지를 표시한다.
- 최대 3개까지 선택할 수 있다.
- 네 번째 배지를 누르면 기존 선택을 임의 해제하지 않고 최대 선택 안내를 보여준다.

#### 4단계: 추천 결과 미리보기

- 추천 장소 8곳을 표시한다.
- 추천 이유는 실제 점수 근거에서 최대 두 개만 노출한다.
- `추천 다시 받기`와 `취향 수정`을 제공한다.
- 둘러보기와 상세 보기는 비회원도 가능하다.
- 저장, 평가, 코스 생성은 로그인 전환 지점으로 사용한다.

### 4.3 화면 형태

- 모바일 웹과 앱: 안전 영역을 고려한 전체 화면 단계 전환
- 데스크톱 웹: 배경 위 중앙 카드, 최대 너비 제한
- 공통: 동일한 단계 상태 머신과 폼 데이터 계약 사용
- 앱 전환 시 웹뷰에 종속된 저장 방식 대신 앱 저장소 어댑터를 붙일 수 있도록 임시 저장 인터페이스를 분리

## 5. 상태와 데이터 구조

### 5.1 비회원 세션

비회원 상태는 서버가 발급한 무작위 `guest_session_id`로 식별한다. 원본 위치 좌표나 브라우저 지문을 식별자로 사용하지 않는다. 브라우저에서는 보안 쿠키와 필요한 최소 화면 상태를 사용하고, 앱에서는 동일한 식별자를 보안 저장소에 보관할 수 있게 한다.

비회원 세션 데이터의 기본 구조는 다음과 같다.

```ts
type GuestTasteSession = {
  id: string;
  onboardingVersion: number;
  locationMode: "DEVICE" | "DEFAULT";
  foodTasteIds: string[];
  styleTasteIds: string[];
  completedSteps: string[];
  completedAt: string | null;
  mergedUserId: string | null;
  expiresAt: string;
};
```

진행 중인 비회원 세션은 유효한 온보딩 읽기·저장 활동마다 만료 시각과 쿠키를 활동 시각 기준 30일 뒤로 갱신한다. 완료·건너뛰기 세션은 마지막 완료·건너뛰기 시각 기준 30일 뒤로 한 번 고정하고 이후 추천 조회로 연장하지 않으며, 병합 세션도 연장하지 않는다. 매일 예약 작업이 만료 세션을 삭제하고 `guest_taste_badges`는 외래 키 cascade로 함께 삭제한다.

기기 위치는 위도·경도를 소수점 셋째 자리(약 100m)로 반올림한 뒤에만 중심점과 bbox로 사용한다. 반올림 값도 브라우저 `sessionStorage`와 현재 추천 요청 URL에만 단기 보관하며 취향 세션 D1 속성이나 제품 이벤트에는 저장하지 않는다. URL query는 브라우저 기록과 Worker 접근 로그 표면에 남을 수 있으므로 개인정보 데이터 인벤토리에 별도 공개한다.

### 5.2 취향 신호

기존 취향 배지 구조를 유지하고 신호의 출처와 강도를 구분한다.

```ts
type TasteSignal = {
  category: "FOOD" | "TASTE" | "STYLE";
  tasteId: string;
  score: number;
  source: "USER" | "NAVER" | "GOOGLE" | "INFERRED";
  evidenceCount: number;
  updatedAt: string;
};
```

- 온보딩에서 직접 선택한 항목은 `USER` 출처다.
- 저장, 상세 보기, 긍정·부정 반응으로 갱신한 항목은 `INFERRED` 출처다.
- 외부 계정 연결에서 가져온 정보는 별도의 `NAVER`, `GOOGLE` 출처로 유지한다.
- 서로 다른 출처를 한 행으로 덮어쓰지 않고 추천 단계에서 결합한다.
- 추천 입력에서는 저장 점수를 `0..1`로 정규화한 뒤 출처 신뢰도(`USER 1.0`, `NAVER/GOOGLE 0.9`, `INFERRED 0.75`)를 곱한다. 현재 비회원 세션에서 직접 선택한 배지 ID는 `USER`, 점수 `1.0`으로 해석한다.
- 정규화 점수가 `0`인 추론 신호는 familiar 가산점을 만들지 않으며, 부분 점수는 개인화 기여도를 비례 축소한다. 방향 보정까지 합친 개인화 기여도는 항상 유한한 수이고 `0.35` 이하로 제한한다.

### 5.3 피드백 이벤트

추천 피드백은 다음 세 가지를 기본 동작으로 사용한다.

- `SAVE`: 다시 보고 싶은 장소
- `LIKE`: 내 취향에 맞는 장소
- `DISLIKE`: 추천에서 덜 보고 싶은 장소

부정 반응의 선택 이유는 `MENU`, `DISTANCE`, `PRICE`, `ATMOSPHERE`, `ALREADY_VISITED`로 제한한다. 한 번의 부정 반응만으로 취향 점수를 제거하지 않고, 반복된 증거가 쌓일 때 점진적으로 낮춘다.

같은 사용자 또는 비회원 세션이 같은 장소에 같은 반응을 반복하면 최신 상태만 유효하게 처리한다. 이벤트 이력은 분석을 위해 보존할 수 있지만 추천 점수에는 중복 가중치를 주지 않는다.

## 6. 추천 점수와 학습

### 6.1 초기 추천 구성

온보딩 직후 추천의 개념적 구성은 다음과 같다.

- 직접 선택 취향 신호 45%
- 거리와 시간대 20%
- 평가 신뢰도 20%
- 새로운 취향 탐색 15%

이 비율은 초기 신호를 설명하기 위한 내부 구성이다. 최종 장소 점수에서는 기존 정책대로 개인 취향의 총 영향력을 35% 이하로 제한한다. 직접 선택 신호가 강해도 평가 신뢰도가 낮은 장소가 상위로 급상승하지 않게 품질 하한을 먼저 적용한다.

### 6.2 행동이 쌓인 이후

- 초기에는 직접 선택 신호를 우선한다.
- 저장과 긍정 반응이 누적되면 실제 행동 신호의 비중을 점진적으로 높인다.
- 상세 보기만으로 강한 취향으로 확정하지 않는다.
- 부정 반응은 1회당 작은 감점만 적용하고 반복 증거가 있을 때 감점을 키운다.
- 오래된 행동은 완전히 삭제하지 않고 시간 감쇠를 적용한다.
- 사용자가 프로필에서 직접 수정한 취향은 추론 신호보다 우선한다.

### 6.3 다양성 보장

- 추천 8곳 중 새로운 취향 후보를 최소 2곳 유지한다.
- 동일 대표 음식 카테고리는 최대 3곳으로 제한한다.
- 동일 동네는 최대 2곳으로 제한한다.
- 직접 선택과 하나도 관련 없는 후보는 새로운 취향 슬롯에서만 노출한다.
- 후보 부족 시 취향 인접 그래프를 사용해 자연스럽게 확장한다.

## 7. 회원 전환과 병합

### 7.1 로그인 유도 시점

다음 동작을 실행할 때 로그인 안내를 표시한다.

- 장소 저장
- 긍정 또는 부정 평가 확정
- 코스 저장 또는 공유
- 여러 기기에서 취향 동기화

로그인 안내를 닫아도 현재 추천 결과와 비회원 취향은 유지한다.

### 7.2 병합 규칙

- 로그인 성공 시 `guest_session_id`와 회원 ID를 서버에서 연결한다.
- 병합은 트랜잭션 안에서 한 번만 실행한다.
- 이미 `mergedUserId`가 설정된 세션은 다시 병합하지 않는다.
- 같은 취향이 회원 계정에 있으면 직접 선택 신호를 우선하되 점수를 단순 합산해 1을 초과시키지 않는다.
- 같은 장소의 저장·평가가 이미 있으면 회원의 최신 상태를 유지하고 중복 행을 만들지 않는다.
- 병합 성공 후 비회원 쿠키의 쓰기 권한을 종료하고 회원 세션만 사용한다.
- 로그인 실패 시 비회원 데이터와 현재 화면을 그대로 유지하고 로그인만 재시도할 수 있게 한다.

## 8. 구성 요소와 책임

### 온보딩 화면 계층

- 단계 전환과 선택 상태 표현
- 접근성 상태, 최대 선택 안내, 건너뛰기 처리
- 서버가 제공한 배지 목록과 문구 렌더링

### 온보딩 세션 서비스

- 비회원 세션 발급, 만료, 단계별 저장
- 회원 전환 시 중복 없는 병합
- 브라우저·앱 저장소가 같은 계약을 쓰도록 세션 인터페이스 제공

### 취향 카탈로그 서비스

- FOOD, TASTE, STYLE 배지 목록과 표시 순서 제공
- 화면 문구와 내부 식별자를 분리
- 프로필과 추천 화면에서 같은 식별자 사용

### 추천 서비스

- 기존 장소 품질 점수와 취향 벡터 재사용
- 온보딩 선택, 거리, 시간대, 평가 신뢰도, 탐색 슬롯을 가볍게 재랭킹
- 추천 이유를 실제 점수 근거에서 생성

### 피드백 서비스

- 저장·긍정·부정 상태의 중복 방지
- 추천 학습용 증거 누적
- 분석 이벤트와 추천 상태 변경을 구분

각 구성 요소는 명시적인 입력과 출력 타입을 가지며 화면이 데이터베이스에 직접 접근하지 않게 한다.

## 9. 오류 및 복구

- 위치 권한 거부: 광주시청 기준으로 추천하고 설정에서 다시 요청 가능
- 위치 확인 지연: 기본 좌표로 먼저 결과를 제공하고 위치가 확인되면 사용자가 갱신 선택
- 중간 종료: 완료한 단계와 선택 상태를 비회원 세션에 저장하고 재진입 시 복원
- 네트워크 실패: 현재 선택을 화면에 유지하고 동일 요청을 재시도
- 로그인 실패: 추천 결과와 비회원 데이터 유지
- 병합 중 실패: 트랜잭션 롤백 후 비회원 세션을 유지하고 재시도
- 추천 후보 부족: 인접 취향, 거리 반경 순서로 확장하고 품질 하한은 유지
- 세션 만료: 새 세션을 만들고 사용자에게 다시 선택할 수 있는 짧은 안내 제공

## 10. 측정 기준

개인정보를 과도하게 수집하지 않고 다음 제품 이벤트를 기록한다.

- 온보딩 시작, 단계 완료, 전체 완료, 건너뛰기
- 단계별 이탈
- 선택한 음식 취향 및 스타일의 개수
- 추천 장소 상세 보기
- 저장, 긍정, 부정 반응
- 비회원에서 회원으로 전환
- 추천 결과 중 새로운 취향 장소의 선택

이벤트에는 이메일, 이름, 원본 위치 좌표를 포함하지 않는다.

추천 상세 provenance는 client와 server가 같은 공개 query 계약(`sourceRail`, `discoveryMode`, `recommendationRequestId` 각 1개)으로 검증한다. 알 수 없는 키와 중복 키는 거절한다. React Router의 상세 data 요청에서만 정확한 `.data` suffix와 단일 `_routes=routes/place-detail` 전송 마커를 먼저 제거하며, 나머지 공개 query는 같은 엄격 검증을 그대로 통과해야 한다.

제품 이벤트의 보유 기간은 발생 후 30일이다. 초기 출시 판단은 배포 직후와 24시간 지표를 중심으로 하고 월 단위 단기 비교까지만 필요하므로, 분석 목적을 충족하는 가장 짧은 운영 기간으로 30일을 선택한다. 매일 예약 작업이 30일 경계에 도달한 이벤트를 삭제한다.

초기 성공 기준은 다음과 같다.

- 온보딩에서 하나 이상의 취향을 선택한 사용자 비율 60% 이상
- 추천 결과 상세 보기 비율 25% 이상
- 추천 장소 저장 또는 긍정 반응 비율 10% 이상
- 추천 8곳 중 새로운 취향 노출 최소 2곳 유지
- 로그인 실패와 재접속 후에도 비회원 선택 데이터 복원
- 동일 장소 반복 반응으로 추천 가중치를 중복 획득하지 않음

## 11. 접근성과 앱 확장

- 모든 선택 배지는 버튼 요소와 `aria-pressed` 상태를 사용한다.
- 현재 단계와 오류 안내는 보조 기술에 전달한다.
- 색상만으로 선택 상태를 표현하지 않는다.
- 모바일 터치 영역은 최소 44px을 확보한다.
- 앱의 뒤로 가기 동작은 이전 온보딩 단계로 이동하고 첫 단계에서는 종료 확인 없이 서비스 첫 화면으로 돌아간다.
- 화면 상태와 데이터 저장 로직을 분리해 React Native 또는 네이티브 화면에서도 같은 서버 계약을 사용할 수 있게 한다.
- 위치, 쿠키, 앱 보안 저장소는 어댑터 경계 뒤에 둔다.

- 음식 취향 최대 5개, 스타일 최대 3개 제한

- 개인화 영향력 35% 상한
- 새로운 취향 2곳 이상과 카테고리·동네 다양성 제한
- 중복 피드백의 최신 상태 처리
- 회원 전환 병합의 멱등성

- 비회원 세션 생성과 단계별 복원
- 위치 거부 후 기본 좌표 추천
- 온보딩 완료 후 추천 요청
- 로그인 성공 후 취향·저장·평가 병합

- 중간 종료 후 재진입 복원
- 취향 0개와 최대 개수 선택

- 키보드와 화면 읽기 도구를 통한 배지 선택

## 13. 출시 순서

1. 비회원 세션과 취향 카탈로그 계약
2. 모바일 우선 온보딩 화면과 로컬 복원
3. 기존 추천 서비스와 온보딩 선택 연결
4. 저장·긍정·부정 피드백
5. 회원 전환 병합
6. 제품 이벤트와 운영 관찰
7. 제한된 베타 사용자에게 공개 후 성공 기준 검토

기능 플래그를 사용해 기존 사용자에게는 현재 흐름을 유지하고 신규 세션부터 점진적으로 노출한다. 문제가 발생하면 온보딩만 끄고 기존 `/places` 추천 화면으로 복귀할 수 있어야 한다. 비활성 상태에서는 loader뿐 아니라 stale form과 직접 action POST도 세션·배지·이벤트·쿠키를 만들거나 수정하지 않고 canonical 공개 경로로 복귀한다. 온보딩 `returnTo` 공개 allowlist는 raw pathname이 정확히 `/places` 또는 React Router resource pathname `/places.data`인 경우만 허용하며, 결과 pathname은 항상 `/places`로 canonicalize한다. `bbox`, `category`, `q`, `badge`만 보존하고 온보딩 자기 경로, 관리·인증·로그아웃, 알 수 없는 경로, 외부·protocol-relative, backslash, dot-segment, 중첩 인코딩 입력은 모두 `/places`로 fallback한다.

## 14. 결정 사항 요약

- 비회원이 추천 결과까지 먼저 경험한다.
- 취향 선택은 권장형이며 모든 단계를 건너뛸 수 있다.
- 음식 취향 5개, 식당 스타일 최대 3개를 기준으로 한다.
- 저장·평가·코스 생성 시 로그인을 유도한다.
- 비회원 취향과 행동은 로그인 성공 후 한 번만 병합한다.
- 개인화 영향은 최대 35%로 제한하고 추천 8곳 중 새로운 취향을 최소 2곳 유지한다.
- 앱 우선 전체 화면 흐름을 기준으로 하되 웹과 동일한 상태·서버 계약을 공유한다.
