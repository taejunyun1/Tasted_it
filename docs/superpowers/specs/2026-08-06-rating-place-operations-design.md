# Re:Taste 평가 신뢰도·장소 운영 고도화 설계

작성일: 2026-08-06  
상태: 구현 기준 확정  
적용 범위: 평가 엔진, 장소 제안·정정·병합·폐업 재검증, AI 분류, 관리자 운영 도구

## 1. 목표와 릴리스 단위

이번 작업은 세 릴리스로 나눈다.

1. **평가 기반:** 8표 공개 기준, 역할별 집계, 리뷰어 신뢰도·유사도 감쇠, 버전·스냅샷·배지·Flavor Print, 조작 검토 사건.
2. **장소 운영:** 사용자 장소 제안, 업체 정정·이의 제기, 중복 병합, 폐업 재검증, 장소 변경 이력과 복원.
3. **AI·운영 자동화:** Cloudflare Workers AI 보조 분류, 동기화 실패 알림, 처리량·오류·누락 대시보드.

각 릴리스는 독립 migration, 단위·D1 통합·E2E 테스트, feature branch, PR, 운영 migration, 배포와 회귀 QA를 갖는다. 다음 릴리스는 이전 릴리스의 운영 QA가 통과한 뒤 시작한다.

## 2. 변경 불가 원칙

- 결제·광고·캠페인 참여 여부는 평가 점수, 신뢰도, 배지 입력이 될 수 없다.
- 관리자는 원시 투표와 계산 결과를 직접 수정하지 않는다. 잘못된 이벤트는 무효화 사유와 감사 로그를 남기고 재계산한다.
- AI는 후보와 근거를 제시할 뿐 장소를 자동 공개하거나 기존 장소를 자동 병합하지 않는다.
- 폐업 확정 장소는 공개 지도·목록·검색에서 즉시 제외한다.
- 스냅샷은 원시 입력 수, 가중치 합, 설정 버전, 계산 시각, 근거를 보존해 재현 가능해야 한다.
- 공개 결과에는 이해하기 쉬운 설명을 제공하되 내부 부정행위 탐지 임계값과 계정 식별 정보는 노출하지 않는다.

## 3. 평가 데이터 모델

### 3.1 원시 평가

기존 `vote_events`와 `current_votes`를 원본으로 유지한다. 현재 투표를 집계할 때 투표자의 당시 역할을 스냅샷 입력에 기록하되 역할 변경으로 원시 이벤트를 다시 쓰지 않는다.

추가 구조:

- `rating_configs`: 알고리즘 버전, 공개 최소 표본, Beta prior, 리뷰어 최대 비중, 신뢰도·유사도 상수, 활성 기간.
- `rating_snapshots`: 장소별 전체·회원·리뷰어 집계, 점수, 표본 상태, 유효 가중치, 설정 버전, 근거 JSON, stale 여부.
- `reviewer_reliability_snapshots`: 리뷰어별 비교 가능 평가 수, 적중 수, posterior accuracy, 최종 신뢰 가중치, 버전.
- `reviewer_similarity_edges`: 두 리뷰어의 공통 평가 수, 일치율, 군집 ID, 감쇠값, 버전.
- `rating_recompute_jobs`: 장소 또는 전체 재계산 요청, 상태, 시도 횟수, 오류와 완료 시각.

### 3.2 공개 최소 표본

- 활성 투표가 8개 미만이면 추천율 숫자를 공개하지 않고 `표본 수집 중 · n/8`을 표시한다.
- 8개 이상이면 전체 추천율을 공개한다.
- 회원 또는 리뷰어 하위 집단은 해당 집단의 활성 투표가 각각 8개 이상일 때만 별도 숫자를 공개한다.
- 표본 기준은 `rating-v2.0` 설정에 저장하며 변경 시 새 버전을 발급한다.

### 3.3 기본 점수

각 집단은 Beta(2,2) posterior mean을 사용한다.

`score = round(100 × (2 + positiveWeight) / (4 + positiveWeight + negativeWeight))`

일반 회원 투표의 기본 가중치는 1이다. 리뷰어 투표의 원시 가중치는 아래 신뢰도와 유사도 감쇠를 적용한다. 일반 회원 투표가 하나 이상 존재할 때 리뷰어 유효 가중치 총합은 전체 결합 가중치의 30%를 넘지 않도록 비례 축소한다. 리뷰어가 적은 초기 단계에서 소수 리뷰어가 전체 점수를 지배하지 않게 하기 위함이다.

### 3.4 리뷰어 신뢰도

비교 가능한 평가는 리뷰어 투표 이후 형성된 일반 회원 8표 이상의 다수 방향과 비교한다. 자기 투표, 관리자 계정, 무효화된 투표는 제외한다.

- `posteriorAccuracy = (2 + correct) / (4 + eligible)`
- `reliabilityWeight = clamp(0.60, 1.40, 0.60 + 0.80 × posteriorAccuracy)`
- 비교 가능 평가가 5개 미만이면 중립값 1.00을 사용하고 `CALIBRATING`으로 표시한다.
- 정지 리뷰어의 신규 투표는 리뷰어 집계에서 제외하되 과거 스냅샷은 보존한다.

신뢰도는 사람의 자격 점수가 아니라 평가 예측의 통계적 안정성 지표로 설명한다. 관리자는 값을 직접 변경할 수 없다.

### 3.5 유사 리뷰어 중복 감쇠

- 공통 평가가 10곳 이상이고 같은 방향 비율이 80% 이상인 리뷰어들을 결정론적 union-find 군집으로 묶는다.
- 군집 크기가 `k`이면 각 리뷰어 투표에 `1 / sqrt(k)`를 곱한다.
- 공통 평가가 10곳 미만이면 군집을 만들지 않는다.
- 군집 ID, 공통 표본, 일치율, 감쇠값을 스냅샷에 기록한다.

이는 담합을 확정하는 판정이 아니라 상관된 표본이 독립 표본처럼 과대 계산되는 것을 줄이는 장치다.

## 4. 스냅샷과 재계산

- 투표 생성·변경·철회, 사용자 역할 변경, 리뷰어 상태 변경, 평가 설정 활성화 시 관련 장소를 stale로 표시한다.
- 요청 경로에서는 원시 투표만 원자적으로 저장하고 재계산 작업을 등록한다.
- 예약 작업이 대기 작업을 작은 배치로 재계산한다. 실패하면 마지막 정상 스냅샷을 유지하고 오류를 기록한다.
- 동일 장소·설정 버전·입력 해시의 재계산은 같은 결과를 내며 중복 스냅샷을 만들지 않는다.
- 관리자 화면에서 장소 단건, stale 전체, 설정 버전 전체 재계산을 요청할 수 있다.

## 5. 배지와 Flavor Print

### 5.1 Golden Pick

- ACTIVE 리뷰어만 PUBLISHED 장소에 부여할 수 있다.
- 리뷰어당 달력 월 기준 최대 3개다.
- 같은 리뷰어가 같은 장소에 다시 부여하려면 이전 부여 시점에서 90일이 지나야 한다.
- 부여 후 90일 동안 유효하며 철회·정지·장소 비공개 시 즉시 비활성화된다.
- 부여, 철회, 만료 근거를 이벤트와 감사 로그로 보존한다.

### 5.2 Hidden Gem

자동 후보 조건을 모두 만족할 때만 표시한다.

- 전체 활성 투표 8개 이상, 전체 점수 75 이상.
- 리뷰어 투표 3개 이상, 리뷰어 내부 점수 80 이상.
- 최근 90일 상세 조회가 같은 지역·대표 카테고리 공개 장소의 중앙값 이하.
- 조작 검토 사건이 열려 있지 않다.

조회 지표가 아직 없으면 배지를 발급하지 않고 `EXPOSURE_DATA_MISSING` 근거를 남긴다.

### 5.3 Hot Take

- 한 리뷰어의 투표가 자신을 제외한 리뷰어 5명 이상의 다수 방향과 다르다.
- 비교 집단의 동일 방향 비율이 70% 이상이다.
- 해당 리뷰어의 투표가 현재 활성 상태다.

Hot Take는 제재가 아니라 관점 차이를 설명하는 표시이며 장소 전체 배지가 아닌 리뷰어 평가에 연결한다.

### 5.4 Flavor Print와 취향 그래프

- 카테고리별 활성 템플릿은 5개 핵심 차원, 최대 7개 차원을 가진다.
- Workers AI는 상호명·카테고리·검수된 설명으로 차원 초안을 생성할 수 있지만 REVIEWER 또는 ADMIN 승인 전 공개하지 않는다.
- 리뷰어는 각 차원을 1~5로 평가하고 확신도 `LOW`, `MEDIUM`, `HIGH`를 선택한다.
- 장소 Flavor Print는 승인된 평가 3건 이상부터 차원별 중앙값과 사분위 범위를 공개한다.
- 사용자 취향 그래프는 사용자가 추천한 장소의 공개 Flavor Print 가중 평균으로 계산하며 최소 5곳 전에는 `학습 중`으로 표시한다.
- 사용자는 자신의 취향 그래프만 볼 수 있다. 공개 공유는 이번 범위에서 제외한다.

## 6. 조작 탐지와 운영 검토

자동 제재는 하지 않고 `integrity_cases`를 생성한다.

1차 신호:

- 신규 계정이 10분 안에 15곳 이상 투표.
- 같은 장소의 투표를 24시간 안에 5회 이상 변경.
- 한 장소가 10분 안에 평소 일간 중앙값의 5배 이상 투표를 받음. 기준 데이터가 없으면 20표를 절대 임계값으로 사용.
- 유사 리뷰어 군집이 한 장소 리뷰어 유효 투표의 70% 이상 차지.
- 폐업·비공개 장소에 대한 평가 요청 반복.

사건 상태는 `OPEN`, `REVIEWING`, `DISMISSED`, `CONFIRMED`다. 관리자는 근거 이벤트을 보고 처리 사유를 남긴다. `CONFIRMED`인 사건의 이벤트만 별도 무효화 레코드로 집계에서 제외하며 원본은 삭제하지 않는다.

IP 주소나 브라우저 지문은 이번 범위에서 수집·저장하지 않는다.

## 7. 장소 제안·정정·이의 제기

### 7.1 사용자 장소 제안

- 인증·이메일 확인 회원이 상호명, 주소, 대표 카테고리, 선택 설명을 제출한다.
- 서버가 정규화 이름, 주소, 전화, 100m 이내 좌표, 공공데이터 연결을 비교해 중복 후보를 제시한다.
- 중복 가능성이 있으면 사용자가 기존 장소 정정으로 전환하거나 `다른 장소` 사유를 제출한다.
- 상태는 `SUBMITTED`, `NEEDS_INFO`, `REVIEWING`, `APPROVED`, `REJECTED`, `DUPLICATE`다.
- 승인 시 DRAFT 장소를 생성하고 리뷰어 신청의 승인 제안 수를 원자적으로 갱신한다. PUBLISHED 전에는 기존 공개 검수 조건을 다시 통과한다.

### 7.2 업체·업주 정정 및 이의 제기

- 로그인 없이도 요청은 가능하지만 이메일 확인 링크를 완료해야 접수된다.
- 요청 유형은 정보 정정, 이전, 임시휴업, 폐업, 권리 침해, 기타다.
- 요청자 관계와 증빙 메타데이터를 기록하되 파일 업로드는 R2 이미지 릴리스 전까지 제공하지 않는다.
- 접수 즉시 공개 정보를 직접 변경하지 않는다. 폐업·권리 침해 긴급 요청은 관리자 큐 상단에 표시한다.
- 처리 상태, 운영자 답변, 변경된 필드와 이전 값을 감사 로그에 남긴다.

## 8. 중복 병합과 변경 이력

- 자동 중복 점수는 정규화 상호명, 주소, 전화, 공공데이터 관리번호, 좌표 거리를 사용한다.
- 동일 공공데이터 관리번호는 `EXACT`, 동일 전화+100m 이내는 `HIGH`, 이름 유사+100m 이내는 `MEDIUM` 후보로 분류한다.
- 자동 병합은 하지 않는다. 관리자가 기준 장소와 흡수 장소를 선택한다.
- 병합 시 투표·저장·카테고리·출처·제안·정정 요청을 기준 장소로 이동하고 slug redirect를 만든다.
- 충돌 필드는 관리자가 선택하며 전체 before/after JSON을 `place_revisions`에 기록한다.
- 복원은 새 revision을 만드는 전진 변경이다. 파괴적인 DB rollback을 하지 않는다.

## 9. 폐업 재검증

- 공공데이터 동기화가 공개 장소의 연결 영업 상태를 `CLOSED`로 변경하면 장소를 즉시 `HIDDEN`으로 바꾸고 재검증 사건을 연다.
- `TEMPORARILY_CLOSED`와 `UNKNOWN`은 공개 상태를 자동 변경하지 않고 운영 큐에 올린다.
- 공개 장소는 마지막 확인일로부터 90일 후 재검증 대상이 된다.
- 관리자 화면은 신규 폐업, 임시휴업, 원천 간 충돌, 90일 초과를 구분한다.
- 재개업은 기존 장소 이력을 유지한 채 관리자 승인으로 PUBLISHED 복원한다.

## 10. 실제 AI 보조 분류

- Cloudflare Workers AI binding과 JSON Mode를 사용한다. 1차 모델은 `@cf/meta/llama-3.1-8b-instruct-fast`, 모델 설정 키는 `AI_CLASSIFICATION_MODEL`, 프롬프트 버전은 `place-category-v1`로 고정한다. 모델 변경은 설정 버전과 회귀 표본 비교를 거친 새 릴리스로만 적용한다.
- 입력은 상호명, 공공데이터 업태, 주소 지역, 현재 활성 카테고리 목록뿐이다. 전화번호, 사용자 정보, 원본 전체 payload는 보내지 않는다.
- 출력은 대표 카테고리 slug, confidence 0~1, 최대 3개 근거, 모델명, 프롬프트 버전이다.
- JSON Schema 검증 실패, timeout, rate limit, 알 수 없는 slug는 실패로 저장하고 규칙 기반 수동 검수로 전환한다.
- 규칙과 AI가 일치하고 필수 데이터·중복·영업 상태 차단을 통과한 경우에만 `HIGH` 자동 승인 후보가 될 수 있다.
- 불일치, confidence 0.85 미만, AI 실패는 수동 확인이다.
- 같은 입력 해시는 30일간 결과를 재사용하고 관리자 재실행 시 새 실행 이력을 남긴다.
- 자동 예약 실행은 한 번에 최대 100개, 하루 최대 500개의 미분류 후보만 처리한다. 관리자가 실행 전에 대상 수를 확인할 수 있고, 한도를 넘는 후보는 다음 실행으로 넘긴다.

## 11. 관리자 대시보드와 알림

대시보드는 최근 24시간·7일·30일 기준으로 다음을 표시한다.

- 후보 수집·신규·갱신·실패·폐업·좌표 누락·중복 후보.
- 검수 대기·평균 처리 시간·승인·반려·담당자별 처리량.
- stale 평가·재계산 성공/실패·표본 부족 장소·배지 분포.
- 열린 조작 사건, 정정 요청, 폐업 재검증, 장소 제안.
- Workers AI 호출 성공률·실패 유형·캐시 적중률. 비용 수치는 Cloudflare가 제공하는 실제 측정값만 표시한다.

동기화 또는 재계산 작업이 실패하면 D1에 실패를 영속화하고 관리자 화면 상단에 표시한다. 외부 이메일 알림은 운영 문의 주소가 확정된 뒤 Resend로 연결하며, 그 전에는 대시보드 알림만 제공한다.

## 12. 권한과 감사

- USER: 투표·저장, 장소 제안, 정정 요청, 자신의 상태 조회.
- REVIEWER: USER 기능, Flavor Print 평가, Golden Pick, 자신의 평가 관리.
- ADMIN: 검수·병합·복원·재계산·사건 처리·AI 재실행.
- 모든 mutation은 서버 세션 역할을 확인한다.
- 관리자 작업은 actor, action, target, reason, before, after, timestamp를 기록한다.
- AI 실행은 모델·프롬프트·입력 해시·출력·검증 결과를 기록한다.

## 13. 오류 처리

- 평가 재계산 실패 시 마지막 정상 점수를 유지하고 갱신 지연을 표시한다.
- AI 실패 시 후보를 잃지 않고 규칙 기반 분류와 수동 선택을 유지한다.
- 병합은 모든 관련 레코드 이동이 성공할 때만 완료한다.
- 외부 데이터 충돌 시 가장 최근 데이터라고 자동 신뢰하지 않고 출처별 값을 보존한다.
- 알림 전송 실패는 본 작업 성공 여부와 분리해 기록한다.

## 14. 테스트와 출시 게이트

### 단위 테스트

- 8표 경계, Beta 점수, 30% 리뷰어 상한.
- 신뢰도 보정, CALIBRATING, 유사 군집과 제곱근 감쇠.
- Golden Pick 한도·90일, Hidden Gem, Hot Take, Flavor Print 공개 기준.
- 중복 점수, 폐업 상태 전이, AI 출력 검증과 fallback.

### D1 통합 테스트

- 이벤트 → stale → 재계산 → 스냅샷의 결정론적 흐름.
- 역할별 평가 집계, 무효화 이벤트 제외, 스냅샷 버전 재현.
- 제안 승인과 리뷰어 자격 카운트 원자성.
- 병합 관계 이동과 slug redirect, revision 복원.
- 폐업 자동 비노출, 감사 로그와 조작 사건 상태 전이.

### E2E

- 7표에서는 표본 수집 중, 8표에서 추천율 공개.
- 회원/리뷰어 점수 분리와 공개 표본 기준.
- 장소 제안 → 중복 경고 → 관리자 승인 → DRAFT 생성.
- 정정 요청 → 관리자 처리 → revision과 공개 정보 변경.
- 중복 병합 후 이전 URL redirect와 투표·저장 유지.
- 동기화 폐업 처리 후 회원 지도·목록·검색 비노출.
- AI 실패 후보가 수동 검수 가능하며 AI 단독 공개가 불가능함.

### 운영 배포 게이트

- migration 전 D1 export와 현재 Worker version 기록.
- 원격 migration 후 기존 로그인·지도·투표·저장·관리자 검수 회귀 테스트.
- 각 릴리스는 PR diff와 필수 체크를 검토한 뒤 squash merge한다.
- 병합된 `main`에서만 운영 배포하고 실패 시 이전 Worker version으로 롤백한다.
