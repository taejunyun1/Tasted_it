# Re:Taste 통합 기록 감사 설계

**상태:** PROPOSED — 이 문서는 읽기 전용 진단과 후속 구현의 설계 기준이다. 운영 데이터 수정, 원격 D1 마이그레이션, 보존기간 변경, 로그 삭제를 승인하지 않는다.

**작성일:** 2026-08-14 (KST)

**코드 기준선:** `origin/main@56b05f2`

## 1. 목적

Re:Taste의 장소, 리뷰, 추천, 관리자 조작, 계정·개인정보 관련 기록이 서로 모순되지 않고 필요한 기간 동안 추적 가능한지 검증한다.

감사는 다음 세 질문에 답해야 한다.

1. 현재 공개·추천·집계 결과가 원본 기록과 정책에 맞는가?
2. 중요한 변경을 누가, 언제, 어떤 근거로 수행했는지 재구성할 수 있는가?
3. 개인정보와 운영 기록이 정해진 보존·삭제 원칙을 지키는가?

## 2. 범위와 비범위

### 2.1 포함 범위

| 감사 영역 | 주요 기록 | 핵심 판정 |
| --- | --- | --- |

| 평가·리뷰 | `vote_events`, `current_votes`, `invalidated_vote_events`, `reviewer_visit_reviews`, `reviewer_visit_photos`, `golden_pick_events`, `rating_snapshots` | 이벤트 원장과 현재 상태, 재방문·Golden Pick·평가 스냅샷·사진 공개 상태 |

| 운영 데이터 | 주차·EV snapshot/run 테이블, R2 사진 정리 작업 | 스냅샷 활성화 단일성, 실패·재시도, DB 메타데이터와 R2 객체의 정합성 |

### 2.2 비범위

- 운영 데이터를 자동 수정·삭제·재분류하지 않는다.
- 비밀값, 세션 원문, 이메일 원문, R2 이미지 원본을 감사 보고서에 싣지 않는다.
- Cloudflare 계정 수준 접근 로그의 실제 보존기간은 계정 관리자 설정 확인 전에는 준수 판정하지 않는다.
- 추천 품질의 주관적 우수성을 판정하지 않는다. 대신 정책 위반·입력 누락·결과 재현 가능성만 판정한다.

## 3. 감사 방식

### 3.1 1단계: 읽기 전용 기준선 감사

운영 D1은 SELECT만 허용한 별도 감사 명령으로 조회한다. 결과에는 원문 개인식별정보 대신 건수, 해시, 식별자 일부 마스킹 또는 안전한 내부 ID만 남긴다.

기본 관찰 기간은 다음과 같다.

| 기록 유형 | 관찰 기간 | 이유 |
| --- | --- | --- |
| 현재 상태 테이블 | 전체 활성 레코드 | 현재 공개·추천 결과의 안전성 |
| 이벤트·관리자 로그 | 최근 180일, 최근 30일 추세 별도 | 정책 전환과 최근 회귀 탐지 |
| 제품 이벤트·비회원 세션 | 전체 중 만료 임계 전후 35일 | 30일 TTL 실행 확인 |
| 리뷰어 재방문·Golden Pick | 최근 365일 | 90일 정책과 만료 연결 확인 |
| 스냅샷·동기화 실행 | 최근 180일 | 정기 실행·실패·재시도 확인 |

감사는 스키마 프로필, 관계 무결성, 상태 전이, 시간·보존, 집계 재현, 정책 적격성 순서로 실행한다.

### 3.2 2단계: 상시 감사 체계

1단계에서 확인된 안정적 규칙만 자동화한다. 모든 규칙을 한 번에 강제하지 않는다.

상시 체계는 다음 네 부분으로 구성한다.

1. **통합 감사 이벤트 계약**: 중요 변경에 `actor`, `action`, `target`, `before`, `after`, `reason`, `requestId`, `policyVersion`, `occurredAt`을 남긴다.
2. **일일 정합성 검사**: 고아 참조, 공개·추천 위반, 이벤트와 현재 상태 불일치, 만료 데이터 잔존, 사진 DB/R2 불일치를 검사한다.
3. **관리자 감사 화면**: 최근 변경, 실패한 운영 작업, 열린 정합성 이슈, 보존 작업 결과만 제공한다.
4. **증거 보존**: 검사 결과는 민감 정보 없이 요약·표본 ID·실행 버전·시각을 보존한다.

## 4. 판정 기준

### 4.1 데이터 정합성

| 등급 | 기준 | 예시 | 처리 원칙 |
| --- | --- | --- | --- |
| Critical | 공개·추천·권한·삭제 결과가 잘못되거나 복구 불가 | HIDDEN 장소가 추천됨, 삭제된 사진이 공개됨, 다른 사용자 데이터 노출 | 즉시 공개·추천 차단 또는 롤백, 원인 분석 |
| High | 핵심 집계·정책을 실질적으로 왜곡 | 투표 원장과 현재 투표 불일치, 중복 리뷰 발행, Golden Pick 만료 누락 | 수정 PR과 재계산 전까지 이슈 추적 |
| Medium | 운영자가 판단할 근거가 부족하거나 일부 데이터가 누락 | 감사로그에 사유·전후 값이 없음, 동기화 실패 재시도 기록 부족 | 다음 운영 릴리스에서 보강 |
| Low | 표시·형식·문서 불일치 | 날짜 형식 차이, 설명 문구와 실제 TTL 문서 불일치 | 문서 또는 UI 정리 |

### 4.2 행위 추적 최소 요건

다음 변경은 행위자 또는 자동 실행 주체, 대상 ID, 전후 상태, 시각, 사유를 모두 가져야 한다.

- 장소 승인·반려·병합·복원·영업 검증·추천 제외 복원
- 리뷰어 승인·정지·복귀
- 리뷰 발행·철회·재방문 발행·Golden Pick 부여·철회·만료
- 무결성 케이스 확인과 투표 무효화
- 자동 체인·비음식점 제외와 해제

자동 작업은 `actorUserId = null`만으로 충분하지 않다. 실행 종류, 규칙/정책 버전, 실행 ID 또는 근거를 함께 남겨야 한다.

### 4.3 개인정보·보존 판정

현재 정책의 확인 대상은 다음이다.

- 비회원 취향 세션: 만료 후 삭제되고 연결 배지도 함께 삭제되는지
- 제품 이벤트: 발생 후 30일을 넘긴 레코드가 남지 않는지
- 세션: 로그아웃·탈퇴·만료 후 접근이 가능한지
- 사진: 공개 메타데이터만 노출되고 EXIF·원본 위치 정보가 남지 않는지
- 관리자 감사로그: 사용자 삭제 뒤에도 감사 목적의 최소 정보만 남고 식별자 참조가 안전하게 `NULL` 처리되는지

탈퇴 시 투표·리뷰·감사로그의 보존·익명화 정책은 아직 확정 전이다. 감사 결과에서 이 항목은 반드시 **정책 결정 필요**로 분리하며, 임의로 삭제 적합 판정을 내리지 않는다.

## 5. 핵심 감사 규칙

### 5.1 공개·추천 적격성

- `places.status != PUBLISHED`인 장소는 공개 목록·상세·추천·코스 후보에 나타나지 않아야 한다.
- `place_liveness_states.recommendationExcluded = 1`인 장소는 추천 후보에만 제외되고, 공개 상세와 기존 링크 정책은 별도 계약을 따라야 한다.
- 추천 결과에 반환된 장소마다 공개 상태, 카테고리, 좌표, 후보 근거가 완결되어야 한다.
- 추천 요청은 입력한 알고리즘 버전과 정책 근거를 재현 가능한 범위에서 반환해야 한다.

### 5.2 이벤트 원장과 현재 상태

- 각 `current_votes` 행은 유효한 마지막 `vote_events` 행과 연결되어야 한다.
- `invalidated_vote_events`에 있는 이벤트는 평가 재계산 입력에서 제외되어야 한다.
- Golden Pick `GRANT`는 같은 grant를 참조하는 `WITHDRAW` 또는 `EXPIRE`가 있을 때만 비활성으로 계산되어야 한다.
- 리뷰어 방문 리뷰는 동일 리뷰어·장소의 정책상 허용 기간을 지키며, 90일 이후 재방문은 별도 신뢰 배지로 남되 기존 점수 집계에 중복 반영되지 않아야 한다.
- `reviewer_visit_reviews.photoCount`와 `reviewer_visit_photos` 개수·순번·R2 객체 존재가 일치해야 한다.

### 5.3 장소·운영 이력

- 승인된 장소 제안·정정·병합은 `place_revisions` 및 `admin_audit_logs`와 상호 추적 가능해야 한다.
- 사업자 원천, 제외 상태, 연결 장소의 상태가 정책상 모순되지 않아야 한다.
- 영업 검증 상태가 `HIDDEN`이면 추천 제외·공개 상태·재검증 케이스가 정의된 계약대로 함께 변화해야 한다.
- 동기화 run은 동시에 둘 이상 `RUNNING`으로 남지 않고, 실패한 run은 오류 요약과 종료 시각을 가진다.

## 6. 결과물

1. **기준선 감사 보고서**: 데이터셋·기간·검사 수·결과·심각도·영향·근거·권장 조치.
2. **검사 SQL/테스트 묶음**: 민감 값 없이 재실행 가능한 쿼리와 로컬 fixture 테스트.
3. **감사 커버리지 표**: 중요 행위별 기록 유무, 보존기간, 소유 서비스, 자동 검사 여부.
4. **운영 이슈 백로그**: Critical/High는 즉시 조치 PR, Medium/Low는 소유자·기한·재검증 조건을 가진 이슈.
5. **상시 감사 설계**: 1단계 결과 후 필요한 스키마·배치·UI만 별도 계획으로 제안.

## 7. 보안·운영 안전장치

- 운영 감사 명령은 SELECT 전용 연결과 명시적 allowlist 쿼리만 사용한다.
- 모든 보고서 결과는 이메일·전화·세션·사진 키·주소 전체를 출력하지 않는다.
- 원격 D1 조회는 페이지네이션·행 상한·실행 시간 상한을 둔다.
- Critical 발견 시에도 자동 변경하지 않는다. 차단 또는 복구는 별도 PR과 명시된 운영 실행 계획으로 분리한다.
- 보고서·이슈에는 실행 기준 커밋, 스키마 버전, 감사 시각(KST), 검사 버전을 함께 남긴다.

## 8. 성공 기준

- 각 감사 영역마다 최소 하나 이상의 재현 가능한 정합성 검사와 판정 기준이 있다.
- 중요 상태 전환의 감사로그 커버리지와 누락 목록을 수치로 제시한다.
- 개인정보·보존 관련 확인/미확정 정책을 구분해 공개한다.
- Critical/High 이슈는 영향 범위와 안전한 다음 행동이 명확하다.
- 감사 자체가 운영 데이터·비밀값·개인정보를 추가로 노출하거나 변경하지 않는다.

## 9. 단계적 실행 순서

1. 로컬 fixture로 검사 규칙과 보고서 형식을 검증한다.
2. 승인된 읽기 전용 범위에서 운영 기준선 스냅샷을 수집한다.
3. 보고서와 이슈 백로그를 검토하고 Critical/High 조치 범위를 별도 PR로 확정한다.
4. 반복되는 규칙만 일일 검사·운영 화면·감사 이벤트 계약으로 승격한다.

## 10. 결정 필요 항목

- 탈퇴한 회원의 투표·리뷰·감사로그 보존 또는 익명화 기준
- 관리자 감사로그의 최소 보존기간과 접근 권한
- Cloudflare 접근·오류 로그의 실제 보존 설정과 담당자
- 재방문 리뷰의 신뢰 배지 명칭, 공개 범위, 점수 비반영 규칙의 최종 정책
- 감사 보고서 열람 권한: ADMIN 전용인지, REVIEWER까지 요약을 허용할지
