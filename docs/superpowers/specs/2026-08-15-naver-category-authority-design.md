# NAVER 지역검색 우선 카테고리 검증 설계

- **상태:** ACCEPTED — PR #117 병합을 승인 기록으로 하며, 운영 호출은 kill switch를 명시적으로 켠 뒤에만 허용한다.
- **작성일:** 2026-08-15
- **소유:** Codex (`codex/naver-category-authority`)
- **범위:** 공공데이터 원천 업태, 상호 규칙, AI 보조 판단으로 분류하던 장소 카테고리에 NAVER 지역검색의 검증된 결과를 최우선 근거로 추가한다.

## 1. 문제와 목표

현재 분류기는 공공데이터의 원천 업태와 상호명 규칙을 중심으로 동작한다. 이 방식은 `식육(숯불구이)`와 `정종/대포집/소주방`처럼 명확한 업태에는 효과적이지만, 넓은 업태·상호 변경·부정확한 공공데이터가 섞이면 기본 카테고리로 남을 수 있다.

목표는 장소명과 위치가 함께 일치하는 NAVER 지역검색 결과의 카테고리를 가장 강한 외부 검증 근거로 쓰되, 동명이인과 넓은 카테고리 때문에 잘못 덮어쓰지 않는 것이다.

### 목표

1. 검증된 NAVER 지역검색 결과를 음식 카테고리 판정의 최우선 근거로 사용한다.
2. 상호명·주소 또는 좌표가 함께 맞지 않는 검색 결과는 자동 분류에 쓰지 않는다.
3. `음식점`, `한식`, `주점` 같은 넓은 NAVER 카테고리는 구체 업태·메뉴 근거보다 우선하지 않는다.
4. 원천 업태·NAVER 카테고리·상호·AI의 일치 여부를 신뢰도 점수와 관리자 검수 근거에 함께 표시한다.
5. AI 신뢰도가 높아도 관리자는 언제나 카테고리를 직접 수정할 수 있다.
6. 기존 공개 장소와 대기 후보를 일괄 재검증하되, 낮은 확신 결과는 자동 변경하지 않는다.

### 비목표

- 네이버 지도 웹 화면을 자동 수집하거나 비공식 방식으로 크롤링하지 않는다.
- 사용자 지도·목록 요청마다 NAVER 검색 API를 호출하지 않는다.
- NAVER의 사진·리뷰·소개 문구를 수집하거나 저장하지 않는다.
- 낮은 확신 검색 결과로 공개 장소를 자동 숨기거나 삭제하지 않는다.
- AI가 NAVER 또는 원천 업태의 명확한 근거를 단독으로 뒤집지 않는다.

## 2. 사용 API와 전제

현재 서비스의 `NAVER_MAPS_CLIENT_ID`는 지도 렌더링과 주소 지오코딩에만 쓴다. 업체 카테고리를 얻으려면 서버 전용 NAVER 지역검색 API(현재 NAVER API Hub 이관 대상)를 별도로 등록해야 한다.

| 항목 | 현재 | 이번 설계 |
| --- | --- | --- |
| Dynamic Map·Geocoding | 사용 중 | 주소·좌표 확인에 계속 사용 |
| 지역검색(Local Search) | 미사용 | 상호·주소·카테고리 검증에 사용 |
| 자격증명 | 브라우저 지도 Client ID | 서버 전용 검색 API 자격증명, 비밀값으로 보관 |
| 호출 시점 | 사용자 주소 확인 시 | 수집·관리자 재검증·제한된 배치에서만 |

구현 전에 NAVER API Hub에서 지역검색 제공 여부, 이용약관상 응답 보관 조건, 무료·유료 한도, 오류 코드, 운영 애플리케이션 등록 상태를 확인한다. 이 조건이 확인되지 않으면 기능 플래그를 끈 채 기존 규칙만 사용한다.

## 3. 검증된 NAVER 매칭

검색어는 `상호명 + 시·군·구 또는 도로명 일부`로 구성한다. API가 반환하는 최대 5개 결과 중 하나를 다음 기준으로 판정한다.

| 결과 | 상호명 | 위치 | 처리 |
| --- | --- | --- | --- |
| `VERIFIED` | 정규화 후 정확히 일치하거나 지점 표기를 제외한 동일 상호 | 정규화 주소가 일치하거나 기존 좌표와 100m 이내 | 자동 분류 근거로 사용 |
| `LIKELY` | 높은 유사도이나 지점·약칭 차이 존재 | 같은 시·군·구까지만 일치 | 관리자 검수 후보, 자동 변경 금지 |
| `AMBIGUOUS` | 둘 이상의 결과가 같은 점수 | 주소 또는 좌표가 서로 다름 | 충돌로 보류 |
| `NO_MATCH` | 일치 후보 없음 | - | 기존 원천·상호 규칙으로 진행 |
| `OUT_OF_SCOPE` | 광주·전남 밖 결과 | - | 폐기 |

정규화는 NFKC, 공백·기호·지점 표기 정리, 도로명·지번 주소 정규화를 포함한다. 단, 카테고리만 맞는 결과나 상호명만 비슷한 결과를 같은 장소로 보지 않는다.

## 4. 카테고리 결정 순서

“NAVER 우선”은 **검증된 일치와 충분한 세분성**이 함께 있을 때만 적용한다. 넓은 NAVER 카테고리는 구체적인 원천 업태·메뉴 신호보다 약하다.

| 우선순위 | 근거 | 예시 | 자동 처리 |
| --- | --- | --- | --- |
| 0 | 비음식·유흥 제외 정책 | PC방, 편의점, 룸살롱 | 기존 제외 정책 유지 |
| 1 | `VERIFIED` NAVER의 구체 카테고리 | 육류·고기요리, 냉면, 베이커리 | 매핑된 카테고리 제안 |
| 2 | 공공데이터의 구체 원천 업태 | 식육(숯불구이), 정종/대포집/소주방 | 매핑된 카테고리 제안 |
| 3 | 상호의 구체 음식·재료 신호 | 장어, 국밥, 라멘, 떡볶이 | 매핑된 카테고리 제안 |
| 4 | `VERIFIED` NAVER의 넓은 카테고리 | 한식, 음식점, 카페 | 보조 점수만 부여 |
| 5 | 넓은 원천 업태와 원천 종류 기본값 | 일반음식점, 한식 | 최후 기본값 |
| 6 | AI 판단 | 근거 사이의 의미 보완 | 동점 해소·검수 보조만 |

### 충돌 규칙

1. NAVER의 구체 카테고리와 구체 원천 업태가 다르면 자동 변경하지 않고 `CONFLICT`로 보낸다.
2. 한쪽이 넓은 카테고리고 다른 쪽이 구체 카테고리면 구체 카테고리가 이긴다.
3. 상호의 구체 음식 신호는 넓은 NAVER 카테고리를 이길 수 있다. 예: `풍천장어구이`가 NAVER에서 단순 `한식`으로 나오면 해산물·장어 카테고리를 유지한다.
4. `LIKELY`, `AMBIGUOUS`, `NO_MATCH`는 기존 규칙을 대체하지 않는다.
5. AI는 후보 중 하나를 추천할 수 있지만, 1~3순위 확정 근거와 반대일 때 자동 저장하지 않는다.

## 5. 신뢰도와 AI 검증

카테고리의 신뢰도는 단일 AI 점수가 아니라 근거의 일치도와 세분성으로 계산한다.

| 구성 | 최대 점수 | 조건 |
| --- | ---: | --- |
| NAVER 매칭 신뢰도 | 40 | `VERIFIED`의 이름·주소/거리 일치 |
| NAVER 카테고리 세분성 | 20 | 내부 카테고리로 단일 매핑 가능한 구체 표현 |
| 공공데이터 원천 업태 일치 | 20 | 같은 내부 카테고리 또는 넓은 상위 카테고리 일치 |
| 상호 음식 신호 일치 | 10 | 구체 메뉴·재료 표현 일치 |
| AI 판단 일치 | 10 | 위 후보와 같은 카테고리일 때만 가산 |

- 85점 이상: `HIGH` — 후보 자동 승인 가능. 단, 직접 관리자 수정은 항상 허용한다.
- 65~84점: `MEDIUM` — 미리보기에서 변경 후보로 표시하고 관리자 일괄 승인만 가능하다.
- 40~64점: `LOW` — 자동 변경 금지, 검수 큐로 보낸다.
- 명확한 근거 사이 충돌: `CONFLICT` — 점수와 무관하게 자동 변경 금지.

AI가 `HIGH`여도 카테고리 `<select>`를 잠그지 않는다. AI 신뢰도는 설명과 우선 검수 순서를 위한 메타데이터이지 관리자 권한 제한이 아니다.

기존 **공개 장소**의 제한된 이력 보정은 `VERIFIED` 이름·주소/100m 일치(40) + NAVER 구체 카테고리(20) + 원천 세부업태 일치(20)까지 확인된 `80점`도 관리자 일괄 적용 대상으로 허용한다. 이는 새 후보의 자동 승인과 다르며, NAVER 응답을 임의로 신뢰하는 규칙이 아니다. 이름·주소·구체 업태 중 하나라도 빠지거나 충돌하면 수동 확인으로 남긴다.

## 6. 데이터·호출·보존 정책

### 저장하는 것

각 장소에 대해 재검증 가능한 최소 결과만 저장한다.

- 검증 상태(`VERIFIED`, `LIKELY`, `AMBIGUOUS`, `NO_MATCH`, `FAILED`)
- 내부 매핑 카테고리, 매칭·세분성·최종 신뢰도 점수
- 조회 시각, 규칙 버전, 입력 지문(상호·주소의 해시)
- 사람에게 보여줄 수 있는 제한된 근거 코드(예: `NAVER_EXACT_ADDRESS`, `SOURCE_SUBTYPE_GRILL`)

NAVER 원문 응답, 이미지, 리뷰, 설명 문구는 저장하지 않는다. 원문 카테고리 문자열과 링크의 보관도 API 이용약관을 확인한 뒤 꼭 필요한 기간에만 허용한다.

### 호출 제한

1. 수집 시 새 후보 1회, 주소·상호가 바뀐 경우 1회, 관리자의 명시 재검증에서만 호출한다.
2. 일괄 재검증은 1회 100곳 이하이며, 호출 상한·실패 수·다음 커서를 기록한다.
3. 정상 `VERIFIED` 결과는 기본 90일 동안 다시 조회하지 않는다. 단, 제공자 이용약관의 허용 보존 기간이 더 짧으면 그 기간을 우선한다.
4. 사용자 공개 화면에서는 외부 호출을 하지 않는다.
5. 일일 한도·타임아웃·재시도 횟수는 환경 변수와 kill switch로 제한한다. 한도 초과·429·5xx에서는 기존 분류를 유지하고 `FAILED`만 기록한다.

초기에는 새 cron을 추가하지 않는다. 기존 수집 흐름과 관리자 배치로 검증한 뒤, 관측·중복 실행·비용 한도가 확인되면 별도 설계로 유지보수 작업을 검토한다.

## 7. 관리자 경험

관리자 검수 행은 현재 카테고리만 보여 주지 않고 다음을 한 줄 요약으로 표시한다.

```text
현재: 백반·가정식
제안: 주점 · HIGH 92
근거: NAVER 상호·주소 일치 → 포장마차 / 원천 업태 정종·대포집·소주방 일치
```

- `자동 적용 가능`, `관리자 확인`, `충돌`, `검색 실패`, `원천 없음` 탭으로 나눈다.
- 고신뢰 AI 결과를 포함해 모든 행에서 직접 카테고리 변경·저장이 가능해야 한다.
- 수정 후에는 NAVER·원천·상호·AI 각각의 찬성/반대 근거를 펼쳐 확인한다.
- 일괄 적용은 `VERIFIED + HIGH`만 기본 선택하며, `MEDIUM`·`CONFLICT`는 명시적으로 선택하지 않으면 포함하지 않는다.
- 각 변경은 기존 `admin_audit_logs`에 전후 카테고리, 규칙 버전, 근거 코드, 검증 시각을 남긴다.

## 8. 기존 장소 재검증과 롤아웃

1. **사전 표본 검증:** 상호·주소·업태가 다른 100곳을 local fake와 운영 읽기 전용 preview로 비교한다.
2. **미리보기:** 원천이 연결된 `PUBLISHED` 장소와 `PENDING` 후보를 100곳 단위로 분류한다. 원천 없는 장소는 별도 검수 큐로 남긴다.
3. **1차 적용:** `VERIFIED + HIGH` 변경만 적용한다. 공개 장소를 삭제하거나 숨기지 않는다.
4. **2차 검수:** `MEDIUM`·`CONFLICT`와 비음식 제외 후보를 관리자가 확인한다.
5. **운영 확인:** 변경 수와 감사 로그 수, 제외 수, 외부 API 실패·한도 소진 수를 대조한다.

롤백은 migration 되돌리기가 아니라 감사 로그의 이전 카테고리로 forward-fix 한다. API kill switch를 끄면 즉시 기존 공공데이터·상호 규칙만으로 분류한다.

## 9. 구현 경계와 테스트

외부 API는 `NaverLocalSearchAdapter` 하나로 격리한다. 라우트·React 컴포넌트는 API를 직접 호출하지 않는다. local/unit/integration 테스트에서는 반드시 fake adapter를 사용하며 실제 NAVER 호출은 운영 승인된 별도 contract 검증만 수행한다.

필수 검증:

1. 정확 상호+주소 일치, 좌표 100m 이내, 동명이인, 지점명 차이, 광주·전남 밖 결과.
2. 구체 NAVER 대 구체 업태 충돌, 넓은 NAVER 대 구체 메뉴 우선, AI 반대 사례.
3. 고신뢰 AI 행의 관리자 직접 수정 가능 여부.
4. 429·5xx·타임아웃·한도 초과 시 기존 카테고리 유지와 안전한 실패 기록.
5. 100곳 cursor batch의 재시도·중복 감사 로그 방지·rollback 근거.
6. 데스크톱·모바일 관리자 미리보기, 탭, 직접 수정, 접근성 QA.

## 10. 구현 전 승인 게이트

이번 설계는 기존 지도 기능을 넘어 NAVER 지역검색이라는 외부 API를 추가한다. 따라서 구현 PR에는 아래를 명시해야 한다.

1. NAVER API Hub의 지역검색 이용 가능 상태, 이용약관·응답 보관 조건.
2. 검색 API 전용 secret, 도메인·권한 설정, local fake, 운영 kill switch.
3. 일·월 쿼터와 비용 상한, 1회·1일 호출 상한, 429·5xx 사용자/관리자 UX.
4. 전송 데이터(상호·주소), 저장 데이터, 보존기간, 로그 마스킹.
