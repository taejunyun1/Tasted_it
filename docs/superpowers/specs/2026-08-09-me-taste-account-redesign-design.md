# 나의 취향·계정 센터 리디자인 설계

## 1. 목표

`/me`를 단순한 계정 정보 목록이 아니라 사용자의 취향과 활동을 가장 먼저 보여주는 개인화 허브로 재구성한다. 사용자는 페이지에 진입한 즉시 자신의 대표 취향, 취향 학습 진행도, 저장·평가 활동을 이해할 수 있어야 하며, 같은 페이지 아래에서 이메일·비밀번호·Google·네이버 연결과 즉시 회원 탈퇴까지 실제로 처리할 수 있어야 한다.

## 2. 선택한 방향

### 검토한 대안

1. **A형 — 취향 중심 허브 + 하단 계정 설정**
   - 장점: Re:Taste의 핵심 가치인 취향 기록이 첫 화면에서 명확하다.
   - 장점: 계정 관리가 콘텐츠를 방해하지 않으면서도 한 페이지 안에 남는다.
   - 단점: 페이지가 길어질 수 있으므로 모바일 접이식 구성이 필요하다.
2. **B형 — 취향 페이지와 계정 설정 페이지 완전 분리**
   - 장점: 각 화면이 짧고 단순하다.
   - 단점: 사용자가 계정 상태를 확인하기 위해 추가 탐색해야 한다.
3. **C형 — 모든 정보를 동일 비중의 대시보드로 배치**
   - 장점: 많은 정보를 한 번에 볼 수 있다.
   - 단점: 빈 데이터가 많은 초기 사용자에게 복잡하고 Re:Taste의 취향 중심성이 약해진다.

### 결정

A형을 사용한다. 페이지의 상위 70%는 취향과 활동에 사용하고, 계정 및 보안은 하단의 독립된 설정 영역으로 분리한다.

## 3. 시각 방향

### 디자인 토큰

- 배경 `Paper Cream`: `#FAFAF8`
- 기본 글자 `Ink`: `#14251C`
- 브랜드 녹색 `Field Green`: `#22543D`
- 선택 강조 `Signal Lime`: `#E7FF55`
- 보조 표면 `Mist Green`: `#EDF4ED`
- 카드 표면 `White`: `#FFFFFF`
- 기본 구분선 `Line`: `#CDD4CC`
- 위험 행동 `Danger`: `#B4233A`
- 본문 글꼴: `SUIT`, `Pretendard`, `Apple SD Gothic Neo`, `Noto Sans KR`, system-ui
- 데이터·눈썹 제목: `IBM Plex Mono`

### 형태와 밀도

- 페이지 최대 폭은 기존 `.shell`의 `1280px`을 유지한다.
- 대표 카드와 설정 그룹은 `24px`에서 `28px`의 R값을 사용한다.
- 취향·상태 뱃지는 완전한 알약 형태(`999px`)를 사용한다.
- 저장·평가 목록 카드는 `18px` R값을 사용하고, 정보 카드 전체에 동일한 큰 그림자를 반복하지 않는다.
- 테두리는 `1px`로 유지하며, 대표 취향 카드 한 곳에만 `8px` 오프셋 그림자를 사용한다.
- 그라데이션, 장식용 이모지, 의미 없는 일련번호는 사용하지 않는다.

### 이 페이지의 대표 요소

`나의 취향 신호` 영역을 페이지의 시각적 서명으로 사용한다. 실제 Flavor Print 상위 값을 최대 3개의 큰 뱃지로 보여주고, 가장 높은 값 하나만 라임 배경으로 강조한다. 이는 장식이 아니라 추천 취향의 현재 근거를 요약한다.

## 4. 정보 구조

### 4.1 프로필 헤더

- 눈썹 제목: `MY TASTE / PROFILE`
- 제목: `{displayName}님의 취향`
- 이메일과 이메일 인증 상태를 보조 정보로 제공한다.
- 우측에는 `리뷰어 신청·상태`를 보조 버튼으로 둔다.
- 저장 수, 평가 수, 취향 학습 장소 수를 작은 활동 뱃지로 표시한다.

### 4.2 나의 취향 신호

- `tasteGraph.status === "VISIBLE"`이면 값이 높은 순으로 정렬한 뒤 최대 3개를 표시한다.
- 뱃지 문구는 데이터 해석을 과장하지 않고 `{dimension.key} {value.toFixed(1)}` 형태로 쓴다.
- 최상위 뱃지만 라임 배경과 진한 녹색 테두리를 사용한다.
- 나머지 뱃지는 흰색 배경과 진한 녹색 테두리를 사용한다.
- 세부 영역에는 모든 dimension을 막대로 표시해 대표 뱃지의 근거를 확인할 수 있게 한다.
- 임계값을 이용해 `좋아함`, `싫어함` 같은 의미를 임의 생성하지 않는다.

### 4.3 학습 중 상태

- Flavor Print가 있는 추천 장소가 5개 미만이면 임의 취향 뱃지를 만들지 않는다.
- 대표 뱃지는 `취향 학습 중 {placeCount}/5` 하나만 표시한다.
- 5칸 진행 표시와 `장소를 평가할수록 코스 추천이 더 선명해져요.` 안내를 제공한다.
- 다음 행동은 `맛집 둘러보기` 링크로 연결한다.

### 4.4 저장·평가 기록

- 데스크톱에서는 2열, 모바일에서는 1열로 배치한다.
- 각 섹션 헤더에 제목과 실제 개수를 뱃지로 표시한다.
- 장소 행은 카테고리·동네, 장소명, 상태 행동으로 구성한다.
- 저장한 장소는 `상세 보기`와 `저장 해제`를 제공한다.
- 평가한 장소는 `추천했어요` 또는 `비추천했어요` 상태 뱃지를 제공한다.
- 빈 상태는 단순 문장만 남기지 않고 다음 행동으로 연결하는 링크를 제공한다.

### 4.5 계정 및 보안

- 취향 영역과 구분되는 하단 설정 카드로 제공한다.
- 데스크톱에서는 항상 펼쳐지고, 모바일에서는 `<details>` 기반 접이식 그룹을 사용한다.
- 그룹은 `기본 정보`, `로그인 연결`, `계정 삭제` 세 개로 구분한다.

#### 기본 정보

- 닉네임은 2자 이상 30자 이하로 변경할 수 있다.
- 이메일 변경은 새 주소 입력 → 기존 계정 세션 확인 → 새 주소로 Resend 확인 메일 발송 → 30분 안에 링크 확인 순으로 처리한다.
- 확인 전까지 기존 이메일을 로그인 주소로 유지한다.
- 이미 사용 중인 이메일은 일반화된 오류 문구로 거절한다.
- 비밀번호가 있는 계정은 `비밀번호 변경 메일 보내기`, 소셜 전용 계정은 `비밀번호 등록 메일 보내기`로 표시한다.
- 비밀번호 설정은 기존 재설정 토큰 흐름을 재사용하고 이메일 존재 여부를 외부에 노출하지 않는다.

#### 로그인 연결

- Google과 네이버를 각각 한 행으로 표시한다.
- 연결됨/연결되지 않음을 상태 뱃지로 명확히 표시한다.
- 연결되지 않은 제공자는 OAuth 연결 흐름을 시작한다.
- 연결된 제공자는 다른 로그인 수단이 하나 이상 있을 때만 해제할 수 있다.
- 마지막 로그인 수단은 해제 버튼 대신 `다른 로그인 수단을 먼저 등록해 주세요.` 안내를 표시한다.
- 연결·해제 결과는 페이지 상단의 `role="status"` 또는 `role="alert"` 메시지로 전달한다.

#### 즉시 회원 탈퇴

- 별도의 옅은 붉은색 위험 구역에 배치한다.
- 사용자가 `탈퇴합니다`를 정확히 입력하고 최종 버튼을 눌러야 한다.
- 서버는 현재 세션을 다시 확인한 뒤 사용자 행을 삭제한다.
- 사용자와 연결된 세션, 인증 식별자, 저장, 평가, 계정 토큰은 외래키 cascade로 함께 삭제한다.
- 삭제 후 세션 쿠키를 즉시 만료시키고 `/`로 이동한다.
- 탈퇴는 복구할 수 없다는 내용을 버튼 바로 위에 명시한다.

## 5. 컴포넌트 경계

- `app/routes/me.tsx`
  - loader/action 조합과 페이지 섹션 배치를 담당한다.
  - loader는 화면에 필요한 사용자, 활동, 취향, 로그인 수단 상태만 반환한다.
  - action은 intent를 해석한 뒤 독립된 계정 서비스 함수를 호출한다.
- `app/components/me/TasteSignals.tsx`
  - 취향 상위 3개 정렬, 학습 상태, 전체 dimension 막대를 렌더링한다.
  - 데이터 해석 규칙을 UI 내부에 중복하지 않는다.
- `app/components/me/ActivityCollection.tsx`
  - 저장·평가 목록과 빈 상태를 일관된 카드 형태로 렌더링한다.
- `app/components/me/AccountSettings.tsx`
  - 기본 정보, 로그인 연결, 위험 구역을 렌더링한다.
  - 서버 데이터와 action 결과만 소비하며 DB에 직접 접근하지 않는다.
- `app/features/auth/account-management.server.ts`
  - 닉네임 변경, 이메일 변경 요청·확정, 비밀번호 메일 요청, 제공자 연결 해제, 회원 삭제 정책을 담당한다.
- Google OAuth 공통 흐름
  - 기존 Google 로그인 동작을 유지하면서 `LOGIN`, `CONNECT`, `DISCONNECT` 흐름을 구분한다.
  - 네이버와 동일한 마지막 로그인 수단 보호 정책을 적용한다.

## 6. 데이터 변경

- 신규 순번 migration으로 이메일 변경 요청에 필요한 `pending_email`과 전용 확인 토큰 목적을 추가한다.
- 이미 운영에 적용된 migration은 수정하지 않는다.
- 회원 삭제가 요구하는 cascade 관계를 새 migration과 통합 테스트로 검증한다.
- 비밀값이나 OAuth 토큰은 DB, 로그, URL query 또는 PR에 저장하지 않는다.

## 7. 서버 동작과 오류 처리

- 모든 action은 `requireUser`를 먼저 수행한다.
- action intent는 허용 목록으로 검증하며 알 수 없는 값은 `400`으로 거절한다.
- 닉네임, 이메일, 탈퇴 확인 문자열은 Zod 스키마로 검증한다.
- 이메일 발송 실패 시 pending 상태를 남기되 기존 이메일과 로그인은 그대로 유지하고 재시도 안내를 표시한다.
- OAuth 제공자 장애는 해당 연결 행에 오류를 표시하며 이메일 로그인과 다른 제공자 로그인은 유지한다.
- 저장 해제는 기존 동작을 보존한다.
- 성공 action은 PRG(Post/Redirect/Get) 패턴으로 `/me`에 돌아와 중복 제출을 방지한다.

## 8. 반응형과 접근성

- `900px` 이상: 취향 대표 영역 2열, 활동 기록 2열, 계정 설정 전체 펼침.
- `899px` 이하: 모든 핵심 영역 1열, 계정 그룹 `<details>` 접이식.
- `520px` 이하: 카드 안쪽 여백을 줄이고 뱃지는 가로 스크롤이 아니라 줄바꿈한다.
- 모든 상태는 색상만으로 구분하지 않고 텍스트를 함께 제공한다.
- 뱃지 목록은 의미 있는 목록 구조를 사용한다.
- progress와 meter에는 스크린리더용 이름과 현재 값을 제공한다.
- 위험 행동은 키보드로 수행 가능하며 확인 문자열이 맞지 않으면 버튼을 비활성화한다.
- 포커스 표시와 `prefers-reduced-motion` 설정을 보존한다.

## 9. 검증

### 단위 테스트

- 취향 dimension이 값 내림차순으로 정렬되고 최대 3개만 대표 뱃지로 선택되는지 확인한다.
- 학습 상태에서 임의 취향 뱃지가 생성되지 않는지 확인한다.
- 계정 상태별 연결·해제 버튼 문구와 마지막 로그인 수단 보호 문구를 확인한다.

### 통합 테스트

- 닉네임 변경 성공과 길이 검증을 확인한다.
- 이메일 변경 요청, 중복 이메일 거절, 새 이메일 확인, 기존 이메일 유지 정책을 확인한다.
- 비밀번호 등록·변경 메일 요청을 확인한다.
- Google·네이버 연결 해제와 마지막 로그인 수단 보호를 확인한다.
- 회원 삭제 후 사용자 연관 데이터와 세션이 제거되는지 확인한다.

### 브라우저 검증

- QA 계정의 취향 학습 중 상태와 취향 공개 상태를 각각 확인한다.
- 데스크톱 `1440×1000`, 모바일 `390×844` 화면을 캡처한다.
- 저장 해제, 모바일 계정 접이식, 탈퇴 확인 입력, 키보드 포커스를 확인한다.
- 브라우저 콘솔 오류가 없어야 한다.

## 10. 구현 단위 분리

이 설계는 한 페이지에서 만나는 경험이지만, 리뷰 가능한 크기를 유지하기 위해 두 개의 독립된 구현 계획으로 나눈다.

1. **취향 허브 리디자인**
   - 프로필 헤더, 취향 신호, 학습 상태, 저장·평가 기록, 현재 제공 중인 네이버 연결 상태를 새 레이아웃으로 구현한다.
   - 데이터베이스나 인증 정책을 변경하지 않는다.
   - 이 단위만 병합해도 기존 기능을 잃지 않는 완성된 `/me` 화면이어야 한다.
2. **계정 수명주기 관리**
   - 닉네임·이메일·비밀번호, Google·네이버 연결 관리, 즉시 회원 탈퇴를 구현한다.
   - 신규 migration과 인증 서비스 변경은 이 단위에만 포함한다.
   - 아직 구현되지 않은 동작은 첫 번째 단위에서 비활성 버튼이나 가짜 링크로 노출하지 않는다.

두 단위는 각각 별도 테스트와 검토를 통과한 뒤 순서대로 병합한다. 최종적으로 두 단위가 모두 반영되어야 이 설계 전체가 완료된다.

## 11. 완료 조건

- `/me`가 코스 추천 페이지의 크림·딥그린·라임 디자인 언어와 일치한다.
- 대표 취향이 실제 데이터 기반 뱃지로 가장 먼저 읽힌다.
- 데이터 부족 상태가 과장 없이 다음 행동을 안내한다.
- 저장·평가 기록과 계정 설정이 명확히 분리된다.
